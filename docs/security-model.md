Bombadil is built to protect one thing: the person's ability to see what the agent did and to take it back. It is not a sandbox. The agent runs as the account `user` with passwordless `sudo`, and each provider CLI starts in its no-prompt mode, so whatever that account or root can do, the agent can do. Nothing confines it. Several checks in the code (the desk gate, the job gate, the risk marks, the app check, the mail marks, the press check and the connection tools' marks) keep a well-behaved agent tidy and do not stop a hijacked one. What stands in for guard rails is a restore point of the root filesystem before each turn, plain-words narration of each step, and a Stop that needs no model. The agent has no tool that sends mail, posts a Slack reply, creates a task or writes a comment, and each of those leaves only on the person's own press, which the code checks and cannot enforce against a process that runs as the person. The keys to Slack and the work tools are kept by a service with a system user of its own, in a directory the person's own programs cannot open; the image still gives the agent passwordless `sudo`, so that protection is a rule with a check and not a wall ([The connection service](#the-connection-service)). A coding session, the vendor's own tool started by a word in the pill, is not a turn: no restore point, narration or Stop stands behind it, it keeps the account's passwordless `sudo`, and the code takes its processes for the agent's where it asks who pressed or typed ([Coding sessions](#coding-sessions) below; how they work is in [coding sessions](architecture/coding-sessions.md)). This page lists where the code grants power, which doors are open, where secrets sit, what undo does not reach and what is intended but not enforced. The reasoning for the choice is in [the principle](principles.md#full-access-with-undo) and [foundation choices](design/foundation-choices.md); this page does not repeat it.

Where this page says "designed", a brief decides it and no code exists. Where it says "convention", the code says so itself or a reader can walk around it.

The kernel enforces one boundary here, between accounts, and the agent holds root through `sudo`. The connection service is the one piece of Bombadil that runs as an account of its own, so its keys sit behind that boundary, and `sudo` is the way across it ([The connection service](#the-connection-service)). Inside the account every box runs as the same user, so the boxes are separated by convention, not by permission. The one line the code draws inside the account is the systemd scope: each turn's CLI and everything it starts run in a `bombadil-turn-` scope (`agentd` falls back to the CLI's process tree where the machine cannot make one), a coding session's tool runs in a `bombadil-dev-<project>-<role>-<run>` scope, `procs.cgroup_of` recognises both (`procs.AGENT_SCOPES`), and `agentd`, the mail service, the connection service and the browser service read the scope of the process on the other end of a socket to decide whether it is the agent's. A process the agent starts outside both is not marked: a `job` unit, or anything started with `systemd-run --user`, passes ([Coding sessions](#coding-sessions)). Between the person and the account there is nothing: `greetd` logs `user` in on tty1 without a prompt, the account has an empty password, and no lock screen is installed. Bombadil's own code listens only on Unix sockets (`agentd.sock`, `brain.sock`, `mail.sock`, `browserd.sock`, `connect.sock` as its own user and, as root, `watch.sock`), and the bar owns a name on the session bus for notifications. The connection service connects out to Slack and to the work tools' servers. Bombadil connects to Chromium's debugging port on loopback, checks that the provider's host answers on port 443, and asks the nameserver for the MX record of a mail domain the person types (`src/bombadil/signin.py:91-97`, `src/bombadil/sysmap.py:240-257`, `src/bombadil/mail/accounts.py:127-184`). Network traffic otherwise comes from the provider CLIs, Chromium, Thunderbird, `pacman`, `npm` or a command the agent runs.

## Who can reach what

| Interface | Reachable by | Protection | Where defined |
|---|---|---|---|
| `agentd` socket, `$XDG_RUNTIME_DIR/bombadil/agentd.sock` | Any process that can open the file: the agent, generated apps, the shell, the Mail window, `bombadil`, `bombadil-browser`, `bombadil-os-mcp`, `bombadil-signal` (what the coding tools' hooks run) and the coding sessions themselves. | No mode is set and the protocol has no authentication, so the socket takes its mode from the process umask. The folder is made with the default mode. The only guard is `/run/user/<uid>`, which systemd-logind makes 0700; that is not in this repository and no test checks it. `agentd` does read `SO_PEERCRED` for every client: one inside a turn's `bombadil-turn-` scope or a coding session's `bombadil-dev-` scope, or one it cannot name, is taken for the agent, so its typed prompt is marked `asked_by: "agent"` (a launcher word is carried out whoever sent it, so the look decides nothing for one) and its notice chips, dismissals and presses are refused. A process outside both scopes (a generated app the person opened, a shell, a command in a `job` unit) is treated as the person; a coding session's tool and its hooks are inside a scope, so what it types is marked as the agent's and its presses, chips and dismissals are refused. Every other message is taken with no look at who sent it, from a process in a scope too: `stop`, `local`, `open`, `card` (which takes diagrams only from a client), `desk`, `jobs`, `ai`, `signin`, the `desk-tool`, `job-tool`, `mail-tool` and `connect-tool` messages and the rest. The messages the bar sends about connections that change something, `proposal`, `card_action` and `notification`, are looked at and refused to a process in an agent's scope. ## The connection service

Messages and connections ([how it works](architecture/connect.md), the wire contract in [CONNECT.md](CONNECT.md)) add two services. `bombadil-connect` is a system service with a user of its own: it keeps the keys to Slack and the work tools and is the one place that does what leaves the machine. `bombadil-browserd` is a user service that holds a connection to the browser panel's Chromium and reads a page. This section says who can reach them and what stops what, from the code at `24c836c`. It does not repeat the protocol.

**The token store is a rule with a check, not a wall.**

- The keys are closed to the person's own programs and not to `sudo`. `user ALL=(ALL) NOPASSWD: ALL` is in `iso/airootfs/etc/sudoers.d/bombadil` and the agent runs as `user`, so its shell can read `connect.db`, where every key is in the clear, and a process that holds a key can call Slack or a work tool directly, with no card, no fingerprint and no press. The unit file says so in a comment. The store becomes a wall only if the agent loses `sudo`, which nothing in the code does.
- A press on `connect.sock` is checked for who sent it and for which words, not against a secret. The fingerprint is a SHA-256 of the kind, the target and the content, which any caller can work out, so a process of the person's outside both scopes (one started with `systemd-run --user`, say) can connect to the 0666 socket and ask for a post, and the service does it when a connection owns the target and can post. The fingerprint guards a card that changed under the person's press.
- Reading straight on the socket is open to the agent. The marks, the quoting and the ledger that flags a later draft belong to the tools in `agentd`; a process in a scope that asks the socket directly for `messages` gets the words unmarked, and no turn is remembered as having read them.
- Disconnecting deletes the keys from `connect.db` and stops the driver. Nothing tells Slack or the tool's server that the grant is over.
- What stands against all of it is the connection skill and the tools' descriptions, which tell the agent not to, the fingerprints, the warnings on a card, the press log and the refusals above, none of which is a boundary against `sudo`.

## What undo covers and does not

How the restore point is taken and applied is in [restore points](architecture/restore-points.md). This table says what it reaches.

| Thing | Covered | Why, and where |
|---|---|---|
| System files, packages, `/etc`, `/usr`, `/var` (the `@` subvolume) | Yes, from the next restart | `iso/airootfs/usr/local/bin/bombadil-install:23-27`, `iso/airootfs/usr/local/bin/bombadil-rollback:2-16` |
| The person's files, `~/Apps` and app data, `~/.claude`, `~/.codex`, the browser profile, the mail profile, turn logs, `brain.db`, `proposals.json` (`@home`) | No | `iso/airootfs/usr/local/bin/bombadil-install:23,27`. The answer to "undo" says "Your home folder and apps stay as they are" (`src/bombadil/launcher.py:863-864`), and `narrate` marks `rm` in the home folder irreversible for that reason (`src/bombadil/narrate.py:471-476`). |
| `persona.toml`, `said.json` and `tips.json` | No | They are in the home folder. An edit of `persona.toml` that the agent makes with its own tools is worded "Changing how I talk to you" and is not a change to the system: it has no summary entry and no Undo on the closing line, so `undo` has nothing to offer for it and would not reach the file if it had. The card (`voice`) or a request to the agent changes the name and voice back. `src/bombadil/narrate.py:989`, `src/bombadil/narrate.py:1073-1074`. |
| The connection service's keys and press ids, `/var/lib/bombadil-connect` (the `@` subvolume) | Yes, from the next restart | The store is in `@`, so an undo puts it back as it was before the last turn: a key replaced or revoked since comes back and fails, and the ids of presses performed since are forgotten, so a reply or a task that went stays posted and a draft already marked sent answers with its old receipt and asks the service nothing. `iso/airootfs/usr/local/bin/bombadil-install:23-27`, `iso/airootfs/etc/systemd/system/bombadil-connect.service:22-23`, `src/bombadil/outbox.py:238-250`. |
| The kernel, initramfs and boot loader (`/boot`, the EFI partition) | No | After a kernel update and an undo, the older root can boot the newer kernel. The installer takes the kernel from the system it copies. `iso/airootfs/usr/local/bin/bombadil-install:11-15,39-41`, [known issues](known-issues.md#open). |
| The restore points | No | They sit on the same disk at `/.snapshots`. Snapper's cleanup timer keeps the newest 30 (`NUMBER_LIMIT=30`, with no hourly ones: `TIMELINE_CREATE=no`), so on a long-lived install the oldest restore point goes by design. The agent can still delete any of them, or change that configuration, with `sudo`. The old roots `@.undone-<time>` that each undo leaves are not snapper's, and nothing removes them. `iso/airootfs/usr/local/bin/bombadil-install:46,70-72,98-99`, `src/bombadil/snapshots.py:43-46`, [retention](architecture/restore-points.md#retention-and-pruning). |
| Anything that left the machine | No | Mail, Slack replies, tasks and comments, pushes, uploads and everything sent to the provider. |
| The live ISO | No restore points exist | `snapshots.available` needs a snapper config, which only an installed system has. `src/bombadil/snapshots.py:32-34`, `src/bombadil/launcher.py:833-836`. |
| A turn with `snapshots = false`, or without snapper | No restore point is taken | `src/bombadil/config.py:52`, `src/bombadil/agentd.py:2783`, `src/bombadil/agentd.py:3420`. |
| A coding session's work | No restore point is taken for it | `src/bombadil/dev.py` calls nothing in `snapshots`. What a session changes in `@home` (the project, a worktree and its branch, the tool's own state) is outside undo. What it changes under `@` is in no restore point of its own: an undo goes back to the state before the last turn, whatever a session did before it. [Coding sessions](#coding-sessions). |

Undo itself depends on parts the agent can change. It runs `sudo snapper` and `sudo bombadil-rollback` (`src/bombadil/snapshots.py:37`, `src/bombadil/snapshots.py:66`), and `sudo`, `snapper` and the script all sit in `@`. The swap happens at the next restart, so the agent keeps running on the old root until then. `bombadil-rollback` moves `@` aside as `@.undone-<time>` and only then creates `@` from the restore point, so a failure between the two leaves no `@` (`iso/airootfs/usr/local/bin/bombadil-rollback:14-15`). A start that fails does not put itself back: no boot-count, rescue or repair code exists, and a restore point is applied by running `bombadil-rollback` by hand. Putting a failed start back is designed in the [installed OS brief](design/installed-os-brief.md) and not built.

## Things that cross to other people

The rule is [only the person's press reaches people](principles.md#the-persons-press-reaches-people): the agent reads, drafts and points, and the person's own press releases. For mail, for a Slack reply and for a new task or a comment in a work tool the press is built as a check that refuses a press from inside an agent's turn. For everything else it is a rule, not a wall.

```mermaid
flowchart LR
    AG["Agent: mail_draft"]
    P["The person"]
    W["Mail window"]
    A["agentd: Outbox.press"]
    S["bombadil-mail: send"]
    T["Thunderbird"]
    AG -->|"draft, not sent"| S
    P -->|"presses Send"| W
    W -->|"press, fingerprint"| A
    A -->|"send, unless it came from a turn's scope"| S
    S -->|"checks what was shown"| T
    AG -.->|"a press from its own scope: refused"| A
    AG -.->|"a process it started outside the scope: passes"| A
```

- **What the code does.** `os-mcp` registers no tool whose purpose is to send, post, share, pay or push (`src/bombadil/mcp_server.py:60-182`, `src/bombadil/appkit/tools.py:159-246`, `src/bombadil/cardtools.py:118-152`, `src/bombadil/mail/tools.py:67-127`). `show_card` and `system_map` only draw. The `job` tool runs any shell command, which is the same power as the shell. A mail draft leaves only on the person's press on the Send that the Mail window drew: the window sends a `press` to `agentd`, `Outbox.press` refuses it from a process inside an agent's turn, from one whose sender it cannot name and from one that has gone, and then calls the mail service's `send` once, which also refuses a process in a turn's scope and checks that the draft is what was shown. Each press leaves a row in `presses.jsonl`, mode 0600. `agentd` writes a repeated refusal from the same process, one of those that say something about who pressed, at most once in 5 seconds; the mail service writes its refusal for a press from a turn's scope at most once in 10 seconds, with a count of the ones it skipped. A typed "send it" opens the draft in the Mail window and says that sending is the person's; it sends nothing. A reply, a new task or a comment is a proposal in `proposals.json`, drawn on a card in the bar: the agent's `propose` makes one, and `Outbox.press` takes a press on the card's Send, Create or Comment button the same way, after the three fingerprints (the proposal's own, the pressed one and the one the card said it drew) agree, and asks the connection service to do it once ([The connection service](#the-connection-service); `src/bombadil/outbox.py:61`, `src/bombadil/outbox.py:194-201`, `src/bombadil/outbox.py:274-284`, `src/bombadil/outbox.py:290-303`, `src/bombadil/mail/service.py:114`, `src/bombadil/mail/service.py:1686-1700`, `src/bombadil/agentd.py:659-662`, `src/bombadil/agentd.py:1506-1533`, `src/bombadil/mail/service.py:1659-1700`, `src/bombadil/launcher.py:633-643`).
- **What the code does not do.** The agent has a shell, the network and `sudo`, so `curl`, `git push` or a chat client works. Nothing blocks them. The system prompt tells the agent to "act, don't ask for permission" (`src/bombadil/providers.py:44-45`) and has a line about sending only for mail: the agent cannot send mail, and the person's press does. It has no line about other ways out (`src/bombadil/providers.py:50-56`). Narration marks risky commands and does not pause (`src/bombadil/narrate.py:8`).
- **The press is a check, not a wall.** The check reads the systemd scope of the process on the other end of the socket, which `procs.cgroup_of` recognises when it is a `bombadil-turn-` or a `bombadil-dev-` scope, and whether the process is in the running turn's process tree, which is what marks a turn that has no scope (`src/bombadil/procs.py:92-101`, `src/bombadil/agentd.py:1535-1541`, `src/bombadil/outbox.py:274-284`). A process the agent starts outside its scope passes it: a command started with the `job` tool runs in its own `systemd-run --user` unit (`src/bombadil/jobs.py:363-366`), and so does anything else it starts with `systemd-run --user`. Anything running as the person can also read Thunderbird's profile or connect to `mail.sock`. Against that stand the system prompt and the mail skill, which tell the agent not to, and the connection skill, the fingerprints, the draft warnings and the press log.
- **What is designed, and not built.** A kind of press other than mail and the three proposals (`Outbox.register` takes one, `Outbox.__init__` registers `mail` and one performer for each of `KINDS`, and nothing in `src/` calls `register` otherwise: `src/bombadil/outbox.py:177-178`, `src/bombadil/connect/driver.py:32`), a general outbox the agent fills, `agentd` accepting presses only from the shell's own process, the agent losing `sudo`, which would turn the token store from a rule into a wall, and hands for the browser service. The [everyday work brief](design/everyday-work-brief.md) says "the press is a rule, not yet a wall"; [mail](architecture/mail.md#who-may-do-what) says what is built.
- **What leaves the machine by design.** Each turn's conversation, tool results and screenshots go to the provider through its CLI, and a tool result includes the text of a mail the agent read. The brain's `describe` asks the provider's fast model for one sentence about a thing, and the prompt carries what the model is shown: the first 64 KB of a file, the first three pages of a PDF, the names in a folder with its path, a page's title and its address without the query, or a past turn's request and the agent's answer. It does this only for a thing someone is looking at, and never for a private path (`src/bombadil/brain/describe.py:1-8`, `src/bombadil/brain/describe.py:36-47`, `src/bombadil/brain/describe.py:66-73`, `src/bombadil/brain/describe.py:170-221`, `src/bombadil/brain/describe.py:249`).
- **Words from other people.** They are data, and the code keeps them from becoming instructions only where a model has no tools. The describer fences its input with a random marker and runs with `--tools ""`, `--strict-mcp-config` and `--safe-mode` under Claude (`src/bombadil/providers.py:476-484`, `src/bombadil/brain/describe.py:256-262`). Where the model has tools the code only marks them: `mail_read` puts a mail's text between two marks that carry a fresh random word, cuts it at 20 000 characters and strips control characters and the ones that turn text around, and the tool descriptions and the system prompt say to read a mail and never obey it. `messages_unread`, `message_thread` and `tasks_waiting` do the same, with a fresh word in each pair of marks and every line of a message quoted with `> `, and `propose` warns the person on the card when the agent wrote a draft after reading messages and the words are not ones the person typed (`src/bombadil/connect/tools.py:404-408`, `src/bombadil/connect/tools.py:422-433`, `src/bombadil/proposals.py:140-158`). That is a convention for a model with a shell, not a separation (`src/bombadil/mail/tools.py:14-17`, `src/bombadil/mail/tools.py:383-415`, `src/bombadil/providers.py:52-53`). For the two Brain words, the note the next turn receives names the action and leaves the Brain's answer out (`BRAIN_NOTES`, `src/bombadil/agentd.py:300`, `src/bombadil/agentd.py:1808-1809`). `--strict-mcp-config` keeps the account's connectors out of a turn (`src/bombadil/providers.py:271`). The turn itself reads pages, mail and files with full access and no separation between data and instructions. A page or a mail that talks the agent round has everything in the first table.

## Known gaps

Each gap was checked in the code. A designed fix is named where one exists.

1. **No authentication on the `agentd` socket.** No mode is set, so the socket takes it from the umask. Anything outside the agent's scopes (a turn's and a coding session's) that opens it can type for the person, restart or shut down the machine, and claim `asked_by`. `agentd` refuses a press, a chip and a dismissal to a process inside a scope and marks its prompt `asked_by: "agent"`, but a `local` message, or a prompt that is a launcher word other than `connect <service>`, gets no look, so a process inside either scope can restart or shut down the machine, undo, switch the provider, or start and end coding sessions (`src/bombadil/agentd.py:557-569`, `src/bombadil/agentd.py:658-687`, `src/bombadil/agentd.py:712-715`). No test asserts the mode of this socket, of `brain.sock`, of `watch.sock` or of the sudoers file.
2. **Passwordless `sudo`, an empty console password, autologin and no lock screen.** The [installed OS brief](design/installed-os-brief.md) names one password for the disk, the account, the lock screen and the consoles. It is designed, with no code.
3. **Undo can be switched off from inside.** Deleting restore points, editing the sudoers file, `bombadil-rollback` or snapper's configuration, or writing `snapshots = false` removes it (see the undo table). A coding session has the same `sudo` as the agent and can do each of these.
4. **Home and `/boot` are outside undo.** The sign-ins, the vault files, `~/Apps`, the mail copy, the turn logs, `persona.toml` and the Tips file are in `@home`.
5. **The debugging port is open to every local process.** The profile it controls is the person's.
6. **Generated apps are unconfined.** `Command` runs `/bin/sh -c`, `TextFile` and `KitFiles` write any path the user can, and `Processes.kill` signals any process of the user (`src/bombadil/appkit/native/command.py:172-176`, `src/bombadil/appkit/native/files.py:136-144`, `src/bombadil/appkit/context.py:36-39`, `src/bombadil/appkit/native/processes.py:243-253`). `Agent.ask` types as the person, except from an app that runs inside a turn's or a coding session's scope, as an app the agent opened does; an app the person opened from the pill does not (`src/bombadil/appkit/native/agent.py:181-191`, `src/bombadil/outbox.py:199-200`). `Clipboard` clears a copied secret after a delay the app chooses, only if the app asks (`src/bombadil/appkit/native/clipboard.py:37-48`). The kit has no network component, and nothing stops an app's Python or a `Command` from using the network.
7. **The Vault protects a file, not a secret from the agent.** The agent writes the app that shows the unlock screen and holds root.
8. **The press rule is enforced by a scope check, and a process outside both scopes passes it.** The check covers mail, a Slack reply and a new task or a comment, and refuses a process in a turn's or a coding session's scope; one the agent starts in a `job` unit or with `systemd-run --user` is in neither. For everything else the press is a rule. The system prompt has a line about sending only for mail, and the connection skill says the same for the rest.
9. **The provider login travels with the install.** `bombadil-install` copies `.claude`, `.claude.json`, `.codex` and `.config/bombadil` (which holds `persona.toml`) to the installed home, and from the state folder `desk.toml` and `tips.json` (`iso/airootfs/usr/local/bin/bombadil-install:82-90`).
10. **Live-only exposures.** The root serial shell and the boot entry that erases `/dev/vda` exist in the live image. The installer removes the first (`iso/airootfs/usr/local/bin/bombadil-install:33-34`). `scripts/run-vm.sh` refuses to attach a disk that already holds a system because of the second (`scripts/run-vm.sh:30-37`).
11. **The CLIs are not pinned.** `npm install -g` fetches the provider CLIs at image build time, with no version or hash, and `bombadil-setup` runs `sudo npm install -g` the same way when one is missing. Packages from pacman are signature-checked (`iso/pacman.conf:5`, `scripts/build-iso.sh:19-23`, `iso/airootfs/usr/local/bin/bombadil-setup:12-13`).
12. **The Codex describer has less than the Claude one.** Claude gets `--tools ""` and no connectors. Codex gets a read-only sandbox only (`src/bombadil/providers.py:674-679`), though the describer's docstring says "no tools and no MCP servers" (`src/bombadil/brain/describe.py:10-12`).
13. **The whole screen goes to the vendor.** `screenshot` captures every window, including a password the person has on screen. It leaves `screen.png` in a temporary folder that nothing in the code removes (`src/bombadil/mcp_server.py:105-109`).
14. **No firewall.** The repository sets none.
15. **The mail copy and its tokens are not encrypted at rest.** Thunderbird's profile holds the person's mail and its login store, readable by anything that runs as the person, and the installer has no encrypted layout (`src/bombadil/mail/engine.py:1000-1004`, `iso/airootfs/usr/local/bin/bombadil-install:16-27`).
16. **A coding session is on the agent's side of the scope check, and keeps `sudo`.** `procs.cgroup_of` returns a scope when its name starts with `bombadil-turn-` or `bombadil-dev-` (`procs.AGENT_SCOPES`), so `agentd`, the mail service, the connection service and the browser service refuse a press, a notice chip, a dismissal and a proposal's edit from a session's tool, and mark its typed words as the agent's. Where the machine makes no scope a session has none, and nothing can tell its processes from the person's. A process it starts outside the scope passes, as one the agent starts does. Stop does not reach a session, no restore point is taken for its work, `narrate` marks none of its steps, the agent can start one with a launcher word, and it has the account's passwordless `sudo` with nothing in the code to remove it, so it can write `@`, turn undo off like the agent (gap 3) and read the connection service's keys (gap 20; `iso/airootfs/etc/sudoers.d/bombadil:2`, `src/bombadil/procs.py:89-100`, `src/bombadil/outbox.py:274-284`, `src/bombadil/dev.py:413`, `src/bombadil/dev.py:428-436`, `src/bombadil/agentd.py:1964-2004`). Not checked: the tools' own permission prompts (no session was run), and whether another process can type into a session through zellij's own socket.
17. **The `dev`, `dev-signal` and `away` messages are neither authenticated nor looked at.** Any client can bring back, restart or end a session that is in the registry, report a state for it with up to 140 characters of the sender's own words that the pill and the cards then show, make a "yours" entry, and clear the Away card. A forged `SessionStart` sets the session's conversation id, which `command_for` puts in the command that resumes it, and a forged `exit` with a non-zero code sets the path of the session's last screen, which `bombadil dev why` prints in the details drawer, so any file the user can read can be put on the screen (`src/bombadil/agentd.py:731-750`, `src/bombadil/dev.py:581-584`, `src/bombadil/dev.py:630-637`, `src/bombadil/dev.py:827-839`, `bin/bombadil:166-177`).
18. **`BOMBADIL_OS` and `BOMBADIL_SESSION` are plain environment variables.** `bombadil-signal` skips a run when `BOMBADIL_OS=1`, and `session_env` removes the mark from a session. Whoever starts a process can set or clear it, so it only keeps the agent's own turns out of the dots, and it stops no message from reaching `agentd` (`bin/bombadil-signal:130-131`, `src/bombadil/dev.py:808-824`).
19. **A session's last screen and the hook spool are kept without a mode.** `dev/<project>-<role>.last` holds what was on the screen when a tool stopped, `dev/signals.jsonl` holds hook events until `agentd` reads it, and the registry holds the first line of each prompt typed to a tool. No code sets a mode on them, and nothing deletes a `.last` file (`src/bombadil/dev.py:864-871`, `src/bombadil/dev.py:885-931`).
20. **The keys to Slack and the work tools are readable with `sudo`.** `connect.db` is 0600 in a 0700 directory of a system user, and the agent's `sudo` opens both. A key read that way works with no card, no fingerprint and no press, and nothing in the code removes `sudo`. The store is in `@`, so an undo can bring back a key that was replaced or revoked. Disconnecting deletes the copy and does not tell Slack or the tool that the grant is over (`iso/airootfs/etc/sudoers.d/bombadil:2`, `src/bombadil/connect/store.py:67-74`, `src/bombadil/connect/store.py:243-281`, `iso/airootfs/etc/systemd/system/bombadil-connect.service:14-23`; [The connection service](#the-connection-service)).
21. **The connection socket has no secret, and a peer in an agent's scope can read from it unmarked.** `connect.sock` is mode 0666 and takes any user whose uid is in the range, so a process of the person outside both scopes can ask it to post, and it does when a connection owns the target and can post; the fingerprint is public and says what was pressed, not who pressed. A process in a scope that asks for `messages`, `thread` or `tasks` on the socket directly gets the words with none of the marks the tools add, and no turn is remembered as having read them, so the card's warning about a draft written after reading does not follow (`src/bombadil/connect/service.py:81-90`, `src/bombadil/connect/service.py:751-767`, `src/bombadil/connect/service.py:992-1027`, `src/bombadil/connect/driver.py:70-75`).
22. **Any program on the session bus can put a line above the pill.** The bar owns `org.freedesktop.Notifications`, and a notification from the agent's `notify` tool (which runs `notify-send`) or from any other program (the start hook's comment names a web page's) is shown the same way, made plain and cut to 60 characters of summary and 100 of body, at most one line for each app in 2 seconds. Nothing marks the line as another program's: it reads as the summary and the body, and the app's name is on it only when there is one of the two, and on the card that Reply draws. Reply's card copies the person's words and cannot send, and Open invokes the notification's own action, which is the sender's (`src/bombadil/notifications.py:60-67`, `src/bombadil/notifications.py:108-112`, `src/bombadil/notifications.py:133-178`).

## If you fork it

Decide first whether you keep full access. If you do, add no confirm dialog for something undo can reverse; make it visible and undoable, as [the principle](principles.md#full-access-with-undo) says. If you narrow it, the places are the two flag sets in `src/bombadil/providers.py:267` and `src/bombadil/providers.py:590-592`, `iso/airootfs/etc/sudoers.d/bombadil`, the system prompt in `src/bombadil/providers.py:33-70`, and `tests/test_providers.py`. Nothing in Bombadil is built to ask, so narrowing means building that.

Before you hand an image to anyone else:

| Do this | Where |
|---|---|
| Set a password: drop `passwd -d user`, and stop `greetd` logging `user` in unasked or pair it with disk encryption. | `iso/airootfs/usr/local/bin/bombadil-install:60`, `iso/airootfs/etc/systemd/system/bombadil-live.service:8`, `iso/airootfs/etc/greetd/config.toml` |
| Install a lock screen. `lock` already runs `hyprlock` when it is present. | `iso/packages.x86_64`, `src/bombadil/launcher.py:1037-1041` |
| Give the `agentd` socket mode 0600, as the brain and the mail service do, and decide what `agentd` does with a peer outside the agent's scopes (it takes one for the person) and with `dev`, `dev-signal` and `away`, which it does not look at. | `src/bombadil/agentd.py:569`, `src/bombadil/agentd.py:731-750`, `src/bombadil/agentd.py:1446-1468`, `src/bombadil/brain/service.py:376`, `src/bombadil/mail/service.py:506-511` |
| Remove boot entries 02 and 03 and the serial autologin from the profile. | `iso/efiboot/loader/entries/`, the `ttyS0` serial-getty drop-in folder under `iso/airootfs/etc/systemd/system/` |
| Pin the provider CLI versions. | `scripts/build-iso.sh:19-23`, `iso/airootfs/usr/local/bin/bombadil-setup:12-13` |
| Make the home folder 0700 and set a session umask of 077. The installer sets neither. | `iso/airootfs/usr/local/bin/bombadil-install:58-59` |

When you add something:

- **A socket or a port.** Put it under `paths.runtime_dir()`, set its mode in the code, check `SO_PEERCRED` when others can open it, and add a test for the mode. The mail socket has a test of its mode (`tests/test_mail_service.py:303`), the connection socket, its directory and its database have one (`tests/test_connect_service.py:388-394`) and so does the browser socket (`tests/test_browserd.py:329`); `agentd.sock`, `brain.sock` and `watch.sock` have none.
- **A tool in `os-mcp`.** It is power handed to a model that reads other people's words. Register it with `OsTools._tool` (`src/bombadil/mcp_server.py:46-54`). Give the agent a way to prepare, never a tool that releases, and put the press where only the person's own press reaches it.
- **Something that reaches people.** Register a performer with `Outbox.register(kind, performer)` (`src/bombadil/outbox.py:177-178`) where `agentd` builds its outbox (`src/bombadil/agentd.py:457`; the three proposal kinds are registered in `Outbox.__init__`), and let only the person's press on a view the person controls call it. Have the service that does the act check what was shown, as the mail service's `send` and the connection service's `perform` do (each works the fingerprint out again, refuses a peer in an agent's scope, and writes the press down as `unknown` before the act), and add no second way from a press to an act. Never add a tool that releases, such as a `mail_send`, and keep the scope check and the press log. Tests: `tests/test_outbox.py`, `tests/test_mcp_server.py:410`; [extending mail](architecture/mail.md#extending-it).
- **A process the person starts through the agent, as a coding session is.** Decide which side of the scope check it is on (`procs.cgroup_of` recognises the names in `procs.AGENT_SCOPES`, a turn's and a coding session's), what its hooks may send and who else may send the same message, and whether its work needs a restore point. `bombadil-signal` trims what it sends and `agentd` believes it ([Coding sessions](#coding-sessions)).
- **A key to another service.** Keep it in the connection service's store (`ConnectionSecrets`, `src/bombadil/connect/store.py:243-281`), where no op, tool, card or log line returns it, and have the browser service's `take` or the person put it there, never a tool the agent calls. Keep the unit's hardening and the 0700 directory, keep the refusal of a peer in an agent's scope for the ops that connect, store or perform, and say in the page that `sudo` reads the store until the agent loses it ([The connection service](#the-connection-service)).
- **A value that reaches the system prompt.** `persona.clean_name` accepts one to three words of letters, marks, hyphens, apostrophes and dots, at most 24 characters, and `persona.load` takes a default for any field that fails, because the file is written by the card, by the agent and by hand and the prompt does not escape what it holds (`src/bombadil/persona.py:48`, `src/bombadil/persona.py:80-89`).
- **A binding in the app kit.** Assume the app is the agent: whatever it exposes runs with the user's rights. Make writes a no-op under `ctx.check`, as `Vault`, `TextFile` and `Clipboard` do.
- **A secret.** Write it with `atomic_write(..., mode=0o600)` (`src/bombadil/appkit/native/files.py:95-112`), keep it out of what a turn logs, and add its name to the private lists so the brain never reads it (`src/bombadil/brain/rules.py:39-46`).
- **Anything that puts outside text in front of a model.** Fence it with a random marker, as `describe` does, and run that model with no tools (`src/bombadil/brain/describe.py:256-262`). Where the model has to have tools, mark the text as `mail_read` does and say that the marks are a convention (`src/bombadil/mail/tools.py:383-415`).
