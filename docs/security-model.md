Bombadil is built to protect one thing: the person's ability to see what the agent did and to take it back. It is not a sandbox. The agent runs as the account `user` with passwordless `sudo`, and each provider CLI starts in its no-prompt mode, so whatever that account or root can do, the agent can do. Nothing confines it. Several checks in the code (the desk gate, the job gate, the risk marks, the app check, the mail marks, the press check and the connection tools' marks) keep a well-behaved agent tidy and do not stop a hijacked one. What stands in for guard rails is a restore point of the root filesystem before each turn, plain-words narration of each step, and a Stop that needs no model. The agent has no tool that sends mail, posts a Slack reply, creates a task or writes a comment, and each of those leaves only on the person's own press, which the code checks and cannot enforce against a process that runs as the person. The keys to Slack and the work tools are kept by a service with a system user of its own, in a directory the person's own programs cannot open; the image still gives the agent passwordless `sudo`, so that protection is a rule with a check and not a wall ([The connection service](#the-connection-service)). A coding session, the vendor's own tool started by a word in the pill, is not a turn: no restore point, narration or Stop stands behind it, it keeps the account's passwordless `sudo`, and the code takes its processes for the agent's where it asks who pressed or typed ([Coding sessions](#coding-sessions) below; how they work is in [coding sessions](architecture/coding-sessions.md)). Remote control, a Claude Code session on this computer that a person steers from another device, is a third kind of process: the code does not take it for the agent's, so every check that refuses the agent's scope lets it through, and it has the account's passwordless `sudo` and, in the folder Bombadil makes for it, no permission questions ([Remote control](#remote-control)). The installer can lock the disk with a password (LUKS2); that protects a computer that is switched off and nothing that runs as `user` ([The installer and the disk](#the-installer-and-the-disk)). This page lists where the code grants power, which doors are open, where secrets sit, what undo does not reach and what is intended but not enforced. The reasoning for the choice is in [the principle](principles.md#full-access-with-undo) and [foundation choices](design/foundation-choices.md); this page does not repeat it.

Where this page says "designed", a brief decides it and no code exists. Where it says "convention", the code says so itself or a reader can walk around it.

The kernel enforces one boundary here, between accounts, and the agent holds root through `sudo`. The connection service is the one piece of Bombadil that runs as an account of its own, so its keys sit behind that boundary, and `sudo` is the way across it ([The connection service](#the-connection-service)). Inside the account every box runs as the same user, so the boxes are separated by convention, not by permission. The one line the code draws inside the account is the systemd scope: each turn's CLI and everything it starts run in a `bombadil-turn-` scope (`agentd` falls back to the CLI's process tree where the machine cannot make one), a coding session's tool runs in a `bombadil-dev-<project>-<role>-<run>` scope, `procs.cgroup_of` recognises both (`procs.AGENT_SCOPES`), and `agentd`, the mail service, the connection service and the browser service read the scope of the process on the other end of a socket to decide whether it is the agent's. A process the agent starts outside both is not marked: a `job` unit, or anything started with `systemd-run --user`, passes ([Coding sessions](#coding-sessions)). A remote-control session is one of them: `bombadil remote` starts it with `systemd-run --user --scope` and no `bombadil-` name ([Remote control](#remote-control)). Between the person and the account there is nothing once the disk is open: `greetd` logs `user` in on tty1 without a prompt, the account has an empty password unless the installer was given one, and no lock screen is installed. An install given a password encrypts the disk, and GRUB asks for the password at power-on ([The installer and the disk](#the-installer-and-the-disk)). Bombadil's own code listens only on Unix sockets (`agentd.sock`, `brain.sock`, `mail.sock`, `browserd.sock`, `connect.sock` as its own user and, as root, `watch.sock`), and the bar owns a name on the session bus for notifications. The connection service connects out to Slack and to the work tools' servers. Bombadil connects to Chromium's debugging port on loopback, checks that the provider's host answers on port 443, and asks the nameserver for the MX record of a mail domain the person types (`src/bombadil/signin.py:91-97`, `src/bombadil/sysmap.py:240-256`, `src/bombadil/mail/accounts.py:127-183`). Network traffic otherwise comes from the provider CLIs, Chromium, Thunderbird, `pacman`, `npm` or a command the agent runs.

## Coding sessions

A coding session is the vendor's own tool (`claude` or `codex`), or the person's shell, kept alive in an invisible zellij session and brought back by name ([coding sessions](architecture/coding-sessions.md) says how it works). It is not a turn, and it has the account's passwordless `sudo`. This section says what a session can do, what stands around it, who may tell `agentd` about one, and what the managed tool files add.

This section says who can reach them and what stops what, from the code at `24c836c`. It does not repeat the protocol.

**The token store is a rule with a check, not a wall.**

- The keys are closed to the person's own programs and not to `sudo`. `user ALL=(ALL) NOPASSWD: ALL` is in `packaging/bombadil/root/etc/sudoers.d/bombadil` and the agent runs as `user`, so its shell can read `connect.db`, where every key is in the clear, and a process that holds a key can call Slack or a work tool directly, with no card, no fingerprint and no press. The unit file says so in a comment. The store becomes a wall only if the agent loses `sudo`, which nothing in the code does.
- A press on `connect.sock` is checked for who sent it and for which words, not against a secret. The fingerprint is a SHA-256 of the kind, the target and the content, which any caller can work out, so a process of the person's outside both scopes (one started with `systemd-run --user`, say) can connect to the 0666 socket and ask for a post, and the service does it when a connection owns the target and can post. The fingerprint guards a card that changed under the person's press.
- Reading straight on the socket is open to the agent. The marks, the quoting and the ledger that flags a later draft belong to the tools in `agentd`; a process in a scope that asks the socket directly for `messages` gets the words unmarked, and no turn is remembered as having read them.
- Disconnecting deletes the keys from `connect.db` and stops the driver. Nothing tells Slack or the tool's server that the grant is over.
- What stands against all of it is the connection skill and the tools' descriptions, which tell the agent not to, the fingerprints, the warnings on a card, the press log and the refusals above, none of which is a boundary against `sudo`.

Putting a failed start back by itself is designed in the [installed OS brief](design/installed-os-brief.md) and not built.

## Things that cross to other people

The rule is [only the person's press reaches people](principles.md#the-persons-press-reaches-people): the agent reads, drafts and points, and the person's own press releases. For mail, for a Slack reply and for a new task or a comment in a work tool the press is built as a check that refuses a press from inside an agent's turn. For everything else it is a rule, not a wall.

```mermaid
flowchart LR
    AG["Agent: mail_draft"]
    P["The person"]
    W["Mail window"]
    A["agentd: Outbox.press"]
    S["bombadil-mail: send"]
    T["Thunderbird"]
    AG -->|"draft, not sent"| S
    P -->|"presses Send"| W
    W -->|"press, fingerprint"| A
    A -->|"send, unless it came from a turn's scope"| S
    S -->|"checks what was shown"| T
    AG -.->|"a press from its own scope: refused"| A
    AG -.->|"a process it started outside the scope: passes"| A
```

- **What the code does.** `os-mcp` registers no tool whose purpose is to send, post, share, pay or push (`src/bombadil/mcp_server.py:60-188`, `src/bombadil/appkit/tools.py:159-246`, `src/bombadil/cardtools.py:118-152`, `src/bombadil/mail/tools.py:67-127`). `show_card` and `system_map` only draw. The `job` tool runs any shell command, which is the same power as the shell. A mail draft leaves only on the person's press on the Send that the Mail window drew: the window sends a `press` to `agentd`, `Outbox.press` refuses it from a process inside an agent's turn, from one whose sender it cannot name and from one that has gone, and then calls the mail service's `send` once, which also refuses a process in a turn's scope and checks that the draft is what was shown. Each press leaves a row in `presses.jsonl`, mode 0600. `agentd` writes a repeated refusal from the same process, one of those that say something about who pressed, at most once in 5 seconds; the mail service writes its refusal for a press from a turn's scope at most once in 10 seconds, with a count of the ones it skipped. A typed "send it" opens the draft in the Mail window and says that sending is the person's; it sends nothing. A reply, a new task or a comment is a proposal in `proposals.json`, drawn on a card in the bar: the agent's `propose` makes one, and `Outbox.press` takes a press on the card's Send, Create or Comment button the same way, after the three fingerprints (the proposal's own, the pressed one and the one the card said it drew) agree, and asks the connection service to do it once ([The connection service](#the-connection-service); `src/bombadil/outbox.py:61`, `src/bombadil/outbox.py:194-201`, `src/bombadil/outbox.py:274-284`, `src/bombadil/outbox.py:290-303`, `src/bombadil/mail/service.py:114`, `src/bombadil/mail/service.py:1686-1700`, `src/bombadil/agentd.py:681-684`, `src/bombadil/agentd.py:1562-1589`, `src/bombadil/mail/service.py:1659-1700`, `src/bombadil/launcher.py:691-701`).
- **What the code does not do.** The agent has a shell, the network and `sudo`, so `curl`, `git push` or a chat client works. Nothing blocks them. The system prompt tells the agent to "act, don't ask for permission" (`src/bombadil/providers.py:44-45`) and has a line about sending only for mail: the agent cannot send mail, and the person's press does. It has no line about other ways out (`src/bombadil/providers.py:54-60`). Narration marks risky commands and does not pause (`src/bombadil/narrate.py:8`).
- **The press is a check, not a wall.** The check reads the systemd scope of the process on the other end of the socket, which `procs.cgroup_of` recognises when it is a `bombadil-turn-` or a `bombadil-dev-` scope, and whether the process is in the running turn's process tree, which is what marks a turn that has no scope (`src/bombadil/procs.py:92-101`, `src/bombadil/agentd.py:1591-1597`, `src/bombadil/outbox.py:274-284`). A process the agent starts outside its scope passes it: a command started with the `job` tool runs in its own `systemd-run --user` unit (`src/bombadil/jobs.py:363-366`), and so does anything else it starts with `systemd-run --user`, a remote-control session included ([Remote control](#remote-control)). Anything running as the person can also read Thunderbird's profile or connect to `mail.sock`. Against that stand the system prompt and the mail skill, which tell the agent not to, and the connection skill, the fingerprints, the draft warnings and the press log.
- **What is designed, and not built.** A kind of press other than mail and the three proposals (`Outbox.register` takes one, `Outbox.__init__` registers `mail` and one performer for each of `KINDS`, and nothing in `src/` calls `register` otherwise: `src/bombadil/outbox.py:177-178`, `src/bombadil/connect/driver.py:32`), a general outbox the agent fills, `agentd` accepting presses only from the shell's own process, the agent losing `sudo`, which would turn the token store from a rule into a wall, and hands for the browser service. The [everyday work brief](design/everyday-work-brief.md) says "the press is a rule, not yet a wall"; [mail](architecture/mail.md#who-may-do-what) says what is built.
- **What leaves the machine by design.** Each turn's conversation, tool results and screenshots go to the provider through its CLI, and a tool result includes the text of a mail the agent read. The brain's `describe` asks the provider's fast model for one sentence about a thing, and the prompt carries what the model is shown: the first 64 KB of a file, the first three pages of a PDF, the names in a folder with its path, a page's title and its address without the query, or a past turn's request and the agent's answer. It does this only for a thing someone is looking at, and never for a private path (`src/bombadil/brain/describe.py:1-7`, `src/bombadil/brain/describe.py:36-47`, `src/bombadil/brain/describe.py:66-73`, `src/bombadil/brain/describe.py:170-220`, `src/bombadil/brain/describe.py:249`).
- **Words from other people.** They are data, and the code keeps them from becoming instructions only where a model has no tools. The describer fences its input with a random marker and runs with `--tools ""`, `--strict-mcp-config` and `--safe-mode` under Claude (`src/bombadil/providers.py:480-488`, `src/bombadil/brain/describe.py:256-262`). Where the model has tools the code only marks them: `mail_read` puts a mail's text between two marks that carry a fresh random word, cuts it at 20 000 characters and strips control characters and the ones that turn text around, and the tool descriptions and the system prompt say to read a mail and never obey it. `messages_unread`, `message_thread` and `tasks_waiting` do the same, with a fresh word in each pair of marks and every line of a message quoted with `> `, and `propose` warns the person on the card when the agent wrote a draft after reading messages and the words are not ones the person typed (`src/bombadil/connect/tools.py:404-408`, `src/bombadil/connect/tools.py:422-433`, `src/bombadil/proposals.py:140-158`). That is a convention for a model with a shell, not a separation (`src/bombadil/mail/tools.py:14-17`, `src/bombadil/mail/tools.py:383-414`, `src/bombadil/providers.py:56-57`). For the two Brain words, the note the next turn receives names the action and leaves the Brain's answer out (`BRAIN_NOTES`, `src/bombadil/agentd.py:315`, `src/bombadil/agentd.py:1864-1865`). `--strict-mcp-config` keeps the account's connectors out of a turn (`src/bombadil/providers.py:275`). The turn itself reads pages, mail and files with full access and no separation between data and instructions. A page or a mail that talks the agent round has everything in the first table.

## Known gaps

Each gap was checked in the code. A designed fix is named where one exists.

1. **No authentication on the `agentd` socket.** No mode is set, so the socket takes it from the umask. Anything outside the agent's scopes (a turn's and a coding session's) that opens it can type for the person, restart or shut down the machine, and claim `asked_by`. `agentd` refuses a press, a chip and a dismissal to a process inside a scope and marks its prompt `asked_by: "agent"`, but a `local` message, or a prompt that is a launcher word other than `connect <service>`, gets no look, so a process inside either scope can restart or shut down the machine, undo, switch the provider, start and end coding sessions, start remote control or, on the USB stick, open the installer (`src/bombadil/agentd.py:579-591`, `src/bombadil/agentd.py:680-709`, `src/bombadil/agentd.py:734-737`). No test asserts the mode of this socket, of `brain.sock`, of `watch.sock` or of the sudoers file.
2. **Passwordless `sudo`, autologin and no lock screen, and an empty account password unless one was given at install.** The installer can set one password for the disk (GRUB asks for it at power-on) and the account, but `greetd` still logs `user` in on tty1 unasked, `sudo` asks for no password and no lock screen is installed, so the password guards a switched-off computer and nothing else; the installer's own line says it "unlocks the screen", which nothing does. The [installed OS brief](design/installed-os-brief.md) names the lock screen and the consoles; they are designed, with no code (`packaging/bombadil/root/usr/bin/bombadil-install:597-603`, `packaging/bombadil/root/usr/bin/bombadil-install:932-950`, `packaging/bombadil/root/usr/share/bombadil/greetd/config.toml:8-13`).
3. **Undo can be switched off from inside.** Deleting restore points, editing the sudoers file, `bombadil-rollback` or snapper's configuration, or writing `snapshots = false` removes it (see the undo table). A coding session and a remote-control session have the same `sudo` as the agent and can do each of these.
4. **Home and the EFI partition are outside undo.** The sign-ins, the vault files, `~/Apps`, the mail copy, the turn logs, `persona.toml` and the Tips file are in `@home`. The kernel and initramfs are in `@/boot` and go back with a restore point; GRUB on the EFI partition does not.
5. **The debugging port is open to every local process.** The profile it controls is the person's.
6. **Generated apps are unconfined.** `Command` runs `/bin/sh -c`, `TextFile` and `KitFiles` write any path the user can, and `Processes.kill` signals any process of the user (`src/bombadil/appkit/native/command.py:172-176`, `src/bombadil/appkit/native/files.py:136-144`, `src/bombadil/appkit/context.py:36-39`, `src/bombadil/appkit/native/processes.py:243-253`). `Agent.ask` types as the person, except from an app that runs inside a turn's or a coding session's scope, as an app the agent opened does; an app the person opened from the pill does not (`src/bombadil/appkit/native/agent.py:234-244`, `src/bombadil/outbox.py:199-200`). `Clipboard` clears a copied secret after a delay the app chooses, only if the app asks (`src/bombadil/appkit/native/clipboard.py:37-48`). The kit has no network component, and nothing stops an app's Python or a `Command` from using the network.
7. **The Vault protects a file, not a secret from the agent.** The agent writes the app that shows the unlock screen and holds root.
8. **The press rule is enforced by a scope check, and a process outside both scopes passes it.** The check covers mail, a Slack reply and a new task or a comment, and refuses a process in a turn's or a coding session's scope; one the agent starts in a `job` unit or with `systemd-run --user` is in neither. For everything else the press is a rule. The system prompt has a line about sending only for mail, and the connection skill says the same for the rest.
9. **The provider login and the apps travel with the install.** `bombadil-install` copies what `install/carry.list` names from the stick's home folder: `.claude`, `.claude.json`, `.codex`, `.config/bombadil` (which holds `persona.toml`), `desk.toml` and `tips.json` from the state folder, `Apps` with their data, and `.config/chromium`. It also copies the Wi-Fi connections joined on the stick (`install/carry.list`, `packaging/bombadil/root/usr/bin/bombadil-install:656-679`).
10. **Live-only exposures.** The root serial shell exists in every live image, and the boot entries that erase or refresh `/dev/vda` (03, 04, 05 and 06) and the serial smoke entry (02) exist in an image built with `BOMBADIL_TEST_ENTRIES`; entry 04 installs with a password that is in the repository, and 06 erases the disk and then updates from the host of a test VM. The installer removes the serial shell from the installed system (`packaging/bombadil/root/usr/bin/bombadil-install:435`). A normal build deletes entries 02 to 09 (`scripts/build-iso.sh:15-27`), and `scripts/run-vm.sh` refuses to attach a disk that already holds a system because of the entries that erase (`scripts/run-vm.sh:30-37`).
11. **The CLIs are not pinned.** `npm install -g` fetches the provider CLIs at image build time, with no version or hash, and `bombadil-setup` runs `sudo npm install -g` the same way when one is missing. Packages from pacman are signature-checked (`iso/pacman.conf:7`, `scripts/build-iso.sh:38-42`, `packaging/bombadil/root/usr/bin/bombadil-setup:12-13`).
12. **The Codex describer has less than the Claude one.** Claude gets `--tools ""` and no connectors. Codex gets a read-only sandbox only (`src/bombadil/providers.py:678-683`), though the describer's docstring says "no tools and no MCP servers" (`src/bombadil/brain/describe.py:10-12`).
13. **The whole screen goes to the vendor.** `screenshot` captures every window, including a password the person has on screen. It leaves `screen.png` in a temporary folder that nothing in the code removes (`src/bombadil/mcp_server.py:105-109`).
14. **No firewall.** The repository sets none.
15. **The mail copy and its tokens are not encrypted by Bombadil.** Thunderbird's profile holds the person's mail and its login store, readable by anything that runs as the person. The disk is encrypted only when the installer was given a password, and then only while the computer is off (`src/bombadil/mail/engine.py:1001-1004`, `packaging/bombadil/root/usr/bin/bombadil-install:217-238`).
16. **A coding session is on the agent's side of the scope check, and keeps `sudo`.** `procs.cgroup_of` returns a scope when its name starts with `bombadil-turn-` or `bombadil-dev-` (`procs.AGENT_SCOPES`), so `agentd`, the mail service, the connection service and the browser service refuse a press, a notice chip, a dismissal and a proposal's edit from a session's tool, and mark its typed words as the agent's. Where the machine makes no scope a session has none, and nothing can tell its processes from the person's. A process it starts outside the scope passes, as one the agent starts does. Stop does not reach a session, no restore point is taken for its work, `narrate` marks none of its steps, the agent can start one with a launcher word, and it has the account's passwordless `sudo` with nothing in the code to remove it, so it can write `@`, turn undo off like the agent (gap 3) and read the connection service's keys (gap 20; `packaging/bombadil/root/etc/sudoers.d/bombadil:2`, `src/bombadil/procs.py:89-100`, `src/bombadil/outbox.py:274-284`, `src/bombadil/dev.py:413`, `src/bombadil/dev.py:428-436`, `src/bombadil/agentd.py:2020-2060`). Not checked: the tools' own permission prompts (no session was run), and whether another process can type into a session through zellij's own socket.
17. **The `dev`, `dev-signal` and `away` messages are neither authenticated nor looked at.** Any client can bring back, restart or end a session that is in the registry, report a state for it with up to 140 characters of the sender's own words that the pill and the cards then show, make a "yours" entry, and clear the Away card. A forged `SessionStart` sets the session's conversation id, which `command_for` puts in the command that resumes it, and a forged `exit` with a non-zero code sets the path of the session's last screen, which `bombadil dev why` prints in the details drawer, so any file the user can read can be put on the screen (`src/bombadil/agentd.py:753-772`, `src/bombadil/dev.py:581-584`, `src/bombadil/dev.py:630-637`, `src/bombadil/dev.py:827-839`, `bin/bombadil:170-181`).
18. **`BOMBADIL_OS` and `BOMBADIL_SESSION` are plain environment variables.** `bombadil-signal` skips a run when `BOMBADIL_OS=1`, and `session_env` removes the mark from a session. Whoever starts a process can set or clear it, so it only keeps the agent's own turns out of the dots, and it stops no message from reaching `agentd` (`bin/bombadil-signal:130-131`, `src/bombadil/dev.py:808-824`).
19. **A session's last screen and the hook spool are kept without a mode.** `dev/<project>-<role>.last` holds what was on the screen when a tool stopped, `dev/signals.jsonl` holds hook events until `agentd` reads it, and the registry holds the first line of each prompt typed to a tool. No code sets a mode on them, and nothing deletes a `.last` file (`src/bombadil/dev.py:864-871`, `src/bombadil/dev.py:885-931`).
20. **The keys to Slack and the work tools are readable with `sudo`.** `connect.db` is 0600 in a 0700 directory of a system user, and the agent's `sudo` opens both. A key read that way works with no card, no fingerprint and no press, and nothing in the code removes `sudo`. The store is in `@`, so an undo can bring back a key that was replaced or revoked. Disconnecting deletes the copy and does not tell Slack or the tool that the grant is over (`packaging/bombadil/root/etc/sudoers.d/bombadil:2`, `src/bombadil/connect/store.py:67-74`, `src/bombadil/connect/store.py:243-281`, `packaging/bombadil/root/usr/lib/systemd/system/bombadil-connect.service:14-23`; [The connection service](#the-connection-service)).
21. **The connection socket has no secret, and a peer in an agent's scope can read from it unmarked.** `connect.sock` is mode 0666 and takes any user whose uid is in the range, so a process of the person outside both scopes can ask it to post, and it does when a connection owns the target and can post; the fingerprint is public and says what was pressed, not who pressed. A process in a scope that asks for `messages`, `thread` or `tasks` on the socket directly gets the words with none of the marks the tools add, and no turn is remembered as having read them, so the card's warning about a draft written after reading does not follow (`src/bombadil/connect/service.py:81-90`, `src/bombadil/connect/service.py:751-767`, `src/bombadil/connect/service.py:992-1027`, `src/bombadil/connect/driver.py:70-75`).
22. **Any program on the session bus can put a line above the pill.** The bar owns `org.freedesktop.Notifications`, and a notification from the agent's `notify` tool (which runs `notify-send`) or from any other program (the start hook's comment names a web page's) is shown the same way, made plain and cut to 60 characters of summary and 100 of body, at most one line for each app in 2 seconds. Nothing marks the line as another program's: it reads as the summary and the body, and the app's name is on it only when there is one of the two, and on the card that Reply draws. Reply's card copies the person's words and cannot send, and Open invokes the notification's own action, which is the sender's (`src/bombadil/notifications.py:60-67`, `src/bombadil/notifications.py:108-112`, `src/bombadil/notifications.py:133-178`).
23. **Remote control is outside the scope check, takes no permission questions and is steered from another device.** The tmux session `bombadil-remote` is in none of the agent's scopes, so `agentd`, the mail service, the connection service and the browser service take its processes for the person, and a press, a chip, a connection or a key from it is accepted. In the folder Bombadil makes for it, it runs with `bypassPermissions`. The word `remote` starts it for any sender, the agent's included, and the agent can type into the session with `tmux send-keys`. A restore point is taken before each prompt in that folder only, and the protection from outside is the vendor's claude.ai sign-in, which this page did not check (`src/bombadil/remote.py:64-69`, `src/bombadil/remote.py:78-93`, `src/bombadil/launcher.py:106`, `src/bombadil/launcher.py:1071-1073`, `src/bombadil/procs.py:92-101`; [Remote control](#remote-control)).
24. **The recovery key stays on the disk, and a plan install never shows it.** `/var/lib/bombadil/recovery-key` (mode 0600) is written at install, the script's comment says it stays only until the first start shows it, and nothing in the product shows it or removes it (only the smoke checks that it exists, `packaging/bombadil/root/usr/bin/bombadil-smoke:903-904`). Only a guided run shows the key, on its terminal; an install from a plan (the way the smoke does it, and the way a designed install card would) leaves a key nobody has seen. It is inside the encrypted volume, in `@`, so every restore point holds it and a refresh keeps it (`packaging/bombadil/root/usr/bin/bombadil-install:817-867`, `packaging/bombadil/root/usr/bin/bombadil-install:384-386`, `packaging/bombadil/root/usr/bin/bombadil-install:1040-1049`, `packaging/bombadil/root/usr/bin/bombadil-install:1083-1085`).
25. **The disk's encryption ends at the EFI partition.** GRUB's core and modules, `grub.cfg`, `grubenv`, the picture and the font are in the clear, and the repository has no Secure Boot, signing or TPM measurement, so whoever can write to that partition can replace GRUB and read the password as it is typed. Encryption protects a computer that is switched off, not one that is altered and handed back (`packaging/bombadil/root/usr/bin/bombadil-install:520-563`, `packaging/bombadil/root/usr/bin/bombadil-install:747-768`).
26. **Systems kept aside stay for good.** `@.undone-<time>`, `@.before-refresh-<time>` and `@.after-refresh-<time>`, with their restore points, are not snapper's and nothing removes them, though the guided run says the old system "is kept for 14 days". Each holds the keys and files of its time, the connection service's included, and a disk that fills up is the only thing that makes anyone look (`packaging/bombadil/root/usr/bin/bombadil-rollback:39-54`, `packaging/bombadil/root/usr/bin/bombadil-rollback:56-67`, `packaging/bombadil/root/usr/bin/bombadil-install:320-367`, `packaging/bombadil/root/usr/bin/bombadil-install:1009`).

## If you fork it

Decide first whether you keep full access. If you do, add no confirm dialog for something undo can reverse; make it visible and undoable, as [the principle](principles.md#full-access-with-undo) says. If you narrow it, the places are the two flag sets in `src/bombadil/providers.py:271` and `src/bombadil/providers.py:594-596`, `packaging/bombadil/root/etc/sudoers.d/bombadil`, the system prompt in `src/bombadil/providers.py:33-74`, and `tests/test_providers.py`. Nothing in Bombadil is built to ask, so narrowing means building that.

Before you hand an image to anyone else:

The live image's `passwd -d user` leaves the stick's account empty. | `packaging/bombadil/root/usr/bin/bombadil-install:597-603`, `packaging/bombadil/root/usr/bin/bombadil-install:932-950`, `iso/airootfs/etc/systemd/system/bombadil-live.service:8`, `packaging/bombadil/root/usr/share/bombadil/greetd/config.toml` |

When you add something:

- **A socket or a port.** Put it under `paths.runtime_dir()`, set its mode in the code, check `SO_PEERCRED` when others can open it, and add a test for the mode. The mail socket has a test of its mode (`tests/test_mail_service.py:303`), the connection socket, its directory and its database have one (`tests/test_connect_service.py:388-394`) and so does the browser socket (`tests/test_browserd.py:329`); `agentd.sock`, `brain.sock` and `watch.sock` have none.
- **A tool in `os-mcp`.** It is power handed to a model that reads other people's words. Register it with `OsTools._tool` (`src/bombadil/mcp_server.py:46-54`). Give the agent a way to prepare, never a tool that releases, and put the press where only the person's own press reaches it.
- **Something that reaches people.** Register a performer with `Outbox.register(kind, performer)` (`src/bombadil/outbox.py:177-178`) where `agentd` builds its outbox (`src/bombadil/agentd.py:477`; the three proposal kinds are registered in `Outbox.__init__`), and let only the person's press on a view the person controls call it. Have the service that does the act check what was shown, as the mail service's `send` and the connection service's `perform` do (each works the fingerprint out again, refuses a peer in an agent's scope, and writes the press down as `unknown` before the act), and add no second way from a press to an act. Never add a tool that releases, such as a `mail_send`, and keep the scope check and the press log. Tests: `tests/test_outbox.py`, `tests/test_mcp_server.py:437`; [extending mail](architecture/mail.md#extending-it).
- **A process the person starts through the agent, as a coding session is.** Decide which side of the scope check it is on (`procs.cgroup_of` recognises the names in `procs.AGENT_SCOPES`, a turn's and a coding session's), what its hooks may send and who else may send the same message, and whether its work needs a restore point. `bombadil-signal` trims what it sends and `agentd` believes it ([Coding sessions](#coding-sessions)).
- **A key to another service.** Keep it in the connection service's store (`ConnectionSecrets`, `src/bombadil/connect/store.py:243-281`), where no op, tool, card or log line returns it, and have the browser service's `take` or the person put it there, never a tool the agent calls. Keep the unit's hardening and the 0700 directory, keep the refusal of a peer in an agent's scope for the ops that connect, store or perform, and say in the page that `sudo` reads the store until the agent loses it ([The connection service](#the-connection-service)).
- **A value that reaches the system prompt.** `persona.clean_name` accepts one to three words of letters, marks, hyphens, apostrophes and dots, at most 24 characters, and `persona.load` takes a default for any field that fails, because the file is written by the card, by the agent and by hand and the prompt does not escape what it holds (`src/bombadil/persona.py:48`, `src/bombadil/persona.py:80-89`).
- **A binding in the app kit.** Assume the app is the agent: whatever it exposes runs with the user's rights. Make writes a no-op under `ctx.check`, as `Vault`, `TextFile` and `Clipboard` do.
- **A secret.** Write it with `atomic_write(..., mode=0o600)` (`src/bombadil/appkit/native/files.py:95-112`), keep it out of what a turn logs, and add its name to the private lists so the brain never reads it (`src/bombadil/brain/rules.py:39-46`).
- **Anything that puts outside text in front of a model.** Fence it with a random marker, as `describe` does, and run that model with no tools (`src/bombadil/brain/describe.py:256-262`). Where the model has to have tools, mark the text as `mail_read` does and say that the marks are a convention (`src/bombadil/mail/tools.py:383-414`).
