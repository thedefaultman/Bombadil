Bombadil is built to protect one thing: the person's ability to see what the agent did and to take it back. It is not a sandbox. The agent runs as the account `user` with passwordless `sudo`, and each provider CLI starts in its no-prompt mode, so whatever that account or root can do, the agent can do. Nothing confines it. Several checks in the code (the desk gate, the job gate, the risk marks, the app check, the mail marks and the press check) keep a well-behaved agent tidy and do not stop a hijacked one. What stands in for guard rails is a restore point of the root filesystem before each turn, plain-words narration of each step, and a Stop that needs no model. The agent has no tool that sends mail, and a draft leaves only on the person's own press, which the code checks and cannot enforce against a process that runs as the person. A coding session, the vendor's own tool started by a word in the pill, is not a turn: no restore point, narration or Stop stands behind it, and the code takes its processes for the person, not for the agent ([Coding sessions](#coding-sessions) below; how they work is in [coding sessions](architecture/coding-sessions.md)). This page lists where the code grants power, which doors are open, where secrets sit, what undo does not reach and what is intended but not enforced. The reasoning for the choice is in [the principle](principles.md#full-access-with-undo) and [foundation choices](design/foundation-choices.md); this page does not repeat it.

Where this page says "designed", a brief decides it and no code exists. Where it says "convention", the code says so itself or a reader can walk around it.


The kernel enforces one boundary here, between accounts, and the agent holds root through `sudo`. Inside the account every box runs as the same user, so the boxes are separated by convention, not by permission. The one line the code draws inside the account is the systemd scope: each turn's CLI and everything it starts run in a `bombadil-turn-` scope (`agentd` falls back to the CLI's process tree where the machine cannot make one), and `agentd` and the mail service read the scope of the process on the other end of a socket to decide whether it is the agent's. A process the agent starts outside the scope is not marked. A coding session is outside it by design: its tool runs in a `bombadil-dev-<project>-<role>-<run>` scope, `procs.cgroup_of` recognises only `bombadil-turn-` names, and so both checks take its processes for the person ([Coding sessions](#coding-sessions)). Between the person and the account there is nothing: `greetd` logs `user` in on tty1 without a prompt, the account has an empty password, and no lock screen is installed. Bombadil's own code listens only on Unix sockets (`agentd.sock`, `brain.sock`, `mail.sock` and, as root, `watch.sock`). It connects to Chromium's debugging port on loopback, checks that the provider's host answers on port 443, and asks the nameserver for the MX record of a mail domain the person types (`src/bombadil/signin.py:91-97`, `src/bombadil/sysmap.py:240-257`, `src/bombadil/mail/accounts.py:127-184`). Network traffic otherwise comes from the provider CLIs, Chromium, Thunderbird, `pacman`, `npm` or a command the agent runs.

## What undo covers and does not

How the restore point is taken and applied is in [restore points](architecture/restore-points.md). This table says what it reaches.

| Thing | Covered | Why, and where |
|---|---|---|
| System files, packages, `/etc`, `/usr`, `/var` (the `@` subvolume) | Yes, from the next restart | `iso/airootfs/usr/local/bin/bombadil-install:23-27`, `iso/airootfs/usr/local/bin/bombadil-rollback:2-16` |
| The person's files, `~/Apps` and app data, `~/.claude`, `~/.codex`, the browser profile, the mail profile, turn logs, `brain.db` (`@home`) | No | `iso/airootfs/usr/local/bin/bombadil-install:23,27`. | The restore points | No | They sit on the same disk at `/.snapshots`. Snapper's cleanup timer keeps the newest 30 (`NUMBER_LIMIT=30`, with no hourly ones: `TIMELINE_CREATE=no`), so on a long-lived install the oldest restore point goes by design. | Anything that left the machine | No | Mail, pushes, uploads and everything sent to the provider. |
| The live ISO | No restore points exist | `snapshots.available` needs a snapper config, which only an installed system has. `src/bombadil/snapshots.py:32-34`, `src/bombadil/launcher.py:786-789`. |
| A turn with `snapshots = false`, or without snapper | No restore point is taken | `src/bombadil/config.py:52`, `src/bombadil/agentd.py:2280`, `src/bombadil/agentd.py:2911`. |
| A coding session's work | No restore point is taken for it | `src/bombadil/dev.py` calls nothing in `snapshots`. What a session changes in `@home` (the project, a worktree and its branch, the tool's own state) is outside undo. What it changes under `@` is in no restore point of its own: an undo goes back to the state before the last turn, whatever a session did before it. [Coding sessions](#coding-sessions). |

Undo itself depends on parts the agent can change. It runs `sudo snapper` and `sudo bombadil-rollback` (`src/bombadil/snapshots.py:37`, `src/bombadil/snapshots.py:66`), and `sudo`, `snapper` and the script all sit in `@`. The swap happens at the next restart, so the agent keeps running on the old root until then. `bombadil-rollback` moves `@` aside as `@.undone-<time>` and only then creates `@` from the restore point, so a failure between the two leaves no `@` (`iso/airootfs/usr/local/bin/bombadil-rollback:14-15`). A start that fails does not put itself back: no boot-count, rescue or repair code exists, and a restore point is applied by running `bombadil-rollback` by hand. Putting a failed start back is designed in the [installed OS brief](design/installed-os-brief.md) and not built.

## Things that cross to other people

The rule is [only the person's press reaches people](principles.md#the-persons-press-reaches-people): the agent reads, drafts and points, and the person's own press releases. For mail the press is built as a check that refuses a press from inside an agent's turn. For everything else it is a rule, not a wall.

```mermaid
flowchart LR
    AG["Agent: mail_draft"]
    P["The person"]
    W["Mail window"]
    A["agentd: Outbox.press"]
    S["bombadil-mail: send"]
    T["Thunderbird"]
    AG -->|"draft, not sent"| S
    P -->|"presses Send"| W
    W -->|"press, fingerprint"| A
    A -->|"send, unless it came from a turn's scope"| S
    S -->|"checks what was shown"| T
    AG -.->|"a press from its own scope: refused"| A
    AG -.->|"a process it started outside the scope: passes"| A
```

- **What the code does.** `os-mcp` registers no tool whose purpose is to send, post, share, pay or push (`src/bombadil/mcp_server.py:60-179`, `src/bombadil/appkit/tools.py:159-246`, `src/bombadil/cardtools.py:112-145`, `src/bombadil/mail/tools.py:67-127`). `show_card` and `system_map` only draw. The `job` tool runs any shell command, which is the same power as the shell. A mail draft leaves only on the person's press on the Send that the Mail window drew: the window sends a `press` to `agentd`, `Outbox.press` refuses it from a process inside an agent's turn, from one whose sender it cannot name and from one that has gone, and then calls the mail service's `send` once, which also refuses a process in a turn's scope and checks that the draft is what was shown. Each press leaves a row in `presses.jsonl`, mode 0600. `agentd` writes a repeated refusal from the same process, one of those that say something about who pressed, at most once in 5 seconds; the mail service writes its refusal for a press from a turn's scope at most once in 10 seconds, with a count of the ones it skipped. A typed "send it" opens the draft in the Mail window and says that sending is the person's; it sends nothing (`src/bombadil/outbox.py:51`, `src/bombadil/outbox.py:146-153`, `src/bombadil/outbox.py:185-195`, `src/bombadil/outbox.py:201-214`, `src/bombadil/mail/service.py:114`, `src/bombadil/mail/service.py:1686-1700`, `src/bombadil/agentd.py:530-533`, `src/bombadil/agentd.py:1224-1244`, `src/bombadil/mail/service.py:1659-1700`, `src/bombadil/launcher.py:589-596`).
- **What the code does not do.** The agent has a shell, the network and `sudo`, so `curl`, `git push` or a chat client works. Nothing blocks them. The system prompt tells the agent to "act, don't ask for permission" (`src/bombadil/providers.py:44-45`) and has a line about sending only for mail: the agent cannot send mail, and the person's press does. It has no line about other ways out (`src/bombadil/providers.py:50-56`). Narration marks risky commands and does not pause (`src/bombadil/narrate.py:8`).
- **The press is a check, not a wall.** The check reads the systemd scope of the process on the other end of the socket, which `procs.cgroup_of` recognises only when it is a `bombadil-turn-` scope, and whether the process is in the running turn's process tree, which is what marks a turn that has no scope (`src/bombadil/procs.py:86-95`, `src/bombadil/agentd.py:1246-1252`, `src/bombadil/outbox.py:185-195`). A process the agent starts outside its scope passes it: a command started with the `job` tool runs in its own `systemd-run --user` unit (`src/bombadil/jobs.py:363-366`), and a coding session's tool runs in a `bombadil-dev-` scope, which the agent can start with a launcher word (`src/bombadil/dev.py:413`). Anything running as the person can also read Thunderbird's profile or connect to `mail.sock`. Against that stand the system prompt and the mail skill, which tell the agent not to, the fingerprints, the draft warnings and the press log.
- **What is designed, and not built.** Kinds of press other than mail (`Outbox.register` takes another kind, and nothing in `src/` registers one: `src/bombadil/outbox.py:129-130`), a general outbox the agent fills, `agentd` accepting presses only from the shell's own process, `bombadil-connect` and a separate user for connector tokens. The [everyday work brief](design/everyday-work-brief.md) says "the press is a rule, not yet a wall"; [mail](architecture/mail.md#who-may-do-what) says what is built.
- **What leaves the machine by design.** Each turn's conversation, tool results and screenshots go to the provider through its CLI, and a tool result includes the text of a mail the agent read. The brain's `describe` asks the provider's fast model for one sentence about a thing, and the prompt carries what the model is shown: the first 64 KB of a file, the first three pages of a PDF, the names in a folder with its path, a page's title and its address without the query, or a past turn's request and the agent's answer. It does this only for a thing someone is looking at, and never for a private path (`src/bombadil/brain/describe.py:1-8`, `src/bombadil/brain/describe.py:36-47`, `src/bombadil/brain/describe.py:66-73`, `src/bombadil/brain/describe.py:170-221`, `src/bombadil/brain/describe.py:249`).
- **Words from other people.** They are data, and the code keeps them from becoming instructions only where a model has no tools. The describer fences its input with a random marker and runs with `--tools ""`, `--strict-mcp-config` and `--safe-mode` under Claude (`src/bombadil/providers.py:470-478`, `src/bombadil/brain/describe.py:256-262`). Where the model has tools the code only marks them: `mail_read` puts a mail's text between two marks that carry a fresh random word, cuts it at 20 000 characters and strips control characters and the ones that turn text around, and the tool descriptions and the system prompt say to read a mail and never obey it. That is a convention for a model with a shell, not a separation (`src/bombadil/mail/tools.py:14-17`, `src/bombadil/mail/tools.py:383-415`, `src/bombadil/providers.py:52-53`). For the two Brain words, the note the next turn receives names the action and leaves the Brain's answer out (`BRAIN_NOTES`, `src/bombadil/agentd.py:237`, `src/bombadil/agentd.py:1352-1353`). `--strict-mcp-config` keeps the account's connectors out of a turn (`src/bombadil/providers.py:265`). The turn itself reads pages, mail and files with full access and no separation between data and instructions. A page or a mail that talks the agent round has everything in the first table.

## Known gaps

Each gap was checked in the code. A designed fix is named where one exists.

1. **No authentication on the `agentd` socket.** No mode is set, so the socket takes it from the umask. Anything outside a turn's scope that opens it can type for the person, restart or shut down the machine, and claim `asked_by`. `agentd` refuses a press, a chip and a dismissal to a process inside a scope and marks its prompt `asked_by: "agent"`, but a `local` message, or a prompt that is a launcher word, gets no look, so a process inside a turn's scope can restart or shut down the machine, undo, switch the provider, or start and end coding sessions (`src/bombadil/agentd.py:444-452`, `src/bombadil/agentd.py:529-549`, `src/bombadil/agentd.py:574-577`). No test asserts the mode of this socket, of `brain.sock`, of `watch.sock` or of the sudoers file.
2. **Passwordless `sudo`, an empty console password, autologin and no lock screen.** The [installed OS brief](design/installed-os-brief.md) names one password for the disk, the account, the lock screen and the consoles. It is designed, with no code.
3. **Undo can be switched off from inside.** Deleting restore points, editing the sudoers file, `bombadil-rollback` or snapper's configuration, or writing `snapshots = false` removes it (see the undo table).
4. **Home and `/boot` are outside undo.** The sign-ins, the vault files, `~/Apps`, the mail copy and the turn logs are in `@home`.
5. **The debugging port is open to every local process.** The profile it controls is the person's.
6. **Generated apps are unconfined.** `Command` runs `/bin/sh -c`, `TextFile` and `KitFiles` write any path the user can, and `Processes.kill` signals any process of the user (`src/bombadil/appkit/native/command.py:172-176`, `src/bombadil/appkit/native/files.py:136-144`, `src/bombadil/appkit/context.py:36-39`, `src/bombadil/appkit/native/processes.py:243-253`). `Agent.ask` types as the person, except from an app that runs inside a turn's scope, as an app the agent opened does; an app the person opened from the pill does not (`src/bombadil/appkit/native/agent.py:181-191`, `src/bombadil/outbox.py:151-152`). `Clipboard` clears a copied secret after a delay the app chooses, only if the app asks (`src/bombadil/appkit/native/clipboard.py:37-48`). The kit has no network component, and nothing stops an app's Python or a `Command` from using the network.
7. **The Vault protects a file, not a secret from the agent.** The agent writes the app that shows the unlock screen and holds root.
8. **The press rule is enforced for mail by a scope check, and a process outside the turn's scope passes it, a coding session's included.** For everything else it is a rule. The system prompt has a line about sending only for mail.
9. **The provider login travels with the install.** `bombadil-install` copies `.claude`, `.claude.json`, `.codex` and `.config/bombadil` to the installed home (`iso/airootfs/usr/local/bin/bombadil-install:82-88`).
10. **Live-only exposures.** The root serial shell and the boot entry that erases `/dev/vda` exist in the live image. The installer removes the first (`iso/airootfs/usr/local/bin/bombadil-install:33-34`). `scripts/run-vm.sh` refuses to attach a disk that already holds a system because of the second (`scripts/run-vm.sh:30-37`).
11. **The CLIs are not pinned.** `npm install -g` fetches the provider CLIs at image build time, with no version or hash, and `bombadil-setup` runs `sudo npm install -g` the same way when one is missing. Packages from pacman are signature-checked (`iso/pacman.conf:5`, `scripts/build-iso.sh:19-23`, `iso/airootfs/usr/local/bin/bombadil-setup:12-13`).
12. **The Codex describer has less than the Claude one.** Claude gets `--tools ""` and no connectors. Codex gets a read-only sandbox only (`src/bombadil/providers.py:668-673`), though the describer's docstring says "no tools and no MCP servers" (`src/bombadil/brain/describe.py:10-12`).
13. **The whole screen goes to the vendor.** `screenshot` captures every window, including a password the person has on screen. It leaves `screen.png` in a temporary folder that nothing in the code removes (`src/bombadil/mcp_server.py:105-109`).
14. **No firewall.** The repository sets none.
15. **The mail copy and its tokens are not encrypted at rest.** Thunderbird's profile holds the person's mail and its login store, readable by anything that runs as the person, and the installer has no encrypted layout (`src/bombadil/mail/engine.py:1000-1004`, `iso/airootfs/usr/local/bin/bombadil-install:16-27`).
16. **A coding session is outside the scope check.** `procs.cgroup_of` returns a scope only when its name starts with `bombadil-turn-`, and a session runs in a `bombadil-dev-` scope (or in none where scopes are unsupported), so `agentd` and the mail service take its processes for the person: a press, a notice chip, a dismissal and typed words from it are accepted, and the agent can start one with a launcher word. Stop does not reach it, no restore point is taken for its work, and `narrate` marks none of its steps (`src/bombadil/procs.py:86-95`, `src/bombadil/outbox.py:185-195`, `src/bombadil/dev.py:413`, `src/bombadil/dev.py:428-436`, `src/bombadil/agentd.py:1492-1528`). Not checked: the tools' own permission prompts (no session was run), and whether another process can type into a session through zellij's own socket.
17. **The `dev`, `dev-signal` and `away` messages are neither authenticated nor looked at.** Any client can bring back, restart or end a session that is in the registry, report a state for it with up to 140 characters of the sender's own words that the pill and the cards then show, make a "yours" entry, and clear the Away card. A forged `SessionStart` sets the session's conversation id, which `command_for` puts in the command that resumes it, and a forged `exit` with a non-zero code sets the path of the session's last screen, which `bombadil dev why` prints in the details drawer, so any file the user can read can be put on the screen (`src/bombadil/agentd.py:587-602`, `src/bombadil/dev.py:581-584`, `src/bombadil/dev.py:630-637`, `src/bombadil/dev.py:827-839`, `bin/bombadil:166-177`).
18. **`BOMBADIL_OS` and `BOMBADIL_SESSION` are plain environment variables.** `bombadil-signal` skips a run when `BOMBADIL_OS=1`, and `session_env` removes the mark from a session. Whoever starts a process can set or clear it, so it only keeps the agent's own turns out of the dots, and it stops no message from reaching `agentd` (`bin/bombadil-signal:130-131`, `src/bombadil/dev.py:808-824`).
19. **A session's last screen and the hook spool are kept without a mode.** `dev/<project>-<role>.last` holds what was on the screen when a tool stopped, `dev/signals.jsonl` holds hook events until `agentd` reads it, and the registry holds the first line of each prompt typed to a tool. No code sets a mode on them, and nothing deletes a `.last` file (`src/bombadil/dev.py:864-871`, `src/bombadil/dev.py:885-931`).

## If you fork it

Decide first whether you keep full access. If you do, add no confirm dialog for something undo can reverse; make it visible and undoable, as [the principle](principles.md#full-access-with-undo) says. If you narrow it, the places are the two flag sets in `src/bombadil/providers.py:261` and `src/bombadil/providers.py:584-586`, `iso/airootfs/etc/sudoers.d/bombadil`, the system prompt in `src/bombadil/providers.py:33-64`, and `tests/test_providers.py`. Nothing in Bombadil is built to ask, so narrowing means building that.

Before you hand an image to anyone else:

| Do this | Where |
|---|---|
| Set a password: drop `passwd -d user`, and stop `greetd` logging `user` in unasked or pair it with disk encryption. | `iso/airootfs/usr/local/bin/bombadil-install:60`, `iso/airootfs/etc/systemd/system/bombadil-live.service:8`, `iso/airootfs/etc/greetd/config.toml` |
| Install a lock screen. `lock` already runs `hyprlock` when it is present. | `iso/packages.x86_64`, `src/bombadil/launcher.py:990-994` |
| Give the `agentd` socket mode 0600, as the brain and the mail service do, and decide what `agentd` does with a peer outside a turn's scope (it takes one for the person, a coding session's tool included) and with `dev`, `dev-signal` and `away`, which it does not look at. | `src/bombadil/agentd.py:452`, `src/bombadil/agentd.py:587-602`, `src/bombadil/agentd.py:1164-1186`, `src/bombadil/brain/service.py:376`, `src/bombadil/mail/service.py:506-511` |
| Remove boot entries 02 and 03 and the serial autologin from the profile. | `iso/efiboot/loader/entries/`, the `ttyS0` serial-getty drop-in folder under `iso/airootfs/etc/systemd/system/` |
| Pin the provider CLI versions. | `scripts/build-iso.sh:19-23`, `iso/airootfs/usr/local/bin/bombadil-setup:12-13` |
| Make the home folder 0700 and set a session umask of 077. The installer sets neither. | `iso/airootfs/usr/local/bin/bombadil-install:58-59` |

When you add something:

- **A socket or a port.** Put it under `paths.runtime_dir()`, set its mode in the code, check `SO_PEERCRED` when others can open it, and add a test for the mode. The mail socket has a test of its mode (`tests/test_mail_service.py:303`); `agentd.sock`, `brain.sock` and `watch.sock` have none.
- **A tool in `os-mcp`.** It is power handed to a model that reads other people's words. Register it with `OsTools._tool` (`src/bombadil/mcp_server.py:46-54`). Give the agent a way to prepare, never a tool that releases, and put the press where only the person's own press reaches it.
- **Something that reaches people.** Register a performer with `Outbox.register(kind, performer)` (`src/bombadil/outbox.py:129-130`) where `agentd` builds its outbox (`src/bombadil/agentd.py:375`), and let only the person's press on a view the person controls call it. Have the service that does the act check what was shown, as the mail service's `send` does, and add no second way from a press to an act. Never add a tool that releases, such as a `mail_send`, and keep the scope check and the press log. Tests: `tests/test_outbox.py`, `tests/test_mcp_server.py:408`; [extending mail](architecture/mail.md#extending-it).
- **A process the person starts through the agent, as a coding session is.** Decide which side of the scope check it is on (`procs.cgroup_of` recognises only `bombadil-turn-` names), what its hooks may send and who else may send the same message, and whether its work needs a restore point. `bombadil-signal` trims what it sends and `agentd` believes it ([Coding sessions](#coding-sessions)).
- **A binding in the app kit.** Assume the app is the agent: whatever it exposes runs with the user's rights. Make writes a no-op under `ctx.check`, as `Vault`, `TextFile` and `Clipboard` do.
- **A secret.** Write it with `atomic_write(..., mode=0o600)` (`src/bombadil/appkit/native/files.py:95-112`), keep it out of what a turn logs, and add its name to the private lists so the brain never reads it (`src/bombadil/brain/rules.py:39-46`).
- **Anything that puts outside text in front of a model.** Fence it with a random marker, as `describe` does, and run that model with no tools (`src/bombadil/brain/describe.py:256-262`). Where the model has to have tools, mark the text as `mail_read` does and say that the marks are a convention (`src/bombadil/mail/tools.py:383-415`).
