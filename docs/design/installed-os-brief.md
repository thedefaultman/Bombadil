# Bombadil, installed

You download one file from Bombadil's release page. Above the button, a short list starts in Windows: check that your BitLocker recovery key is saved at aka.ms/myrecoverykey, write the file to a USB stick with balenaEtcher, suspend BitLocker once, restart into the firmware settings, turn Secure Boot off, and start from the stick. The stick opens on the pill. You join Wi-Fi and the clock sets itself to your time zone; you sign in, give your name and pick a voice, and a chip says "Install on this computer". The card draws your disk as a bar ("Samsung 980, 1 TB. Windows 11 is on it"), leaves out the stick you started from, and asks for one thing, a password. The time zone, keyboard, computer name and what comes along from the stick each take one line with "change". The red button names the disk. A few minutes later the card says to take the stick out and restart.

The laptop starts "Bombadil" by itself. One plain line asks for your password, and the desktop opens signed in, with your conversation, the apps you made on the stick and "Welcome home, Daniel. Undo works from here." A card shows your recovery key once. In an ordinary week, closing the lid locks the screen behind the same password, old restore points clear themselves before the disk fills, and "update" brings Arch's packages and Bombadil's own new release inside one restore point, so a kernel you regret goes back with undo like anything else.

When a change breaks the start, the machine puts itself back after two failed starts and says which change it undid. If the disk will not start at all, the stick you kept offers Repair: you type your password, the change that broke things shows in red, and "Go back to before that" or "Reinstall, keep my files" leave your home, sign-in and apps where they were.

This is the seventh design pass. ## Does this change what we are doing?

**Mostly no. The product stays the same; the order changes, and some plumbing that is cheap now becomes a migration later.** Every brief so far already assumes an installed machine: undo and restore points, updates as a turn, promises that survive a restart, the Brain's history. None of that works on the stick, which already says "Undo starts once Bombadil is installed" (launcher.py:321-322). What the question changes is what must be true before anyone other than Daniel installs, because an installed machine never sees a new stick: every later fix has to arrive by update, and a few things cannot.

**What stays as it is:**
- the pill, the agent in full-access mode, passwordless sudo for the agent, and undo as the safety;
- sign-in on the stick, carried into the install (ux-brief.md:128), and one install card with one red button that names the disk (ux-brief.md:114, :162);
- GRUB, with the kernel inside restore points and the ESP at /efi (ux-brief.md:152);
- the tty2 rescue page (ux-brief.md:154), updates as a turn on your word (passenger-brief.md:164), Bombadil from its own signed repository (passenger-brief.md:170), and user-level CLI installs (dev-brief.md:153);
- the desk, the Brain, sessions, the voice.

**What changes:**
1. **Four things are decided once, at install, and must be right before the first stranger installs:** the disk layout (ESP at /efi, logs and the package cache outside the root that undo swaps, home folders kept out of home restore points), encryption and the one password, where GRUB lives and how the firmware finds it, and which files pacman owns. Today's install gets all four wrong: the ESP is at /boot so the kernel is outside every restore point (bombadil-install:34-36), GRUB sits only on the fallback path (:63), there is no password or encryption (:55), and nothing Bombadil ships belongs to a package (build-iso.sh:12-23).
2. **A way for Bombadil's own files to reach a machine that is already installed.** Nothing does this today. skel's hyprland.lua is copied once (bombadil-install:54), so PR #7's Virtual-1 fix (hyprland.lua:5) never reached Daniel's laptop VM, which is updated by hand. The passenger brief already chose the route: packages from Bombadil's own signed repository. That moves from "later" to "second".
3. **The install card moves up.** Today installing means typing a device name in a terminal (bombadil-install:7-9). Fine for Daniel and the tests, not for anyone else, so no public download ships before the card.
4. **The stick gets more jobs.** Besides trying and installing, it repairs a machine that will not start, reinstalls while keeping your files, and erases the disk for the next owner.

**One bug to fix now.** Started from a USB stick on a laptop with enough free memory, archiso copies the image into RAM and unmounts the stick (archiso hook v73, :221, :344-351, :377-380). bombadil-install:36 then copies the kernel from the missing `/run/archiso/bootmnt`, and `set -e` stops the script after the disk was wiped and copied, leaving no boot loader. The VM tests attach the ISO as a CD drive (test-vm.sh:73), which the hook exempts. Read in the hook, not reproduced. The fix is one line: take the kernel from `/usr/lib/modules/<kver>/vmlinuz`. It is the first commit of piece 1, and Laptop VM findings fixes can take it sooner.

## The rules

1. **The installed machine is the product; the stick is the door** for trying, installing, repairing, reinstalling and erasing. Everything that lasts lives on the installed machine.
2. **Nothing is erased that you did not name.** The red button names the disk and what is on it. The stick you started from and any disk in use are never offered, and USB disks are marked. The agent may fill in the card and explain it, but no model call sits between the button and the disk.
3. **Two questions: which disk, and one password.** Everything else is filled in from the stick, the network and the machine, one line each with "change".
4. **Decide at install only what an update cannot change later.** The layout, encryption, where GRUB lives and the account name `user` are fixed at install. Everything else arrives by update, or by a numbered layout step inside an update turn.
5. **Every file Bombadil puts in / has an owner.** A pacman package owns it, or, for a file another package owns, a numbered step changes it. Bombadil's defaults live in /usr and change with each update; your own settings live in short files that load those defaults, and no update overwrites them.
6. **Your home is never rewritten.** Install, update, refresh and a root undo only add missing files; the one exception moves an old hyprland.lua aside once and keeps it. A file in your home must still work on the oldest root undo can reach.
7. **Every way back keeps your files and works without the part that broke.** Undo, the bad-start rollback, Repair and "Reinstall, keep my files" need no network, model or desktop; the agent explains when it can.
8. **The laptop VM is the first user.** Each piece ships a smoke mode that walks Daniel's exact path (install from an older ISO, then refresh or update, then undo across a reboot) before anything reaches his disk.

## Build these first

These are the two things no later update can fix: the disk, and the path every later fix travels.

### 1. The disk that lasts: layout v1, and a refresh that keeps your home

**What you see:** Before the card (piece 3), nothing looks different on the stick. On Daniel's laptop VM, `bombadil-vm refresh` puts a fresh system under the same home: still signed in, same Apps, history, Wi-Fi and time zone, and the old system kept aside for 14 days. An undo after a kernel update boots the old kernel with its own modules, and the logs of the bad start are still there. Installing from a USB stick works on a laptop with plenty of memory. With a password set, power-on shows one plain line asking for it, and the desktop follows with no second prompt.

**Why first:** The layout is the one thing no update can change, and encryption cannot be added under an existing btrfs without re-encrypting in place. The kernel sits outside every restore point today (bombadil-install:34-36), which the first brief called "urgent now" (ux-brief.md:198). The copy-to-RAM bug sits on the same lines. And Daniel's VM has no way forward except a wipe (wsl-vm.sh:68-69), which every later layout change would need too.

**What changes:** `iso/airootfs/usr/local/bin/bombadil-install` stays one bash script, split into named functions (`probe`, `partition`, `subvolumes`, `copy`, `carry`, `configure`, `boot`, `record`).
- **First commit:** the kernel comes from `/usr/lib/modules/<kver>/vmlinuz` of the copied root (bombadil-install:36).
- **Command line:** `bombadil-install --plan FILE [--password-fd N]`. The plan is JSON the card will write (disk, time zone and its source, keymap, hostname, carry list, fresh or refresh). The password comes from a file descriptor, never argv or the plan. `bombadil-install DISK --yes` stays for bombadil-smoke:122 and wsl-vm.sh:89 and means no password and no encryption.
- **Guards:** refuse without `/sys/firmware/efi` (the stick is UEFI only, profiledef.sh:10), when the target holds the stick (found from `archisosearchuuid` on /proc/cmdline with `blkid` and `lsblk -no PKNAME`, since copy-to-RAM unmounts it), or when any partition on it is mounted. Partition paths come from `lsblk -nro PATH`, replacing the suffix rule (:14).
- **Partitions:** GPT as today (:11-16), p1 a 1 GiB ESP. With a password, p2 is LUKS2 with btrfs inside, and three keyslots: the password slot GRUB opens, argon2id with memory far below cryptsetup's 1 GiB default (256 MiB or lower, tuned to about 2 to 3 seconds on the slowest test laptop; not measured), because at the default cost GRUB rejects the correct password on firmware that fragments memory below 4 GiB (CachyOS issue #470); a random key file in `/etc/cryptsetup-keys.d/root.key`, added to the initramfs, with a cheap pbkdf2 slot, so the password is typed once; and a recovery key from `systemd-cryptenroll --recovery-key`, kept in `/var/lib/bombadil/recovery-key` (mode 600, inside the encrypted disk) only until the first-start card shows it.
- **Subvolumes:** at the top level `@`, `@home`, `@snapshots` (:18), plus `@log` (/var/log) and `@pkg` (/var/cache/pacman/pkg), beside `@` because rollback renames `@` (bombadil-rollback:14). Inside `@home`, nested subvolumes for what home restore points skip: `user/.cache`, `user/.local/state/bombadil`, `user/.claude`, `user/.codex`, `user/.local/share/claude`, `user/.config/chromium`, `user/Projects` (ux-brief.md:261, dev-brief.md:202, :259). A snapshot does not descend into them. `~/.claude.json` is a file, so the home undo skips it by name. `snapper -c home create-config /home` with `TIMELINE_CREATE=no`, for the decided live home undo (ux-brief.md:104).
- **Copy:** from `/run/archiso/airootfs`, the read-only image under the overlay (hook:370), instead of `cp -ax /.` (:27); if that mount is missing, `cp -ax` with the journal, `/etc/pacman.d/gnupg`, `/root`, the package cache and `/var/lib/NetworkManager` also removed. In the chroot: `pacman-key --init` and `--populate` (the image's keyring is empty); create `user` (UID 1000, as :53); `chpasswd` from the descriptor; zone, keymap and hostname from the plan; enable greetd, NetworkManager, systemd-timesyncd and fstrim.timer. Then snapshot 1, "Bombadil <version>, as installed".
- **Programs installed on the stick:** every package whose version on the stick differs from the image's (what you installed and whatever came with it), installed offline in the chroot from the stick's cache as snapshot 2, "Brought from the USB stick: Spotify", so old libraries never meet new programs. No network, provider or agent needed (untested).
- **Carry:** a new `/usr/share/bombadil/install/carry.list`, one home path per line, read by PR #5's copy loop: its four paths, then `Apps`, `.local/state/bombadil` (turns.jsonl, session.json, desk.toml) and `.config/chromium`. Threads add lines instead of editing the installer. The Wi-Fi connections you joined are copied into `/etc/NetworkManager/system-connections`. Other hand changes to the stick's system files stay behind, and the card says so.
- **Boot:** the ESP at /efi. `grub-install --target=x86_64-efi --efi-directory=/efi --boot-directory=/efi --bootloader-id=Bombadil` makes a named firmware entry; a second run with `--removable` writes `EFI/BOOT/BOOTX64.EFI` on a whole disk or USB drive, never on a Windows ESP; `grub-mkconfig -o /efi/grub/grub.cfg` (also at :70). GRUB's core, modules, grub.cfg and grubenv live on the ESP and never roll back; kernel, initramfs and microcode live in `@/boot` under stable names, so grub.cfg works after any undo. `GRUB_ENABLE_CRYPTODISK=y`, `GRUB_DISTRIBUTOR="Bombadil"` (text; art is the logo thread's), vm-fixes' hidden-menu lines kept.
- **Initramfs and fstab:** `mkinitcpio.conf.d/bombadil.conf` with `systemd`, `microcode`, `sd-vconsole`, `sd-encrypt` and `FILES`, plus `/etc/crypttab.initramfs`; the preset (:43-47) gains a `fallback` image with `-S autodetect`; `amd-ucode` and `intel-ucode` join packages.x86_64. fstab is written from UUIDs instead of genfstab (:38-41): /, /home, /.snapshots, /var/log, /var/cache/pacman/pkg, and /efi with `umask=0077`.
- **Record:** `/var/lib/bombadil/install.json` with date, image version and commit, `layout: 1`, `encrypted`, target kind, `timezone_source`, the packages brought, and `recovery_key_pending`.
- **`--refresh`** (whole-disk layout only in v1): open LUKS if encrypted; rename `@` and `@snapshots` to `@.before-refresh-<date>` and `@snapshots.before-refresh-<date>`, so an old `turn:` snapshot can never be swapped in; before touching the ESP, copy the old ESP's kernel and initramfs into the old root's /boot and point its fstab's /boot line at /efi, so "go back to before the refresh" can start; empty the ESP instead of reformatting it, so its UUID stays; copy into a new `@` while `@home` is not mounted (today it is mounted before the copy, :22, and emptied after, :28); turn the listed home folders into nested subvolumes (move aside, create, reflink back); keep NetworkManager connections, hostname, localtime, locale, vconsole, machine-id, ssh host keys, linger and `user`'s password hash from the old root; write the old root's extra packages to `/var/lib/bombadil/refresh-<date>.txt` for the agent to offer back; copy skel with `cp -an` as `user` instead of `cp -aT` and `chown -R` (:54); copy carry paths only where the kept home lacks them, so a sign-in on the stick never overwrites the kept `.claude.json` or persona.toml; clear `undo.json` (launcher.py:284-285), which names old snapshot numbers.
- **bombadil-rollback** refuses a snapshot with no `boot/vmlinuz-linux`, in one line the launcher's undo shows, and gains `--device DEV` for the stick (today `findmnt /`, bombadil-rollback:7).
- **The stick:** timesyncd enabled (today only NetworkManager, bombadil-live and pacman-init are). Boot entries 02 and 03 only when `BOMBADIL_TEST_ENTRIES=1`, which test-vm.sh and wsl-vm.sh set; entry 03 erases /dev/vda without asking (bombadil-smoke:12, :121-123), and /dev/vda is also Daniel's VM disk.
- **Tests (scripts/test-vm.sh):** `MODE=install` attaches the ISO as a USB disk with 8 GB instead of `-cdrom` (:73), so copy-to-RAM is exercised, and checks the stick is refused as a target; `MODE=install-encrypted` types the password into GRUB with `qmp.py send-keys`; `MODE=refresh OLD_ISO=…` installs from the previous ISO, refreshes, then undoes across a reboot; a writable OVMF variables copy (today read-only code only, :34) so the named entry is checked. The undo mode (bombadil-smoke:125-139) also checks /efi is vfat, /boot is on btrfs, the fallback initramfs, `@log`, `efibootmgr`, `modinfo -k "$(uname -r)" btrfs` after the undo reboot, `cryptsetup status root`, and a kept-home file surviving a refresh.
- **Daniel's VM:** with it off, `qemu-img snapshot -c before-installed-os /root/Bombadil/out/bombadil.qcow2` on the WSL host, then `bombadil-vm refresh`. The host snapshot is required: it is the only way back to the old ESP.

### 2. Bombadil as packages, with homes that follow its releases

**What you see:** "update" (a turn running `sudo pacman -Syu` until passenger piece 6 exists) brings Bombadil's new version in the same restore point as everything else; the receipt names it and undo takes it back. "what version is this?" answers "Bombadil 2026.10.06 (d9dde3b), installed 2 Oct". A fix to a key, a window rule or an autostart line reaches a machine installed last month, because your hyprland.lua is now a few lines that load Bombadil's part, followed by your own. On the laptop, `bombadil-vm update` then "update" takes two minutes and no ISO build.

**Why first:** Every install made before this holds files no package owns (/usr/share/bombadil, the /usr/local/bin links, the npm trees; build-iso.sh:12-23), and on each the first package would need `--overwrite`, the riskiest update Bombadil could ship. Three branches edit skel's hyprland.lua (PR #5, #4, #8) and none of those edits reach an installed home. The Brain's units need a way onto existing machines. And every later brief's "What changes" depends on which files Bombadil owns.

**What changes:**
- **`packaging/bombadil/PKGBUILD` and `bombadil.install` (new).** `/usr/share/bombadil/{bin,src,shell,share,packages.x86_64,VERSION}` at the same path, so `paths.share_dir()` (paths.py:39-40) and hyprland.lua:9 do not change; VERSION holds date and commit. Commands in /usr/bin, because Arch packages never install to /usr/local: agentd, bombadil, bombadil-app, bombadil-os-mcp, and the four scripts from `iso/airootfs/usr/local/bin`. Units in `/usr/lib/systemd/{system,user}`, enabled by the scriptlet in `post_install` and `post_upgrade` from a list in the package, as pipewire.install does; that is how the Brain's units, and later agentd and Quickshell as services, reach existing installs. A tmpfiles.d line for linger replaces the installer's `touch` (dev-sessions bombadil-install:58). `/etc/sudoers.d/bombadil` (440) and `/etc/bombadil/config.toml` in `backup=`; the Claude Code, Codex and Chromium managed settings as plain package files.
- **Files other packages own** (`/etc/greetd/config.toml`, `/etc/environment`, `/etc/default/grub`, `/etc/pacman.conf`, the mirror list) change only by numbered steps in `/usr/share/bombadil/migrate/NNN-*.sh` that check the file, not a version number, or by a drop-in where one exists (a `greetd.service.d` drop-in running greetd with `-c /usr/share/bombadil/greetd/config.toml`).
- **The config split.** Today's 72-line skel file, plus the lines PR #4, #5 and #8 add, moves to `/usr/share/bombadil/share/hypr/bombadil.lua`. skel's hyprland.lua becomes:
  ```lua
  -- Bombadil's part comes from the system and follows its updates. Your own lines go below.
  local ok = pcall(require, "/usr/share/bombadil/share/hypr/bombadil")
  local old = os.getenv("HOME") .. "/.config/hypr/hyprland.lua.before-split"
  if not ok and io.open(old) then dofile(old) end
  ```
  Hyprland 0.56 loads a module starting with `/` as a file and reloads it on change (ConfigManager.cpp:77-78, :575-580); a missing one is a plain Lua error `pcall` catches (lua-CM-v0.56.2.cpp:563-590). The fallback keeps a migrated home working after a root undo to before the split (rule 6).
- **`src/bombadil/homefix.py` (new),** run by agentd at start before it opens its socket: numbered steps, safe to run twice, recorded in `~/.local/state/bombadil/home.json`. Step 1 moves an old hyprland.lua to `hyprland.lua.before-split` and writes the stub followed by the old lines that appear in no shipped skel version (kept in `share/hypr/old/`), including wsl-vm.sh's tagged monitor line (wsl-vm.sh:90), then `hyprctl reload`. Step 2 adds missing skel entries such as app-kit's skill links and PR #5's `chromium-flags.conf`. No step touches `.claude`, `.claude.json`, `.codex` or `.config/bombadil`.
- **`scripts/build-iso.sh`.** Lines 11-18 become `makepkg` into `$work/repo` plus `repo-add`, as a throwaway build user (makepkg refuses root, and build-in-container.sh builds as root). A build-time pacman.conf lists `[bombadil]` over `file://` above `[core]` (iso/pacman.conf:7-10), and `bombadil` joins packages.x86_64. Moved files leave airootfs, because mkarchiso copies airootfs before pacstrap and pacman refuses existing files; profiledef.sh:18-21 and :23 go. The npm CLIs (build-iso.sh:20-23) stay as the one unowned exception until piece 7.
- **Repositories, stage one.** `/etc/pacman.d/bombadil.conf`, owned by the package and included from `[bombadil]`, lists `Server = http://10.0.2.2:8123` (the WSL host, laptop VM only) and `file:///var/lib/bombadil/repo` (a copy on the image), with `SigLevel = Optional TrustAll`. Nothing public reads it. Piece 6 replaces the file by an ordinary update with the signed public server and `SigLevel = Required` (unverified: that `SigLevel` in an included file applies to its section).
- **`scripts/wsl-vm.sh` (windows-vm):** `update` runs `makepkg` in the tree and `repo-add` into `out/repo`, serves it on 127.0.0.1:8123 while the VM runs, and boots the disk (10.0.2.2 reaching the host under WSL is untested).
- **"Install this build"** (dev-brief.md:182) becomes `makepkg` plus `pacman -U` as a machine turn, so pacman keeps owning every file.
- **Existing installs move by one refresh (piece 1), never by `pacman --overwrite`.**
- **Tests.** `tests/test_homefix.py` runs each step twice on a fake home and checks the sign-in files are unchanged byte for byte. `MODE=update` installs, serves a package one `pkgrel` newer, takes a `turn:` snapshot, runs `pacman -Syu`, checks `pacman -Qo` names bombadil, the version, the stub and an empty `hyprctl configerrors`, then undoes across a reboot and checks the older version and the bar. PR #8's tests that read the installer and skel by path (vm-fixes tests/test_iso_profile.py:51, :78) move with the files.

**Before building:** build once and read mkarchiso's output for "exists in filesystem"; in the VM, check the `pcall` fallback, that user lines override the defaults for `hl.monitor` and `hl.bind`, and whether `BROWSER` reaches Chromium and the CLIs from `/usr/lib/environment.d/`; run `pacman -Qo /usr/share/bombadil /etc/greetd/config.toml /etc/environment` on the laptop VM; merge PR #5, PR #4 and the brain branch first (each adds to build-iso.sh:16).

**Effort:** M to L; homefix and the update test take most of it.

## A life with an installed Bombadil

**Getting it.** One download, its checksum, "Intel or AMD PCs only", and the ordered list from Windows; no editions or mirrors. balenaEtcher writes and checks the stick.

**Trying it, and the first start on the stick, in order.** The stick's menu ("Bombadil", then "Safe graphics"), the pill, Wi-Fi through PR #5's chip (the time zone is set silently here), the provider question and sign-in (PR #5), the voice brief's card (a name field and three voice rows), then the chip "Install on this computer" with "Undo starts once Bombadil is installed". "Will my Wi-Fi work if I install?" is answered from the "This computer" rows with no model.

**Installing.** The card (piece 3, or piece 9 next to Windows). "Should I keep Windows?" is answered from the probe and fills the card in; you press the button. The line counts through the copy and ends with "Installed. Take out the USB stick, then Restart."

**First installed start, in order.** The firmware starts "Bombadil"; GRUB shows one Bombadil line and the password prompt (look: logo thread); the desktop opens signed in with no second prompt; the voice line "Welcome home, Daniel. Undo works from here."; the recovery key, once. Details holds the receipt: "Installed on Samsung 980, encrypted. Brought Spotify, Wi-Fi Home and 2 apps." Nothing else asks anything. If you installed before signing in, sign-in and the voice card come now instead.

**A week.** Closing the lid locks the screen. Restore points clear themselves at 100 pairs, and "what's eating my disk?" says how far undo reaches.

**An update.** As the passenger brief designed, with Bombadil's own lines in the receipt. A new kernel ends with "Restart to finish", and undo takes it back too.

**Something breaks.** A change that cuts off the screen, the shell or the network puts itself back (ux-brief.md:116). A dead desktop drops to the tty2 page. A start that fails twice goes back by itself and says which turn it undid. A disk that will not start at all gets the stick's Repair.

**Reinstalling, keeping your files.** On the stick; one line afterwards names the programs it offers back, and the old system stays aside for 14 days.

**A new laptop.** Plug in the copy drive while the new laptop runs the stick; one card and one turn later it has your home, apps, memory and conversation, with its own drivers and name. The old one is erased from the stick in a second.

## Questions only you can answer

**Answered.** Daniel answered "1a 2c 3a" on 30 Sep 2026 at 20:07 UTC, all three recommended options: new installs lock the disk with one password and a recovery key; a flash drive is the try, install and repair stick, plus a full Bombadil installed onto a USB drive you carry; whole disks and spare laptops install first, next to Windows after. **1. Should a new install lock the disk with a password?** Once installed, encryption cannot be added without wiping the disk. It is not a wall between you and the agent, which keeps full access once the machine is on; it stops a thief who takes the laptop.
- a) Yes, by default. You type one password when the computer starts, the same password unlocks the screen, and a recovery key is shown once. **Recommended**: the agent has sudo and your accounts are signed in, so a lost laptop is worth more to a thief than an ordinary one, and Windows 11, macOS, Pop!_OS and Omarchy all encrypt by default.
- b) Offer it on the install card, off unless you tick it. The password then only locks the screen.
- c) No password and no encryption in the first version, as today.

**2. What should a flash drive be for, besides installing?** You said Bombadil will be used on flash drives as well as installed.
- a) Only a stick you try Bombadil on, install from and repair with. It forgets everything at every restart.
- b) The same stick also keeps your things between restarts. It gets no undo and no updates, so it becomes a second, weaker kind of Bombadil.
- c) a), plus a full Bombadil installed onto a USB drive you carry between computers, with undo and updates like any install. **Recommended**: it comes almost free with piece 1 (the start file every PC finds, and a start image that works on any hardware) and piece 3 (USB drives offered as targets).

**3. Who should be able to install it first?**
- a) People installing on a whole disk or a spare laptop; installing next to Windows comes after. **Recommended**: it proves the disk layout and the update path before BitLocker, Fast Startup and Windows' small start partition enter the picture.
- b) Windows laptops first: installing next to Windows ships before any public download.
- c) Only you, until repair and next to Windows both exist.

## Decisions I picked a default for

**How does a merge reach other people's machines?** Default: CI signs every merge that passes the VM smoke test and publishes it to a testing channel, which your laptop VM follows; the stable channel takes it after 3 days with no revert. Nothing waits on you, as you asked for merges, and your daily use catches what the smoke test misses. Other options: every passing merge goes to everyone at once; your own key signs stable when you say "release".

**When is the time zone set, and is it asked?** Default: detected, never asked. On the stick, when the network first comes up, one HTTPS geo-IP request with no model sets the zone, and timesyncd (now enabled on the stick) sets the clock, so even the stick's greeting can say "Good morning". The card shows the zone as one line with "change" ("Europe/Lisbon, from your network · change"), because geo-IP guesses wrong in countries with several zones and behind VPNs. The installer writes it and records `timezone_source`: `detected`, `chosen` (changed on the card or by "set my time zone to …") or `unset` (the stick never went online; the line then reads "Set when this computer first goes online · change"). An installed machine still `unset` does the same lookup once at its first network. The voice build treats the zone as unset only when `timezone_source` is `unset`, which separates a person in UTC from an unset machine (voice-brief.md:262), and shows its "Set my time zone" chip only then. Other options: ask on the card, as Debian does; read Windows' registry, which BitLocker hides on most laptops; wait for the first installed start. The service is the build thread's pick (unverified).

**How does the system get onto the disk?** Default: the clean image as snapshot 1, the programs you installed on the stick replayed offline from its cache as snapshot 2, then the carry list. Two people who press the same button get the same system, and the stick's journal, keyring, root history and caches stay behind on purpose. Other options: today's `cp -ax` of the live root; pacstrap, which needs a network and differs from the tested image.

**Is snapshot 1 kept for good?** Default: no, it ages out like any restore point; the recipe's baseline is the image version and package list in install.json, and the way back to stock is "Reinstall, keep my files". A reset to a months-old base meets new keys and months of Arch news at once. Other options: create it with no cleanup algorithm (`important=yes` would not protect it: those fall under `NUMBER_LIMIT_IMPORTANT`).

**Where does GRUB live?** Default: core, modules, grub.cfg and grubenv on the ESP; kernels in `@/boot`. Modules never skew against the core after an undo, grubenv is where the decided layout puts it, and grub.cfg is read before the disk is unlocked, so a line can sit above the prompt (inferred). Other options: /boot/grub inside `@`, where an undone grub-install leaves old modules under a new core and GRUB stops before any menu.

**Named firmware entry or fallback path?** Default: both on a whole disk or USB drive, only the named entry on a Windows ESP. Firmware forgets NVRAM entries after updates or a flat battery, and every Bombadil VM boots with no stored variables (test-vm.sh:33-34, run-vm.sh:12, wsl-vm.sh:72). Other options: fallback only, as today (Windows can overwrite it); named entry only (breaks every VM).

**Where is the password typed?** Default: once, at GRUB's prompt, with a key file in the initramfs, because the kernel inside restore points means GRUB must unlock the disk. Other options: Plymouth with kernels on the ESP (rejected in ux-brief.md:152); TPM (piece 12).

**How many passwords, and whose account?** Default: one password for the disk, the account, the lock screen and the consoles, set even without encryption, because with passwordless sudo an empty password on tty2 is root for anyone at the keyboard. The account stays `user` (UID 1000): every path, unit and test uses /home/user (bombadil-smoke:126, wsl-vm.sh:90, PR #5's loop, the subvolume names), and your name lives in persona.toml. The agent's sudo stays passwordless. Other options: a separate disk passphrase; a login name typed on the card.

**A recovery key?** Default: yes, shown once as text and a QR code (its characters are meant for a US-layout prompt), replaceable with "new recovery key". Otherwise a forgotten password, or GRUB rejecting a correct one, loses the disk. Other options: none.

**The keyring?** Default: no keyring daemon; Chromium's basic store, protected at rest by the encrypted disk. greetd's autologin skips PAM auth, and with GRUB unlocking the disk pam_systemd_loadkey has no passphrase to reuse. Other options: gnome-keyring with an empty password; pam_fde_boot_pw from the AUR.

**Keyboard, language and computer name?** Default: keyboard and language from the stick's session; the name from the DMI model, with your name in front when the voice card has one ("daniels-thinkpad"), else "bombadil-" and four characters of the machine id, because a fixed "bombadil" (bombadil-install:52) collides on a shared network. Other options: always "bombadil"; ask.

**The hardware clock?** Default: UTC on a whole disk, local time next to Windows, said on the card. Writing `RealTimeIsUniversal` into Windows' SYSTEM hive from Linux risks the one file Windows needs, and BitLocker usually hides it. Other options: UTC with the registry write; a command for you to run in Windows.

**Swap?** Default: zram at min(RAM/2, 8 GiB), no hibernation. A swapfile inside `@` blocks the snapshot before every turn; a top-level `@swap` can come later. Other options: `@swap` from day one.

**Install before sign-in or offline, and can the agent do it?** Default: yes, through the word "install" (a laptop whose Wi-Fi has no driver still needs a way in); the agent fills the card and you press the button (ux-brief.md:114). Other options: only after sign-in; the agent runs the installer when told.

**How do existing installs reach the new layout and the package?** Default: one refresh, with a host snapshot first on the VM; Daniel's hand changes to its root are listed in refresh-<date>.txt and kept aside 14 days. Other options: `pacman --overwrite` in place (a one-off script, and `/etc/sudoers.d/bombadil` would still conflict); a fresh reinstall, which loses his login because wsl-vm.sh deletes the disk.

**Where do Bombadil's defaults live?** Default: /usr/share/bombadil, loaded by a short user file. Other options: `/etc/xdg/hypr/hyprland.lua` alone (one personal line forces a full copy); overwriting the user file each release.

**The stick's boot menu?** Default: one entry plus "Safe graphics" on release ISOs, test entries only in test builds. What the stick keeps between restarts is question 2. Other options: today's three entries, one of which erases /dev/vda.

**Secure Boot?** Default: off, said on the download page with the BitLocker steps and the cost in Windows; Arch's ISO does not boot with it on, and CachyOS, EndeavourOS and Omarchy say the same. Other options: Fedora's signed shim from the AUR with a MOK screen; sbctl now.

**Erase, and a new laptop?** Default: erase from the stick (a second on an encrypted disk), and move through the copy drive plus the recipe, which also covers a dead SSD or a stolen laptop. Other options: `cryptsetup erase` on the running root (unverified); a laptop-to-laptop network transfer.

## Cut, and why

- **archinstall and Calamares.** archinstall uses pacstrap (the install would no longer be the tested image) and the busybox encrypt hook, and cannot shrink Windows; Calamares is a large Qt application only in the AUR, with its own screens. We keep our script and borrow their patterns.
- **Limine, systemd-boot, UKIs, sdbootutil.** GRUB was decided, and these copy kernels onto an ESP that Windows' 100 MiB cannot hold.
- **grub-btrfs snapshot entries.** Its overlay hook does not work with the systemd initramfs; piece 8's rename matches how undo already works.
- **An rsync of the live root over the finished install** (a draft's snapshot 2). It would delete fstab, crypttab, the key, the kernel and grub.cfg.
- **`bombadil adopt` with `pacman --overwrite`, and "reset to snapshot 1" without the stick.** Existing installs move by refresh, and one way back to stock is enough.
- **Refresh as the way people take an update.** Layout changes ship as numbered steps inside the update turn.
- **Persistence on the live stick.** A second kind of Bombadil with no undo.
- **Manual partitioning, LVM, RAID, BIOS/CSM, another Linux beside it, OEM mode, ARM laptops and Macs.** Rare on day one, and each doubles the tests.
- **A Windows entry in GRUB, writing Windows' registry, encrypting an install in place.** BitLocker recovery, risk to the one file Windows needs, risk to someone's only copy.
- **Hibernation, snapper's hourly timeline, A/B roots, a Plymouth splash.** Nobody asked; turn snapshots are the timeline; a read-only root fights the agent; GRUB's prompt comes before any splash.
- **NVIDIA installed on the stick itself.** It blacklists nouveau and leaves older cards with no driver.
- **Our own stick writer, a username field, laptop-to-laptop transfer, TPM and shim now,** and any model call on the path that erases a disk.
