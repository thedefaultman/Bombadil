Bombadil, installed

You download one file, write it to a USB stick and start from it; the stick opens on the pill, you join Wi-Fi, sign in and pick a voice, and a chip says “Install on this computer”. The card draws your disk as a bar, asks for one thing, a password, and its one red button names the disk. A few minutes later the laptop starts Bombadil by itself, one plain line asks for your password, and the desktop opens signed in with “Welcome home, Alex. Undo works from here.”

Besides running from a flash drive, will Bombadil also be installed as an operating system, the way a person installs Debian or Windows, how would that look, and does it change what is being done?

Does this change what we are doing?

Mostly no. The product stays; the order changes, and some plumbing that is cheap now becomes a migration later.

Every brief so far already assumes an installed machine: undo and restore points, updates as a turn, promises that survive a restart, the Brain's history. None of that works on the stick, which already says “Undo starts once Bombadil is installed” (launcher.py:321-322). What the question changes is what must be true before anyone other than the owner installs, because an installed machine never sees a new stick. Every later fix has to arrive by update, and a few things cannot.

What stays as it is

  • The pill, the agent in full-access mode, passwordless sudo for the agent, and undo as the safety.
  • Sign-in on the stick, carried into the install, and one install card with one red button that names the disk.
  • GRUB, with the kernel inside restore points and the ESP at /efi.
  • The tty2 rescue page, updates as a turn on your word, Bombadil from its own signed repository, and user-level CLI installs.
  • The desk, the Brain, sessions, the voice.

What changes

  1. Four things are decided once, at install, and must be right before the first stranger installs: the disk layout (ESP at /efi, logs and the package cache outside the root that undo swaps, home folders kept out of home restore points), encryption and the one password, where GRUB lives and how the firmware finds it, and which files pacman owns. Today's install gets all four wrong: the ESP is at /boot so the kernel is outside every restore point, GRUB sits only on the fallback path, there is no password or encryption, and nothing Bombadil ships belongs to a package.
  2. A way for Bombadil's own files to reach a machine that is already installed. Nothing does this today. skel's hyprland.lua is copied once, so the Virtual-1 monitor fix never reached the VM that mirrors a real install, which is updated by hand. The passenger brief already chose the route, packages from Bombadil's own signed repository; it moves from “later” to “second”.
  3. The install card moves up. Today installing means typing a device name in a terminal. That is fine for the owner and the tests, not for anyone else, so no public download ships before the card.
  4. The stick gets more jobs. Besides trying and installing, it repairs a machine that will not start, reinstalls while keeping your files, and erases the disk for the next owner.
One bug to fix now

Installing from a real USB stick can leave the disk unable to start

  1. You start from a USB stick on a laptop with enough free memory.
  2. archiso copies the image into RAM and unmounts the stick (hook v73, :221, :344-351, :377-380).
  3. The installer wipes the disk and copies the system onto it.
  4. bombadil-install:36 copies the kernel from the missing /run/archiso/bootmnt.
  5. set -e stops the script. The disk was wiped and copied, and has no boot loader.
The fix, one lineTake the kernel from /usr/lib/modules/<kver>/vmlinuz. It is the first commit of piece 1, and the VM findings fixes can take it sooner.

The VM tests attach the ISO as a CD drive (test-vm.sh:73), which the hook exempts. This was read in the hook, not reproduced.

The rules

Eight rules every piece follows.

  1. The installed machine is the product; the stick is the door.The stick is for trying, installing, repairing, reinstalling and erasing. Everything that lasts lives on the installed machine.
  2. Nothing is erased that you did not name.The red button names the disk and what is on it. The stick you started from and any disk in use are never offered, and USB disks are marked. The agent may fill in the card and explain it, but no model call sits between the button and the disk.
  3. Two questions: which disk, and one password.Everything else is filled in from the stick, the network and the machine, one line each with “change”.
  4. Decide at install only what an update cannot change later.The layout, encryption, where GRUB lives and the account name user are fixed at install. Everything else arrives by update, or by a numbered layout step inside an update turn.
  5. Every file Bombadil puts in / has an owner.A pacman package owns it, or, for a file another package owns, a numbered step changes it. Bombadil's defaults live in /usr and change with each update; your own settings live in short files that load those defaults, and no update overwrites them.
  6. Your home is never rewritten.Install, update, refresh and a root undo only add missing files; the one exception moves an old hyprland.lua aside once and keeps it. A file in your home must still work on the oldest root undo can reach.
  7. Every way back keeps your files and works without the part that broke.Undo, the bad-start rollback, Repair and “Reinstall, keep my files” need no network, model or desktop; the agent explains when it can.
  8. A VM that mirrors a real install is the first user.Each piece ships a smoke mode that walks that machine's exact path (install from an older ISO, then refresh or update, then undo across a reboot) before anything reaches a real disk.

Build these first

These are the two things no later update can fix: the disk, and the path every later fix travels.

1

The disk that lasts: layout v1, and a refresh that keeps your home

Build firstL

What you see

Before the card (piece 3), nothing looks different on the stick. On a VM that mirrors a real install, bombadil-vm refresh puts a fresh system under the same home: still signed in, same Apps, history, Wi-Fi and time zone, and the old system kept aside for 14 days. An undo after a kernel update boots the old kernel with its own modules, and the logs of the bad start are still there. Installing from a USB stick works on a laptop with plenty of memory. With a password set, power-on shows one plain line asking for it, and the desktop follows with no second prompt.

Why first

The layout is the one thing no update can change, and encryption cannot be added under an existing btrfs without re-encrypting in place. The kernel sits outside every restore point today (bombadil-install:34-36), which the first brief called “urgent now”. The copy-to-RAM bug sits on the same lines. And a VM that mirrors a real install has no way forward except a wipe (wsl-vm.sh:68-69), which every later layout change would need too.

What changes

  • iso/airootfs/usr/local/bin/bombadil-install stays one bash script, split into named functions: probe, partition, subvolumes, copy, carry, configure, boot, record.
  • First commit: the kernel comes from /usr/lib/modules/<kver>/vmlinuz of the copied root.
  • Command line: bombadil-install --plan FILE [--password-fd N]. The plan is JSON the card will write (disk, time zone and its source, keymap, hostname, carry list, fresh or refresh). The password comes from a file descriptor, never argv or the plan. bombadil-install DISK --yes stays for bombadil-smoke and wsl-vm.sh and means no password and no encryption.
  • Guards: refuse without /sys/firmware/efi (the stick is UEFI only), when the target holds the stick (found from archisosearchuuid on /proc/cmdline with blkid and lsblk -no PKNAME, since copy-to-RAM unmounts it), or when any partition on it is mounted. Partition paths come from lsblk -nro PATH, replacing the suffix rule.
  • Partitions and keys: GPT, p1 a 1 GiB ESP. With a password, p2 is LUKS2 with btrfs inside and three keyslots. The password slot GRUB opens uses argon2id at 256 MiB or lower, tuned to about 2 to 3 seconds on the slowest test laptop (not measured), because at cryptsetup's 1 GiB default GRUB rejects the correct password on firmware that fragments memory below 4 GiB (CachyOS issue #470). A random key file in /etc/cryptsetup-keys.d/root.key, added to the initramfs with a cheap pbkdf2 slot, means the password is typed once. A recovery key from systemd-cryptenroll --recovery-key is kept in /var/lib/bombadil/recovery-key (mode 600, inside the encrypted disk) only until the first-start card shows it.
  • Subvolumes: as drawn above. snapper -c home create-config /home with TIMELINE_CREATE=no, for the decided live home undo.
  • Copy: from /run/archiso/airootfs, the read-only image under the overlay, instead of cp -ax /.; if that mount is missing, cp -ax with the journal, /etc/pacman.d/gnupg, /root, the package cache and /var/lib/NetworkManager also removed. In the chroot: pacman-key --init and --populate (the image's keyring is empty); create user (UID 1000); chpasswd from the descriptor; zone, keymap and hostname from the plan; enable greetd, NetworkManager, systemd-timesyncd and fstrim.timer. Then snapshot 1, “Bombadil <version>, as installed”.
  • Programs installed on the stick: every package whose version on the stick differs from the image's, installed offline in the chroot from the stick's cache as snapshot 2, “Brought from the USB stick: Spotify”, so old libraries never meet new programs. No network, provider or agent needed (untested).
  • Carry: a new /usr/share/bombadil/install/carry.list, one home path per line, read by the native login's copy loop: its four paths, then Apps, .local/state/bombadil (turns.jsonl, session.json, desk.toml) and .config/chromium. Other pieces of work add lines instead of editing the installer. The Wi-Fi connections you joined are copied into /etc/NetworkManager/system-connections. Other hand changes to the stick's system files stay behind, and the card says so.
  • Boot: the ESP at /efi. grub-install --target=x86_64-efi --efi-directory=/efi --boot-directory=/efi --bootloader-id=Bombadil makes a named firmware entry; a second run with --removable writes EFI/BOOT/BOOTX64.EFI on a whole disk or USB drive, never on a Windows ESP; grub-mkconfig -o /efi/grub/grub.cfg. GRUB_ENABLE_CRYPTODISK=y, GRUB_DISTRIBUTOR="Bombadil" (text; art belongs to the logo and design-system work), the VM findings fixes' hidden-menu lines kept.
  • Initramfs and fstab: mkinitcpio.conf.d/bombadil.conf with systemd, microcode, sd-vconsole, sd-encrypt and FILES, plus /etc/crypttab.initramfs; the preset gains a fallback image with -S autodetect; amd-ucode and intel-ucode join packages.x86_64. fstab is written from UUIDs instead of genfstab: /, /home, /.snapshots, /var/log, /var/cache/pacman/pkg, and /efi with umask=0077.
  • Record: /var/lib/bombadil/install.json with date, image version and commit, layout: 1, encrypted, target kind, timezone_source, the packages brought, and recovery_key_pending.
Refresh, rollback, the stick, tests and the VM that mirrors a real install 5 more›

Bombadil as packages, with homes that follow its releases

Build firstM to L

What you see

“update” (a turn running sudo pacman -Syu until passenger piece 6 exists) brings Bombadil's new version in the same restore point as everything else; the receipt names it and undo takes it back. “what version is this?” answers “Bombadil 2026.10.06 (d9dde3b), installed 2 Oct”. A fix to a key, a window rule or an autostart line reaches a machine installed last month, because your hyprland.lua is now a few lines that load Bombadil's part, followed by your own. On the VM, bombadil-vm update then “update” takes two minutes and no ISO build.

Why first

Every install made before this holds files no package owns (/usr/share/bombadil, the /usr/local/bin links, the npm trees; build-iso.sh:12-23), and on each the first package would need --overwrite, the riskiest update Bombadil could ship. Three branches edit skel's hyprland.lua (the native login, the named coding sessions and the VM findings fixes) and none of those edits reach an installed home. The Brain's units need a way onto existing machines. And every later brief's “What changes” depends on which files Bombadil owns.

What changes

Commands in /usr/bin, because Arch packages never install to /usr/local: agentd, bombadil, bombadil-app, bombadil-os-mcp, and the four scripts from iso/airootfs/usr/local/bin. Units in /usr/lib/systemd/{system,user}, enabled by the scriptlet in post_install and post_upgrade from a list in the package, as pipewire.install does; that is how the Brain's units, and later agentd and Quickshell as services, reach existing installs. A life with an installed Bombadil

By moment, as it looks once the pieces on this page are built. The drawn screens are mock-ups in the shell's look, not screenshots; every mark and the power-on look belong to the logo and design-system work.

  1. Getting it

    One download, its checksum, “Intel or AMD PCs only”, and the ordered list from Windows; no editions or mirrors. balenaEtcher writes and checks the stick.

    1. Check that your BitLocker recovery key is saved at aka.ms/myrecoverykey
    2. Write the file to a USB stick with balenaEtcher, or Rufus in DD mode
    3. Suspend BitLocker once
    4. Restart into the UEFI Firmware Settings
    5. Turn Secure Boot off
    6. Start from the stick

    One line on the download page says Secure Boot off stops some Windows games (Valorant, Battlefield 6, Call of Duty Black Ops 7) until piece 12.

  2. Trying it, and the first start on the stick

    In order: the stick's menu (“Bombadil”, then “Safe graphics”), the pill, Wi-Fi through the native login's chip (the time zone is set silently here), the provider question and sign-in, the voice brief's card (a name field and three voice rows), then the chip “Install on this computer” with “Undo starts once Bombadil is installed”. “Will my Wi-Fi work if I install?” is answered from the “This computer” rows with no model.

  3. Installing

    The card (piece 3, or piece 9 next to Windows). “Should I keep Windows?” is answered from the probe and fills the card in; you press the button.

    Which disks
    Disks as bars with one sentence each. The stick you started from and any disk in use are never offered; USB drives are marked and can be targets.
    Readiness
    Rows with one button each (“Plug in the charger”), folded into one green line when nothing needs doing.
    The password
    One field that names the keys which move on a non-US keyboard, since GRUB reads a US layout.
    Coming along
    What comes from the stick, each with an ×. Other hand changes to the stick's system files stay behind, and the card says so.
    The button
    Red, naming the disk and what is on it. The agent may fill in the card and explain it; it cannot press it.
    Found a Bombadil
    The card offers “Reinstall, keep my files”. An install that stops partway says so in plain text.

    The line counts through the copy and ends with “Installed. Take out the USB stick, then Restart.”

  4. First installed start

    In order: the firmware starts “Bombadil”; GRUB shows one Bombadil line and the password prompt; the desktop opens signed in with no second prompt; the voice line “Welcome home, Alex. Undo works from here.”; the recovery key, once. Details holds the receipt: “Installed on Acme SSD, encrypted. Brought Spotify, Wi-Fi Home and 2 apps.” Nothing else asks anything. If you installed before signing in, sign-in and the voice card come now instead.

  5. A week

    Closing the lid locks the screen. Restore points clear themselves at 100 pairs, and “what's eating my disk?” says how far undo reaches.

  6. An update

    As the passenger brief designed, with Bombadil's own lines in the receipt. A new kernel ends with “Restart to finish”, and undo takes it back too.

  7. Something breaks

    A change that cuts off the screen, the shell or the network puts itself back. A dead desktop drops to the tty2 page. A start that fails twice goes back by itself and says which turn it undid: GRUB picks “Start from before turn 41 (install nvidia-open)”. A disk that will not start at all gets the stick's Repair: you type your password, the change that broke things shows in red, and “Go back to before that” or “Reinstall, keep my files” leave your home, sign-in and apps where they were.

  8. Reinstalling, keeping your files

    On the stick; one line afterwards names the programs it offers back, and the old system stays aside for 14 days.

  9. A new laptop

    Plug in the copy drive while the new laptop runs the stick (“Found a copy of your Bombadil from yesterday. Bring it?”); one card and one turn later it has your home, apps, memory and conversation, with its own drivers and name. The old one is erased from the stick in a second.

    A bombadil-keyring package, and a GitHub Actions workflow that builds and signs each merge, builds the ISO, runs the VM test modes and only then publishes. The download page shows one ISO with checksum and signature, “Intel or AMD PCs only”, and the ordered path from Windows.

  1. 7

    Updates as a turn

    M

    Passenger piece 6, which no piece of work owns: keyrings first, then -Su in the same restore point, then the numbered layout steps, then what needs a restart. Installing a program never upgrades the system, and the CLIs become user-level installs.

  2. 8

    A start that fails puts itself back

    M to L

    GRUB clears boot_ok in grubenv at each start, and bombadil-boot-ok.service sets it once agentd answers and the bar is up. After one failed start GRUB shows its menu; after two it picks “Start from before turn 41 (install nvidia-open)” by itself, loading that snapshot's own kernel and initramfs so kernel and modules match.

  3. 9

    Next to Windows

    L

    “Next to Windows” and a red “Replace Windows”, a handle on the bar that never leaves less than 40 GB for Bombadil or 20 GB free for Windows, and, with BitLocker on, the agent walks you through Shrink Volume in Windows first. Windows stays out of GRUB's menu, because starting it from a Linux entry can trigger BitLocker recovery. Its place in the order is question 3.

  4. 10

    Repair, reinstall and erase from the stick

    M

    Repair reads the failed start from @log and offers “Go back to before that” or “Fix it”; Reinstall is piece 1's --refresh; Erase takes a second on an encrypted disk and removes the firmware entry.

  5. 11

    A copy somewhere else, and a new laptop

    L

    “Keep a copy on my USB drive” becomes an Autopilot routine locked with your password; on a new laptop the stick finds the drive, installs stock Bombadil with this laptop's drivers, restores the home and replays the recipe as one turn. The same path adds encryption to an install made without it.

  6. 12

    Secure Boot and TPM

    M to L

    “turn Secure Boot back on” as a red turn with sbctl, keeping Microsoft's keys, only after BitLocker is suspended; then TPM unlock through GRUB's TPM2 key protector, with a GRUB console password. Test with swtpm first; some ThinkPads and ASUS TUF laptops can be bricked by replaced platform keys.

  7. 13

    A Bombadil you carry

    S

    Question 2. An install onto a second USB drive from the same card, with open GPU drivers only and a note that a USB drive is slower and easier to lose. Most of it arrives with pieces 1 and 3.

Questions only you can answer

Each question changes what a person sees, or cannot be undone for people who already installed, so it is yours.

1Should a new install lock the disk with a password?

Once installed, encryption cannot be added without wiping the disk. It is not a wall between you and the agent, which keeps full access once the machine is on; it stops a thief who takes the laptop.

  1. aYes, by default. You type one password when the computer starts, the same password unlocks the screen, and a recovery key is shown once.recommendedThe agent has sudo and your accounts are signed in, so a lost laptop is worth more to a thief than an ordinary one, and Windows 11, macOS, Pop!_OS and Omarchy all encrypt by default.
  2. bOffer it on the install card, off unless you tick it. The password then only locks the screen.
  3. cNo password and no encryption in the first version, as today.

2What should a flash drive be for, besides installing?

The premise of this pass is that Bombadil will be used on flash drives as well as installed.

  1. aOnly a stick you try Bombadil on, install from and repair with. It forgets everything at every restart.
  2. bThe same stick also keeps your things between restarts. It gets no undo and no updates, so it becomes a second, weaker kind of Bombadil.
  3. ca), plus a full Bombadil installed onto a USB drive you carry between computers, with undo and updates like any install.recommendedIt comes almost free with piece 1 (the start file every PC finds, and a start image that works on any hardware) and piece 3 (USB drives offered as targets).

3Who should be able to install it first?

  1. aPeople installing on a whole disk or a spare laptop; installing next to Windows comes after.recommendedIt proves the disk layout and the update path before BitLocker, Fast Startup and Windows' small start partition enter the picture.
  2. bWindows laptops first: installing next to Windows ships before any public download.
  3. cOnly you, until repair and next to Windows both exist.

The owner answered 1a 2c 3a on 30 Sep 2026.

Decisions I picked a default for

Each of these forks. The default is what gets built unless you pick another option.

How does a merge reach other people's machines?›

Default CI signs every merge that passes the VM smoke test and publishes it to a testing channel, which the VM that mirrors a real install follows; the stable channel takes it after 3 days with no revert. Nothing waits on you, as you asked for merges, and your daily use catches what the smoke test misses.

Other options every passing merge goes to everyone at once; your own key signs stable when you say “release”.

When is the time zone set, and is it asked?›

Default Detected, never asked. On the stick, when the network first comes up, one HTTPS geo-IP request with no model sets the zone, and timesyncd (now enabled on the stick) sets the clock, so even the stick's greeting can say “Good morning”. The card shows the zone as one line with “change” (“Europe/Lisbon, from your network · change”), because geo-IP guesses wrong in countries with several zones and behind VPNs.

The installer writes it and records timezone_source: detected, chosen (changed on the card or by “set my time zone to …”) or unset (the stick never went online; the line then reads “Set when this computer first goes online · change”). An installed machine still unset does the same lookup once at its first network. The voice build treats the zone as unset only when timezone_source is unset, which separates a person in UTC from an unset machine, and shows its “Set my time zone” chip only then.

Other options ask on the card, as Debian does; read Windows' registry, which BitLocker hides on most laptops; wait for the first installed start. The service is the builder's pick (unverified).

How does the system get onto the disk?›

Default The clean image as snapshot 1, the programs you installed on the stick replayed offline from its cache as snapshot 2, then the carry list. Two people who press the same button get the same system, and the stick's journal, keyring, root history and caches stay behind on purpose.

Other options today's cp -ax of the live root; pacstrap, which needs a network and differs from the tested image.

Is snapshot 1 kept for good?›

Default No, it ages out like any restore point; the recipe's baseline is the image version and package list in install.json, and the way back to stock is “Reinstall, keep my files”. A reset to a months-old base meets new keys and months of Arch news at once.

Other options create it with no cleanup algorithm (important=yes would not protect it: those fall under NUMBER_LIMIT_IMPORTANT).

Where does GRUB live?›

Default Core, modules, grub.cfg and grubenv on the ESP; kernels in @/boot. Modules never skew against the core after an undo, grubenv is where the decided layout puts it, and grub.cfg is read before the disk is unlocked, so a line can sit above the prompt (inferred).

Other options /boot/grub inside @, where an undone grub-install leaves old modules under a new core and GRUB stops before any menu.

Named firmware entry or fallback path?›

Default Both on a whole disk or USB drive, only the named entry on a Windows ESP. Firmware forgets NVRAM entries after updates or a flat battery, and every Bombadil VM boots with no stored variables.

Other options fallback only, as today (Windows can overwrite it); named entry only (breaks every VM).

Where is the password typed?›

Default Once, at GRUB's prompt, with a key file in the initramfs, because the kernel inside restore points means GRUB must unlock the disk.

Other options Plymouth with kernels on the ESP (rejected in the first brief); TPM (piece 12).

How many passwords, and whose account?›

Default One password for the disk, the account, the lock screen and the consoles, set even without encryption, because with passwordless sudo an empty password on tty2 is root for anyone at the keyboard. The account stays user (UID 1000): every path, unit and test uses /home/user, and your name lives in persona.toml. The agent's sudo stays passwordless.

Other options a separate disk passphrase; a login name typed on the card.

A recovery key?›

Default Yes, shown once as text and a QR code (its characters are meant for a US-layout prompt), replaceable with “new recovery key”. Otherwise a forgotten password, or GRUB rejecting a correct one, loses the disk.

Other options none.

The keyring?›

Default No keyring daemon; Chromium's basic store, protected at rest by the encrypted disk. greetd's autologin skips PAM auth, and with GRUB unlocking the disk pam_systemd_loadkey has no passphrase to reuse.

Other options gnome-keyring with an empty password; pam_fde_boot_pw from the AUR.

Keyboard, language and computer name?›

Default Keyboard and language from the stick's session; the name from the DMI model, with your name in front when the voice card has one (“alexs-thinkpad”), else “bombadil-” and four characters of the machine id, because a fixed “bombadil” collides on a shared network.

Other options always “bombadil”; ask.

The hardware clock?›

Default UTC on a whole disk, local time next to Windows, said on the card. Writing RealTimeIsUniversal into Windows' SYSTEM hive from Linux risks the one file Windows needs, and BitLocker usually hides it.

Other options UTC with the registry write; a command for you to run in Windows.

Swap?›

Default zram at min(RAM/2, 8 GiB), no hibernation. A swapfile inside @ blocks the snapshot before every turn; a top-level @swap can come later.

Other options @swap from day one.

Install before sign-in or offline, and can the agent do it?›

Default Yes, through the word “install” (a laptop whose Wi-Fi has no driver still needs a way in); the agent fills the card and you press the button.

Other options only after sign-in; the agent runs the installer when told.

How do existing installs reach the new layout and the package?›

Default One refresh, with a host snapshot first on the VM; hand changes to its root are listed in refresh-<date>.txt and kept aside 14 days.

Other options pacman --overwrite in place (a one-off script, and /etc/sudoers.d/bombadil would still conflict); a fresh reinstall, which loses the login because wsl-vm.sh deletes the disk.

Where do Bombadil's defaults live?›

Default /usr/share/bombadil, loaded by a short user file.

Other options /etc/xdg/hypr/hyprland.lua alone (one personal line forces a full copy); overwriting the user file each release.

The stick's boot menu?›

Default One entry plus “Safe graphics” on release ISOs, test entries only in test builds. What the stick keeps between restarts is question 2.

Other options today's three entries, one of which erases /dev/vda.

Secure Boot?›

Default Off, said on the download page with the BitLocker steps and the cost in Windows; Arch's ISO does not boot with it on, and CachyOS, EndeavourOS and Omarchy say the same.

Other options Fedora's signed shim from the AUR with a MOK screen; sbctl now.

Erase, and a new laptop?›

Default Erase from the stick (a second on an encrypted disk), and move through the copy drive plus the recipe, which also covers a dead SSD or a stolen laptop.

Other options cryptsetup erase on the running root (unverified); a laptop-to-laptop network transfer.

Cut, and why

Twelve things left out, each with its reason›
  • archinstall and Calamares. archinstall uses pacstrap (the install would no longer be the tested image) and the busybox encrypt hook, and cannot shrink Windows; Calamares is a large Qt application only in the AUR, with its own screens. We keep our script and borrow their patterns.
  • Limine, systemd-boot, UKIs, sdbootutil. GRUB was decided, and these copy kernels onto an ESP that Windows' 100 MiB cannot hold.
  • grub-btrfs snapshot entries. Its overlay hook does not work with the systemd initramfs; piece 8's rename matches how undo already works.
  • An rsync of the live root over the finished install (a draft's snapshot 2). It would delete fstab, crypttab, the key, the kernel and grub.cfg.
  • bombadil adopt with pacman --overwrite, and “reset to snapshot 1” without the stick. Existing installs move by refresh, and one way back to stock is enough.
  • Refresh as the way people take an update. Layout changes ship as numbered steps inside the update turn.
  • Persistence on the live stick. A second kind of Bombadil with no undo.
  • Manual partitioning, LVM, RAID, BIOS/CSM, another Linux beside it, OEM mode, ARM laptops and Macs. Rare on day one, and each doubles the tests.
  • A Windows entry in GRUB, writing Windows' registry, encrypting an install in place. BitLocker recovery, risk to the one file Windows needs, risk to someone's only copy.
  • Hibernation, snapper's hourly timeline, A/B roots, a Plymouth splash. Nobody asked; turn snapshots are the timeline; a read-only root fights the agent; GRUB's prompt comes before any splash.
  • NVIDIA installed on the stick itself. It blacklists nouveau and leaves older cards with no driver.
  • Our own stick writer, a username field, laptop-to-laptop transfer, TPM and shim now, and any model call on the path that erases a disk.
