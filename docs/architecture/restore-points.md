A restore point is a btrfs snapshot of the root subvolume that `agentd` takes through snapper before each turn runs. Saying `undo` makes the newest one the root again, and the swap applies at the next boot, not at once. This is what stands in for permission prompts: the agent has full access, and the person can go back.

## What is built and what is designed

On `main` (details under [How it works](#how-it-works) and in [the table of what the installed-OS design has built](#what-the-installed-os-design-has-built-and-what-is-still-designed)): one restore point of the root per turn, pruned to the newest 30 by snapper's number cleanup with no hourly points, the `undo` word and button, the `rollback` tool, `bombadil undo`, `bombadil snapshot`, `bombadil-rollback` with `--device` and `refresh`, and the installed layout the swap needs. Designed, not built ([known gaps](#known-gaps) and the table linked above say where each stands): the pair design with the last 100 changed pairs kept, pruning of `@.undone-*` and `@.before-refresh-*`, restore points of `/home` (its snapper config exists and nothing takes or undoes them), undo that applies at once, and the start that puts itself back.

## How it works

The person mostly sees "restore point" (`agentd` says "Saving a restore point"); the one line for a snapper failure says "undo point" (`agentd.py:2846`). The code, the snapper commands and the os-mcp tools say "snapshot". Other functions named `snapshot` (`Desk.snapshot`, `Jobs.snapshot`, `sysmap.snapshot`) return state tables and have nothing to do with this piece.

### What a restore point is

- One snapper snapshot in the snapper config `root`, made by `Snapshots.create` with `sudo snapper -c root --jsonout create --print-number --cleanup-algorithm number --description <text>` (`src/bombadil/snapshots.py:51-58`: the arguments are at 56-57, and the subprocess call is in `_snapper`, 47-49). It is taken before the turn, and none is taken after it. Every restore point made through `Snapshots.create`, the turn's, the one the agent's `snapshot` tool takes and the one `bombadil snapshot` takes, is therefore one that snapper's number cleanup may delete (see Retention and pruning).
- Its description is `turn:<n>: <first 60 characters of the prompt>`, for example `turn:4: install htop` (`src/bombadil/agentd.py:2844`). A `!` line keeps its `!`. `<n>` is `AgentD.turns`. At start it is the larger of the number of the last turn in `turns.jsonl` (older rows without a number count in order) and the number in the `turn` file of the state folder, which each turn writes before snapper runs (`agentd.py:400,2825-2827,3370-3417`). Numbers therefore go on across restarts and across an undo, also past a turn that was cut off before it wrote its row. Undo never reads `<n>`: it uses snapper's own number and the `turn:` prefix.
- It is taken after `turn_start` has gone out and the number is taken, and before the provider CLI starts, for every turn that gets that far: model turns and `!` lines alike (`agentd.py:2815-2848`). The line above the pill says "Saving a restore point" while snapper works, and "Waiting for Claude" (or Codex) once the CLI is up (`agentd.py:2842,2906`).
- Its number goes out as a `snapshot` event, into the turn's row in `turns.jsonl` as `snapshot`, and into the CLI's environment as `BOMBADIL_TURN_SNAPSHOT` (`agentd.py:2848,2882-2885,3163`).

The rest of the turn is in [agentd.md](agentd.md#one-turn); this page covers the restore point step and what follows from it.

### When a turn gets no restore point

| Case | What happens | Where |
|---|---|---|
| `snapper` is not on `PATH`, or `/etc/snapper/configs/root` is missing: the live ISO (snapper is in the image, no config exists), a development machine, the tests | `Snapshots.available` is false, the turn skips the step, and `undo` says so | `snapshots.py:42-45`, `iso/packages.x86_64:14` |
| `snapshots = false` in the config (read by `agentd` only) | `agentd` builds `_NoSnapshots`, with `available = False`; the os-mcp tools and `bombadil undo` still work (see known gaps) | `agentd.py:3492,3526-3527` |
| A model turn whose provider CLI is not installed | the turn ends with an `error` event before this step, and takes no number | `agentd.py:2819-2824` |
| `snapper` exits non-zero | an `error` event, "no undo point for this turn: snapper failed (...)", and the turn runs without one | `agentd.py:2844-2846` |
| Any other failure inside `create` (no `sudo`, output that is not a number) | the exception reaches `_worker`, which ends the turn with an `error` event; the number was taken, so it is not reused | `agentd.py:2760-2762` |
| A launcher word or another local action (`open`, `stop`, `undo`, `restart`, a picture) | not a turn, so no restore point | `agentd.py:672-701` |
| The AI cannot be asked: `access` is anything but `ready`, for example signed out, offline, or resting (the account's limit used up, or paused by hand) | a prompt that needs the model waits in the queue and no turn starts; a `!` line still runs, with its restore point | `agentd.py:2721-2731`; `tests/test_agentd_rest.py`, `test_a_typed_command_and_launcher_words_still_work_while_it_rests` |

Other moments make a restore point with another description:

| Moment | Description | Reached by `undo` | Pruned |
|---|---|---|---|
| The agent's `snapshot` tool | whatever the agent passes | only if it starts with `turn:` | yes |
| `bombadil snapshot [WORDS]` in a terminal | `turn: <words>`, or `turn: by hand` with no words; it prints `restore point <n>` | yes | yes |
| `bombadil snapshot --hook`, the hook of a remote-control session | `turn: remote: <the first 60 characters of the prompt>` (`snapshots.label_from_hook`), or `turn: remote` when the prompt cannot be read | yes | yes |
| The installer, when it has finished | `Bombadil <version>, as installed`, and after it, when programs from the USB stick were brought, `Brought from the USB stick: <up to five names>` | no, there is no `turn:` | no, no cleanup algorithm |
| A package update the agent runs (`sudo pacman -Syu`, which brings a newer `bombadil` too) | none of its own: pacman takes no restore point, and the restore point of the turn the update runs in covers it; one run by hand is covered by nothing ([Installed OS](installed-os.md#building-a-package-and-serving-an-update)) | with the turn | with the turn |

`bombadil snapshot` clears the undo marker first, as a turn from the pill does, so that "undo" in the pill takes this turn back and does not skip it (`bin/bombadil:466-483`; a pending marker is kept, see below). It never fails: with no snapper it prints nothing, and on an error it prints one line to standard error (`no restore point: ...`, or `undo marker: ...` when the marker could not be cleared), and the exit status is 0 in every case, because a non-zero hook would stop the prompt it is taken for (`tests/test_remote.py`: `test_taking_a_restore_point_by_hand_never_fails_the_prompt_it_is_a_hook_for`). The hook is in the settings of the folder that `bombadil remote` makes (`remote.FOLDER_SETTINGS`, `remote.py:81-84`, with no permission questions), so every prompt typed from the other device takes a restore point and `undo` in the pill takes back what a remote session did. The sentence for such a point reads `before “remote: <prompt>”`, because the launcher cuts only the first `turn:` (`_snapshot_prompt`, `launcher.py:533-537`). The two the installer takes are never reached by the `undo` word and stay for good. The first is the one to go back to, by its number (`sudo snapper -c root list` shows it), to get the system as it was installed.

### Undo, step by step

1. The person types `undo`, `undo that`, `undo it` or `undo the last change` (`launcher.py:52`), or clicks `Undo` on the closing line, which sends `{"type": "local", "action": "undo"}` (`shell/PillState.qml:932-935`, `agentd.py:734-737`). A typed line goes through `launcher.match` (`agentd.py:672-701`). It is lowercased, trimmed of `. ! ? , ; :` at both ends, and stripped of spaces, hyphens and underscores, so it must equal one of the four words, in ASCII only (`launcher.normalize`, `_key`, `_lookup`; `undo-that` and `undo_it` match too). A question mark does not stop it: `undo?` runs undo, because only `restart`, `shutdown`, `desk` and `widgets` are sent to the agent when the line ends in `?` (`launcher.py:406`). A leading `!` makes it a shell line. No model is involved. A longer sentence such as "undo the docker install" goes to the agent (`tests/test_launcher.py:83`).
2. `AgentD.local` raises `_hold` so no queued turn starts, takes the `_exclusive` lock and, if a turn is running, stops it and waits until it is gone. The running turn is therefore taken back too, and its restore point is the newest one (`agentd.py:1824-1838`, `test_undo_during_a_turn_takes_back_that_turn_even_with_one_queued`).
3. `Launcher._undo` refuses when `available` is false, reads the marker `undo.json`, lists up to 200 restore points and picks the newest one whose description starts with `turn:` and whose number is below the marker's (`launcher.py:907-937`).
4. `Snapshots.rollback` runs `sudo bombadil-rollback <number>`. Its output is captured because, inside os-mcp, stdout is the JSON-RPC stream (`snapshots.py:68-78`).
5. `bombadil-rollback` mounts the btrfs top level (`subvolid=5`) of the device `/` is on, or of the one `--device` names, on a temporary directory. It refuses and changes nothing when `@snapshots/<n>/snapshot` does not exist (`no snapshot <n>`, exit 1), and when the current `@` has a kernel of its own in `/boot` and the restore point has none (`restore point <n> has no kernel of its own and cannot start`, exit 1; `bombadil-rollback:56-62`). Otherwise it makes a `btrfs subvolume snapshot` of the restore point beside `@` as `@.new-<YYYYmmdd-HHMMSS>` (without `-r`, so the root is writable; if this fails, `@` is as it was) and swaps it in under the name `@`, keeping what was there as `@.undone-<YYYYmmdd-HHMMSS>` (`swap_in`, `bombadil-rollback:30-37,63-67`). The swap is one `mv --exchange` where the system has it, so there is no moment with no `@`; where it does not, it is two renames. It unmounts on exit.
6. `Launcher._undo` writes `undo.json` and returns the sentence for the pill. `agentd` broadcasts `local` events, appends the action to `turns.jsonl` (`kind: "local"`) and tells the next model turn what happened without it (`agentd.py:1841-1868,2865-2869`).
7. The root is mounted by subvolume name, not by id, so that a snapshot swapped in under the name `@` is the one found: `write_fstab` gives `/` the options `subvol=@,compress=zstd` and says in its comment that undo swaps a snapshot in under that name (`bombadil-install:461-474`), and `verify` refuses an install whose `grub.cfg` has no `rootflags=subvol=@` or whose default subvolume is not the top level (`bombadil-install:800-809`). Nothing restarts by itself: the person says `restart`, which runs `systemctl reboot` (`launcher.py:1129-1130`).

**When it applies:** on the next boot, never at once. The docstring (`snapshots.py:69`), the script (`bombadil-rollback:2,67`), the sentence the pill shows and the VM check below all say so. The mechanism is inferred, not shown by a file in the repository: a mount stays bound to its subvolume when the subvolume is renamed or exchanged, so the running kernel keeps the replaced `@` until the next boot. What the next boot reads is checked as text by the installer's `verify`: the `grub.cfg` must start the system with `rootflags=subvol=@` and read the kernel and the initramfs from `/@/boot` (`bombadil-install:800-809`). `grub.cfg` itself comes from `grub-mkconfig`, run through `bombadil-grub-config` (`bombadil-grub-config:13`), and no generated file is in the tree. The kernel is in the restore point, so the next boot starts the kernel that goes with the restore point's modules. The effect is recorded: the VM run in Tests booted into the swapped-in `@` (`undo-applied`).

**Between the undo and the restart.** The running root still holds what was undone, so a restore point taken before the restart would bring it back. `undo.json` records the boot id (`/proc/sys/kernel/random/boot_id`), and while it matches, the undo is pending (`launcher.py:851-888,1177-1181`):

- a turn does not clear the marker (`Launcher.clear_undo`, called from `AgentD.turn`, skips a pending one);
- an `undo` says "Already undone" and rolls nothing back when a `turn:` restore point numbered above the marker's is newer than the marker's `covered` (`launcher.py:915-924`). A turn that ran since counts, because the restart takes it back too; so do the restore points of turns an earlier undo already took back, because undo removes none. Every rollback writes a new marker without `covered`. Repeated undos with no turn between therefore alternate: the first two each go one turn further back, then "Already undone", one further back, "Already undone", and so on (see known gaps);
- after the restart the marker is no longer pending. Each further `undo` goes one turn further back, until a turn runs and `clear_undo` removes the marker.

**A turn the limit refused before it changed anything.** `AgentD.turn` reads the marker with `Launcher.undo_marker` before `clear_undo` removes it (`agentd.py:2836-2839`). When the account's limit ends the turn and no step of it changed anything, the turn's restore point is empty, and `Launcher.skip_restore_point` is called with its number and the marker that was read (`agentd.py:3023-3024`, `launcher.py:890-905`):

- with a marker: it is written back, so the next `undo` goes on from where it was. A marker still pending gets `covered` raised to the empty point, so that point does not count as a turn since, and no "Already undone" is said for it;
- with no marker: one is written for the empty point itself (`what` empty, `boot` null, so not pending), and the next `undo` starts below it.

The point stays in snapper. A turn that was not stopped goes back to the front of the queue and runs again when the limit lifts, as a turn of its own with its own number and restore point (`agentd.py:2496-2518`). A turn the limit stopped after it changed something keeps its restore point as the one `undo` takes back. Only the launcher words skip the empty point (see known gaps). The resting state itself is in [the poor man switch](poor-man-switch.md).

**The ways in are not equal.**

| Way in | Path | Writes `undo.json` | A repeat |
|---|---|---|---|
| The four words typed in the pill or sent with `bombadil ask undo` (`bin/bombadil:420-421`: the line goes through `launcher.match` like a typed one), or the Undo button | `AgentD.local`, `Launcher._undo` | yes | before the restart, they alternate between one turn further back and "Already undone", as above; after it, one turn further back each time |
| Any other sentence that means undo | the agent calls `rollback` with no number (its system prompt says to): `Snapshots.undo_last_turn`, which skips the running turn's own restore point (`BOMBADIL_TURN_SNAPSHOT`) | no | each asking is a turn with a restore point of its own, which the next asking picks: see known gaps |
| `bombadil undo` in a terminal (not `bombadil ask undo`, which is the row above) | `bin/bombadil:442-445`, `Snapshots.undo_last_turn` | no | the same restore point each time, until a turn runs and its restore point is the newest |
| `rollback` with a `number`, or `sudo bombadil-rollback N` | any snapshot by number | no | not applicable |

The by-hand path needs no model, no network, and neither `agentd` nor the shell, so it works from a terminal (reaching one from a text console was not checked):

```sh
sudo snapper -c root list        # numbers and descriptions: what Snapshots.list reads
sudo bombadil-rollback 12        # restore point 12 is the root from the next boot
```

From the USB stick, for a system that no longer starts, `sudo bombadil-rollback --device DEV 12` does the same to the btrfs device `DEV` (already unlocked with `cryptsetup open` if the disk is encrypted); without `--device` it reads the device `/` is on (`bombadil-rollback:6-9,19`). A number that is not a restore point is refused, and so is one that has no kernel when the root has one (step 5).

`bombadil-rollback` keeps the replaced root as `@.undone-<time>` at the btrfs top level, so, in its own words, an undo can itself be undone by hand. No command in the repository does that.

### Undoing a refresh

A refresh (`bombadil-install --refresh`) puts the old system aside before it copies the new one in, and `bombadil-rollback refresh` puts it back. The refresh renames `@` to `@.before-refresh-<stamp>` and `@snapshots` to `@snapshots.@.before-refresh-<stamp>`, then makes a new `@` and a new, empty `@snapshots` (`refresh_aside`, `bombadil-install:320-367`). `@home`, `@log` and `@pkg` stay where they are. So the refreshed system starts with no restore points of its own but the baseline it takes at the end, and `undo` never reaches the turns of the old system: they are in the old `@snapshots`, aside, and the installer deletes the old `undo.json`, whose number means nothing now (`carry`, `bombadil-install:656-679`).

`sudo bombadil-rollback [--device DEV] refresh` swaps the newest whole system that a refresh put aside back in as `@`, and its restore points back in as `@snapshots`; the refreshed system and its restore points are kept as `@.after-refresh-<stamp>` and `@snapshots.after-refresh-<stamp>` (`bombadil-rollback:39-54`). A system counts as whole when it has `etc/fstab` and `usr/lib/modules` and no `var/lib/bombadil/install-incomplete`, the marker a refresh writes into a system it has not finished (a refresh that stopped part way leaves a half-made one, which is never chosen). It refuses, with exit 1, when there is none, or when the old system has no kernel in its `/boot`. A refresh of a disk from before layout 1 copies the kernel from the EFI partition into the old system's `/boot` first, and points the old `fstab` at `/efi`, so that the old system can start from the new GRUB. Like an undo, it applies at the next boot, and the words `undo` and `bombadil undo` do not do it. It is a command for the stick or the terminal, and the guided installer tells the person the old system is kept for 14 days (see known gaps).

This is the layout `bombadil-install` writes (layout 1, `bombadil-install:13-19`, `partition` at 193-205, `make_filesystem` at 240-249, `write_fstab` at 462-474): a 1 GiB EFI partition at `/efi`, and a second partition that is btrfs, inside LUKS2 when the install was given a password, with `@`, `@home`, `@snapshots`, `@log` and `@pkg` at the top level. `@` is mounted at `/`, and the kernel and the initramfs are in its own `/boot`, with no `/boot` mount of their own. GRUB is on the EFI partition and reads the kernel from `/@/boot`. `snapper -c root` is created on `/`, with the `@snapshots` subvolume mounted at `/.snapshots` in place of snapper's own and a limit of 30 numbered restore points (see Retention and pruning). `@log` and `@pkg` sit beside `@` because undo swaps `@` for a snapshot: the logs and the package cache are the same before and after.

| Where | In a restore point | What it means |
|---|---|---|
| `/etc`, `/usr`, `/var` (the pacman database, systemd units, state), `/opt`, `/root` | yes | an undo takes back installs, config edits and services |
| `/boot`: the kernel, `initramfs-linux.img` and the fallback image | yes | they are in `@`, put there by the installer, which takes the kernel of the system it copies (the newest `/usr/lib/modules/*/vmlinuz` by version, never one from the boot medium; `bombadil-install:132-137,444`) and makes the initramfs with a preset that names `/boot` (`write_initramfs_config`, `bombadil-install:476-504`, pinned by `test_the_kernel_and_initramfs_are_made_in_the_roots_own_boot_folder`). A restore point holds the kernel with its modules, so an undo after a kernel update does not pair a newer kernel with older modules. That a later `pacman` upgrade writes its new kernel to the same `/boot` is mkinitcpio's behaviour and is not shown by a file here |
| `/var/log` (`@log`) and `/var/cache/pacman/pkg` (`@pkg`) | no | the journal and the downloaded packages survive an undo, and an undo does not take back what the logs recorded |
| `/home` (`@home`): `~/Apps`, `~/.config/bombadil`, the sign-ins copied by the installer (`.claude`, `.claude.json`, `.codex`) | no | an undo never deletes the person's files, apps or sign-in, and never brings back a file deleted from home. Inside `@home` the installer makes nested subvolumes for what a restore point of the home folder must skip (`HOME_SUBVOLS`: `.cache`, `.local/state/bombadil`, `.claude`, `.codex`, `.local/share/claude`, `.config/chromium`, `.local/share/bombadil/browser`, `Projects`; `bombadil-install:44-45`, `prepare_home` at 646-654). No restore point of `/home` is taken, so they change nothing for undo |
| `~/.local/state/bombadil`: `undo.json`, `turns.jsonl`, `turn`, `turns/`, `desk.toml`, `brain.db`, `rest.json`, `mail.db` | no | it is home, so the marker, the logs, the desk, the brain's index, a pause or limit of the AI (`src/bombadil/rest.py:71`) and the mail service's notes (drafts, marks, receipts) survive the swap |

| `/.snapshots` | not part of itself | restore points survive an undo, including those newer than the one chosen |

### Retention and pruning

On `main`, restore points are pruned to the newest 30, and no hourly points are made.

- **Each point is marked for pruning.** `Snapshots.create` passes `--cleanup-algorithm number` (`snapshots.py:56-57`), so a restore point is one of snapper's numbered snapshots. Snapper's other algorithms (`timeline`, `empty-pre-post`) are named per snapshot too ([snapper manual](http://snapper.io/manpages/snapper.html)); no restore point is made under them.
- **The installer sets the limit and turns the timer on.** `snapper_setup` runs in a chroot of the new system: `snapper --no-dbus -c root create-config /`, then `snapper --no-dbus -c root set-config TIMELINE_CREATE=no NUMBER_CLEANUP=yes NUMBER_LIMIT=30` (`bombadil-install:687,691`), and `configure` runs `systemctl enable ... snapper-cleanup.timer` (`bombadil-install:594`). `TIMELINE_CREATE=no` turns the hourly points off: the turn's restore points are the timeline. A refresh runs both steps again on its new root (`bombadil-install:1073-1076`), so a refreshed machine has the limit and the timer. The same step makes a snapper config `home` with the same three values (`bombadil-install:692-699`); no code takes a restore point of the home folder, so the config only waits.
- **The timer enforces the limit, not the creation.** `create` deletes nothing; snapper's cleanup runs when `snapper-cleanup.timer` fires, so more than 30 can exist between two runs. The smoke checks that a restore point shows `"cleanup": "number"` in `snapper list` (`snapshot-is-prunable`), and that the config holds `NUMBER_LIMIT="30"` and `TIMELINE_CREATE="no"` with the timer enabled (`snapshots-are-pruned`, `bombadil-smoke:949-950`); the layout checks add that both configs exist and that `root` has the limit 30 (`layout-snapper`, `bombadil-smoke:894`). It does not wait for a cleanup to delete anything. The snapper manual also describes a minimum age (`NUMBER_MIN_AGE`) that spares young snapshots from the number cleanup; the installer leaves it at the template's value, and this was not checked on a machine.

Not pruned:

- `@.undone-<time>`, one per undo (`bombadil-rollback:66-67`), is removed by nothing.
- `@.before-refresh-<stamp>` and its `@snapshots.@.before-refresh-<stamp>`, one pair per refresh (`bombadil-install:320-367`), and the `@.after-refresh-<stamp>` pair that `bombadil-rollback refresh` leaves, are removed by nothing. The guided refresh tells the person the old system is kept for 14 days (`bombadil-install:1009`); no code deletes it after that or after any other time.
- A restore point made with no cleanup algorithm stays for good: the two the installer takes (`bombadil-install:705-707`, called at 736 and 1067), or one made by hand with `snapper create`.
- A machine that is updated and not refreshed keeps the config it was installed with. An installer from before the limit enabled only `greetd` and `NetworkManager`, so nothing in the repository runs the cleanup there, and none of the package's migrate steps runs `set-config`. A refresh is what applies the settings to such a machine, because it makes a new root with a new config; by hand it takes `sudo snapper -c root set-config ...` and `systemctl enable --now snapper-cleanup.timer`.

What undo can reach is bounded by what snapper keeps, about the newest 30 numbered restore points on an installed machine (the two the installer takes are outside the count), and then by the readers. The launcher looks at up to 200 (`launcher.py:914`), so on an installed machine it is never the limit. `undo_last_turn` (the agent's `rollback` with no number and `bombadil undo`) and `list_snapshots` read the newest 20 (`snapshots.py:60,87`), so they see 20 of the 30.

Designed, not on `main`: the fuller design is a pre and post pair for every turn, pairs with no change dropped at the end of the turn, the last 100 changed pairs kept instead of 30 restore points, and `@.undone-*` and `@.before-refresh-*` pruned (the installed OS brief says by a daily timer, older than 14 days). See [the UX brief's decisions](../design/ux-brief.md#decisions-i-picked-a-default-for) and [the installed OS brief](../design/installed-os-brief.md#after-these-in-order). What is on `main` of it is in [the roadmap](../roadmap.md).

## Principles it keeps

- [Full access, with undo instead of guard rails](../principles.md#full-access-with-undo): every turn that reaches the restore point step on a system with snapper and its `root` config gets one, so nothing in front of the agent asks permission. A snapper failure lets the turn run without one and shows an `error` event. The trap: adding a confirmation before something undo could reverse, or adding a way to change the root outside `AgentD.turn`, which takes no restore point. The other trap is claiming more than undo does: it covers the root only, and only as far back as snapper keeps, which is about the newest 30 restore points.
- [Recovery never goes through the part that broke](../principles.md#recovery-without-the-broken-part): `undo` is a launcher word that `agentd` answers without the model, and `bombadil undo` and `sudo bombadil-rollback` need neither `agentd` nor the shell, and `bombadil-rollback --device` needs not even the installed system, only the btrfs device. The trap: sending undo through the agent. An undo run by the agent is itself a turn with a restore point of its own, and rolling back to that one does nothing; `BOMBADIL_TURN_SNAPSHOT` and the `before` argument of `undo_last_turn` make it skip that one.
- [Records answer before models, and the machine explains itself](../principles.md#records-before-models): the undo sentence is built from the restore point's description and the marker. The trap: letting a model word it, or putting something in a restore point description that is not the person's own prompt.
- [Every piece degrades, and nothing waits on a model it does not need](../principles.md#degrade-and-recover): without snapper or its config every method is a no-op that reports `available = False`, and a snapper failure is an `error` event, not a lost turn. The trap: raising anything other than `subprocess.CalledProcessError` from `create` (the turn ends), or calling snapper on the event loop (it can take a second).
- [Plain files stay the truth](../principles.md#plain-files-stay-the-truth): the marker, the turn number and the turn log are small files in `~/.local/state/bombadil`, outside every restore point so they survive the swap. The trap: putting state that must outlive an undo under `/etc` or `/var`, where undo takes it back; `src/bombadil/desk.py` documents the same rule for `desk.toml`. A second trap is changing how turns are numbered: the number in `turn:<n>` is shared with the brain's turn keys, so it must stay unique across crashes and restarts.

## Extending it

### Change the retention limit

Pruning is already on `main` (see Retention and pruning); these steps change it.

1. The limit is the installer's. Edit `NUMBER_LIMIT=30` in the `set-config` line (`bombadil-install:691`), and the matching lines in `tests/test_iso_profile.py` (`test_the_installed_system_prunes_its_restore_points_and_takes_no_hourly_ones`) and in the smoke check `snapshots-are-pruned` (`bombadil-smoke:950`, which looks for `NUMBER_LIMIT="30"`). Keep the `set-config` after `create-config` and keep `systemctl enable ... snapper-cleanup.timer` (`bombadil-install:594`): without the timer nothing runs the cleanup. The `home` config has its own copy of the line (`bombadil-install:699`); change it too, or leave it, since nothing takes restore points of home. The installed OS brief cuts the hourly timeline on purpose, so leave `TIMELINE_CREATE=no`.
2. A machine that is already installed keeps its config until it is refreshed, because a refresh runs `snapper_setup` on its new root and none of the package's migrate steps runs `set-config`. By hand it takes `sudo snapper -c root set-config NUMBER_LIMIT=<n>`; for every machine without a refresh it needs a migrate step that runs `set-config` (the three steps there are `001-pacman-repo.sh`, `002-os-release-logo.sh` and `003-browser-env.sh`; [Installed OS](installed-os.md#the-three-ways-a-file-changes)).
3. Keep the readers in line with the limit: the launcher reads up to 200 restore points (`launcher.py:914`), the agent's `rollback` and `list_snapshots` and `bombadil undo` the newest 20 (`snapshots.py:60,87`). A limit above 20 is out of their reach.
