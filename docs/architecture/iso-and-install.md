## How it works

### From the repository to an installed machine

```mermaid
flowchart TB
    subgraph build["Build"]
        A["build-in-container.sh or build-iso.sh"] --> B["profile: iso/ plus the tree plus the CLIs"]
        B --> C["mkarchiso"]
        C --> D["out/*.iso"]
    end
    subgraph live["Live boot"]
        E["systemd-boot, 1 entry (5 in a test build)"] --> F["archiso initramfs: erofs plus RAM overlay"]
        F --> G["pacman-init, bombadil-live, NetworkManager, brain watcher, connection service"]
        G --> H["greetd autologin: start-hyprland as user, logged to the journal"]
        H --> I["hyprland.start: import the session environment, restart the agentd and bar units, start a foot server, restart the mail and browser units"]
    end
    subgraph inst["Installed boot"]
        J["GRUB from the EFI partition, menu hidden, the password first on an encrypted disk"] --> K["greetd autologin, then hyprland.start"]
    end
    D --> E
    I -->|"sudo bombadil-install"| J
```

| Stage | What happens | Section below |
|---|---|---|
| Build | The profile is assembled in a work directory and `mkarchiso` writes one ISO to `out/`. | The build |
| Live boot | UEFI firmware starts systemd-boot, archiso mounts the image with a RAM overlay, systemd creates the session user, greetd logs it in, and Hyprland's start hook restarts the user units that run `agentd` and the bar. Nothing on the live system survives power-off. | Boot flow |
| Quiet start | From the boot loader to the desk the console is set to print nothing and to use the desk's ground colour. | Boot and the console |
| First run | With no provider chosen, `agentd` asks in the pill which AI to use and signs in through the browser panel. When the sign-in turns ready and there is no `persona.toml`, the pill then asks for a name and a voice. | Boot flow |
| Install | `bombadil-install` asks which disk (or reads a plan, or takes a disk name), erases it, copies the system image onto btrfs, inside LUKS2 when there is a password, brings what `install/carry.list` names from the live home, and installs GRUB. `--refresh` replaces the system on a disk that has Bombadil and keeps its home folder. | What `bombadil-install` does |
| Installed boot | GRUB boots straight in (an encrypted disk asks for its password there, once), greetd logs `user` in, and the same Hyprland session starts. | Boot flow |

### The build

`scripts/build-iso.sh` reads `WORK` (default `/tmp/bombadil-work`) and `OUT` (default `out/` in the repository root) and does these things.

| Step | What | Where |
|---|---|---|
| 1 | Deletes and recreates `$WORK/profile`, then copies `iso/` into it with `cp -a`. | `scripts/build-iso.sh:8-10` |
| 2 | Copies `bin`, `src`, `shell`, `share`, `install` and `iso/packages.x86_64` into `airootfs/usr/share/bombadil/` of the profile: the whole tree, so the live system and the installer both have it. `install/` holds `carry.list`, the home paths the installer brings along. | `scripts/build-iso.sh:11-14` |
| 3 | Writes `VERSION` into that folder: the date (from `SOURCE_DATE_EPOCH`, else the current time) and the short commit (from `BOMBADIL_COMMIT`, which `scripts/build-in-container.sh` passes because the container cannot read the checkout, else `git rev-parse`, else `unknown`). The installer records it and names the first restore point after it. | `scripts/build-iso.sh:15-18` |
| 4 | Unless `BOMBADIL_TEST_ENTRIES` is set, deletes the boot entries `02` to `09` from the profile (`rm -f .../0[2-9]-*.conf`), so a release has the one entry that boots, and the entries that run the VM tests are only in builds made for them. | `scripts/build-iso.sh:19-23` |
| 5 | Links `agentd`, `bombadil`, `bombadil-app`, `bombadil-browser`, `bombadil-os-mcp`, `bombadil-shell`, `bombadil-signal`, `bombadil-brain`, `bombadil-brain-watch`, `bombadil-mail`, `bombadil-mail-host`, `bombadil-connect` and `bombadil-browserd` in `airootfs/usr/local/bin` to `/usr/share/bombadil/bin/<name>`. The five scripts `bombadil-setup`, `-install`, `-smoke`, `-rollback` and `-grub-config` are real files in `iso/airootfs/usr/local/bin`. | `scripts/build-iso.sh:24-27` |
| 6 | Unless `BOMBADIL_NO_CLIS` is set, runs `npm install -g --no-fund --no-audit --allow-scripts=@anthropic-ai/claude-code --prefix <profile>/airootfs/usr @anthropic-ai/claude-code @openai/codex`, so both CLIs are in the image and first run only has to sign in. The line sets `--allow-scripts` for `@anthropic-ai/claude-code` only. | `scripts/build-iso.sh:28-32` |
| 7 | Runs `mkarchiso -v -w $WORK/build -o $OUT <profile>`. | `scripts/build-iso.sh:33` |
| 8 | Reads the image back (`verify_image`): takes `airootfs.erofs` out of the newest ISO with `xorriso`, mounts it read-only and compares it with the tree `mkarchiso` built from (`diff -rq`), and stops with an error when a file differs. It runs only as root, with `xorriso` and that tree there, and prints a `Note:` line saying the image was not read back when it cannot. | `scripts/build-iso.sh:35-56` |

`scripts/build-in-container.sh` runs that script inside an `archlinux:base` container (`docker`, else `podman`; `CONTAINER_RUNTIME` and `BOMBADIL_BUILD_IMAGE` override). The container is `--privileged`, mounts the repository at `/src`, installs `archiso git nodejs npm`, and builds with `WORK=/tmp/bombadil-work OUT=/src/out`. It passes the proxy variables, host networking when `BOMBADIL_HOST_NET` is set, and a pacman cache when `PACMAN_CACHE` names a directory. It also passes `BOMBADIL_COMMIT` (the checkout's short commit, `unknown` when git cannot answer) and, when set, `BOMBADIL_TEST_ENTRIES` (`scripts/build-in-container.sh:18-20`). An `SSL_CERT_FILE` is mounted into the container and also set there as `CURL_CA_BUNDLE` and `NODE_EXTRA_CA_CERTS`. `SOURCE_DATE_EPOCH` defaults to the time of the last commit (the current time when git cannot answer), so the ISO's label and version carry the commit's date.

`iso/profiledef.sh` is the archiso profile definition.

| Setting | Value |
|---|---|
| `iso_name`, `iso_publisher`, `iso_application` | `bombadil`, `Bombadil`, `Bombadil live` |
| `iso_label`, `iso_version` | `BOMBADIL_<YYYYMM>` and `<YYYY.MM.DD>`, both from `SOURCE_DATE_EPOCH` or the current time |
| `bootmodes` | `uefi-x64.systemd-boot.esp` and `uefi-x64.systemd-boot.eltorito`: x86_64 UEFI only, no BIOS boot |
| `install_dir`, `arch` | `arch`, `x86_64` |
| `airootfs_image_type`, `airootfs_image_tool_options` | `erofs`, with `-zlzma,109` and no `-E ztailpacking`: the comment at `iso/profiledef.sh:14-15` says erofs-utils 1.9.4 wrote zeros over the last block of some incompressible files with it, kernel modules among them, and nothing complained until a driver failed to load. The build reads the image back and the installer reads every kernel module back for the same reason |
| `pacman_conf` | `pacman.conf`: the configuration `mkarchiso` installs the packages with. It enables `core` and `extra` only, with `SigLevel = Required DatabaseOptional`. |
| `file_permissions` | `/etc/shadow` 0400, `/etc/sudoers.d/bombadil` 0440, the five scripts in `/usr/local/bin` (`bombadil-setup`, `-install`, `-smoke`, `-rollback` and `-grub-config`) and `/etc/grub.d/000_bombadil_screen` 0755 (`iso/profiledef.sh:20-25`), and the directories `/usr/share/bombadil/bin/`, `/usr/lib/node_modules/@anthropic-ai/` and `/usr/lib/node_modules/@openai/` 0755. The comment at `iso/profiledef.sh:26` gives the reason: `mkarchiso` copies airootfs without modes, so everything that runs must be listed. `tests/test_iso_profile.py` holds every file the overlay puts in `usr/local/bin` or `etc/grub.d` to a 0755 line here |

### Boot flow

Some statements here and below describe what an upstream tool does, which no file in this repository shows: the `archiso` hook finding the medium, mounting the erofs image and adding the RAM overlay (live row 2); `mkarchiso` replacing `%INSTALL_DIR%` and `%ARCHISO_UUID%` in the boot entries (the boot menu below); `start-hyprland` coming with the `hyprland` package (live row 5); the user's systemd manager starting a unit that has a link in `default.target.wants/` (live row 6); systemd reading `StartLimitIntervalSec` from `[Unit]` and ignoring it under `[Service]` (the session's services section above); `systemd-sysusers` making the connection service's account from `usr/lib/sysusers.d/bombadil-connect.conf` at boot, and systemd applying the `[Service]` keys of that unit, which the smoke reads back with `systemctl show` (the connections section above); systemd matching `ConditionKernelCommandLine=bombadil.smoke` also against `bombadil.smoke=` with a value (`install`, `install-encrypted`, `refresh`, `undo` and `refreshed`; live row 8); `grub-install --bootloader-id=Bombadil` making a firmware boot entry and `--removable` writing `EFI/BOOT/BOOTX64.EFI` (installed row 1); what GRUB, `cryptsetup`, `systemd-cryptenroll` and the `sd-encrypt` hook do with an encrypted disk (installed rows 1 and 3, and [Installed OS](installed-os.md#how-the-disk-is-opened) for the account of it); the kernel line that `grub-mkconfig` writes, its reading of the drop-ins in `/etc/default/grub.d/`, and Arch's own `GRUB_CMDLINE_LINUX_DEFAULT`, which only the test's copy of Arch's defaults shows (`loglevel=3 quiet`, installed row 3); Thunderbird reading the policy file from `/etc/thunderbird/policies/` (the mail section); Claude Code reading `/etc/claude-code/managed-settings.d/*.json`, Codex reading `/etc/codex/config.toml` and `/etc/codex/requirements.toml` and running a hook set there with no trust prompt (the comment in `requirements.toml` says so), `footclient` coming with the `foot` package, `zellij` doing what `share/zellij/config.kdl` asks of it, and systemd honouring a `/var/lib/systemd/linger/user` that the installer made by hand (the coding sessions section; installed row 4); systemd-boot drawing a text menu and printing `Boot in` on the serial console (the boot menu below); what each kernel parameter does in the kernel, and where GRUB's `Loading` lines come from and that no setting hides them (the console section).

### The boot menu

A release ISO's systemd-boot menu has one entry, `01-bombadil.conf`. A build made with `BOMBADIL_TEST_ENTRIES=1` has four more, `02` to `05`; without it `scripts/build-iso.sh` deletes `0[2-9]-*.conf` from the profile (`scripts/build-iso.sh:19-23`). Every entry carries `archisobasedir=%INSTALL_DIR% archisosearchuuid=%ARCHISO_UUID% cow_spacesize=2G`; `mkarchiso` fills in the two placeholders.

| Entry file | Menu title | Extra kernel arguments | What it does |
|---|---|---|---|
| `01-bombadil.conf` | `Bombadil` | the nine quiet-console parameters ([the console](#boot-and-the-console-from-power-on-to-the-desk)) | The normal live boot, selected after three seconds, with a quiet console. |
| `02-bombadil-serial.conf` | `Bombadil (serial console, smoke test)` | `console=tty0 console=ttyS0,115200 bombadil.smoke` | A live boot with the console on the screen and on the serial port, running the live smoke mode, then powering off. |
| `03-bombadil-install-test.conf` | `Bombadil (serial console, smoke test and install to /dev/vda)` | `console=tty0 console=ttyS0,115200 bombadil.smoke=install` | The live smoke mode, then `bombadil-install /dev/vda --yes`, then power off. |
| `04-bombadil-install-encrypted-test.conf` | `Bombadil (smoke test: install to /dev/vda with a password)` | `console=tty0 console=ttyS0,115200 bombadil.smoke=install-encrypted` | The common checks, then `bombadil-install --plan` on `/dev/vda` with a fixed test password on a file descriptor, then power off. The host types the password at GRUB on the next start. |
| `05-bombadil-refresh-test.conf` | `Bombadil (smoke test: refresh the Bombadil on /dev/vda)` | `console=tty0 console=ttyS0,115200 bombadil.smoke=refresh` | On a disk an older ISO installed: plants a marker in its home folder and its system, runs `bombadil-install --refresh /dev/vda --yes`, then power off. |

> **Warning: entries 03, 04 and 05 write to a disk without asking.** After their checks they run `bombadil-install /dev/vda --yes` (entry 03, `iso/airootfs/usr/local/bin/bombadil-smoke:727`), `bombadil-install --plan /tmp/smoke-plan.json` with a password (entry 04, `:742`) and `bombadil-install --refresh /dev/vda --yes` (entry 05, `:765`). `--yes` and a plan file skip the typed confirmation (`confirm`, `bombadil-install:176-181`), so the first virtio disk is wiped (03 and 04) or has its system replaced (05) with no prompt. The installer refuses a target that is not a whole disk, is under 16 GB, holds an ISO, has something mounted or is the stick (`probe`, `bombadil-install:139-173`), and nothing else asks whether this is the disk meant: a 40 GB scratch disk passes. The entries are only in builds made with `BOMBADIL_TEST_ENTRIES=1`, and their menu titles name `/dev/vda` but do not say what happens to it. Do not pick them in a VM that has a disk you want to keep. `scripts/run-vm.sh --disk` refuses to attach a disk larger than 100 MB to the ISO for this reason (`scripts/run-vm.sh:31-37`, `FORCE=1` overrides). Any call of `bombadil-install DISK --yes` erases the same way.

The VM scripts depend on these files by text. `scripts/test-vm.sh` waits for systemd-boot's countdown (`Boot in`) in the serial log and then presses `Down` `MENU_DOWN` times: once for entry 02 (the `live` mode), twice for 03, three times for 04 and four times for 05 (the order is the `sort-key`; `scripts/test-vm.sh:147,156,176,210`). `MODE=refresh` boots an older ISO's own entry 03 with two (`:172`). `scripts/wsl-vm.sh` waits for the same countdown, then presses `Down` once and `e`, `End` and `Backspace` 15 times at the end of entry 02's options line to delete ` bombadil.smoke` (`scripts/wsl-vm.sh:97`), so `bombadil.smoke` must stay the last argument of that entry.

|---|---|

`bombadil-install` copies the drop-in with the rest of the image (`cp -a "$image/." "$target/"`, `bombadil-install:425`, or `cp -ax /.` when no image is mounted, `:428`) and removes nothing under `grub.d` (`tests/test_boot_console.py` holds the copy step to that); it adds `bombadil.cfg` there when the font for the password screen could be made (`grub_theme`). On an installed system the kernel line is, in order: `BOMBADIL_INSTALL_CMDLINE` when set (`bombadil-install:559-561` puts it first in `GRUB_CMDLINE_LINUX_DEFAULT` of `/etc/default/grub`), the stock `GRUB_CMDLINE_LINUX_DEFAULT` (`tests/test_installer.py:135-150` holds a copy of Arch's defaults, which has `loglevel=3 quiet`; that Arch's `grub` ships this value is not shown by a file here), then the drop-in's nine. `quiet` and `loglevel=3` therefore appear twice on stock defaults, which `tests/test_boot_console.py` expects (one more `quiet` than the base). Because the drop-in is part of `/etc`, the installed boot of a VM test carries the quiet parameters as well, behind the test's own arguments.

`scripts/console-palette.py` reads the colour tokens of `share/qml/Bombadil/Theme.qml`. Its `PALETTE` list names the 16 console colours: a name is a Theme token, a `#hex` is a tone no token names. `--table` prints the 16 colours, one a line.

**Still on the screen.** The firmware's logo, the live stick's text menu (systemd-boot draws no pictures) and, on an encrypted disk, GRUB's password prompt. The design note records GRUB's own `Loading Linux` and `Loading initial ramdisk` lines for a moment after the firmware logo, written into `grub.cfg` by `grub-mkconfig`, and says Arch's `grub` has no setting that hides them. The installer therefore writes `grub.cfg` through `bombadil-grub-config` (`bombadil-install:765`), which runs `grub-mkconfig` in the C locale and deletes every `echo 'Loading ...'` line from the file (`iso/airootfs/usr/local/bin/bombadil-grub-config`); a `grub-mkconfig` run by hand writes them back. What the screen shows was not looked at in a VM for this page. There is no Plymouth: nothing in `iso/` or `scripts/` names it, and the note gives the reason.

**What checks it.** `tests/test_boot_console.py` (text checks, no boot; see Tests). In a VM the screen between the loader and the desk is meant to be `#101214` with no text; nothing in the repository checks that automatically, and the note's pictures are from a VM. Under emulation without KVM a whole boot takes minutes and the early framebuffer does not show in a QMP screendump, so the note took the console frames by starting the ISO's kernel and initramfs directly, with the entry's options plus `break=premount`, and a screendump through `scripts/qmp.py` (a method this page did not run).

### What `bombadil-install` does

`bombadil-install` is one bash script with `set -euo pipefail`, written as functions: the tests source it and call them, and run directly it does the install (`bombadil-install:1075-1089`). [Installed OS](installed-os.md) owns the layout it makes, the plan file, the refresh and an undo from outside; this section lists the steps in the order `run` calls them (`bombadil-install:1037-1073`). It runs four ways:

| Command | What it does |
|---|---|
| `bombadil-install` | At a terminal with no arguments: lists the disks, asks which one, a password, a time zone and a name for the computer, writes a plan file and goes on as `--plan` does (`guided`, `bombadil-install:939-1022`; the choice is made at `:1078`). It ends by asking for the stick to be taken out, then restarts. |
| `bombadil-install --plan FILE [--password-fd N]` | What the install card will run (designed). `src/bombadil/installplan.py` checks the plan against the command line and refuses what disagrees. The password comes on file descriptor N, never in an argument or a file. |
| `bombadil-install DISK [--yes]` | A whole disk with no password and no encryption, as the VM tests use it. Unless `--yes` is there it asks for the disk's name to be typed. |
| `bombadil-install --refresh DISK [--yes] [--password-fd N]` | Puts a fresh system on a disk that already holds Bombadil and keeps its home folder; the password opens an encrypted disk. |

### The smoke test

`bombadil-smoke` checks a booted machine and prints one `BOMBADIL-SMOKE:` line per event to `/dev/console` (and so to the serial port when the kernel has one). It ends by powering the machine off, so a VM run is judged from its log. The mode comes from the kernel argument (`iso/airootfs/usr/local/bin/bombadil-smoke:26`). This page holds the catalogue of checks; [Testing the whole system in a VM](../contributing/vm-testing.md) covers the host side (`scripts/test-vm.sh`), the protocol between the host and the guest, the traps and what to do when a check fails, and [Development](../contributing/development.md#the-iso-smoke) describes the layers of tests around it.

On an encrypted disk: LUKS2, three ways in, the key file in the initramfs, the recovery key waiting with mode 600, the record saying so with the zone and its source from the plan, the plan's computer name, and the sign-in the plan carried is there while the `Apps` demo and the `Notes` folder the plan left out are not (`layout-carry-list`; it does not look for anything else in the home) |
| the refreshed disk, in `refreshed` | 8 checks, `refresh-kept-the-home-folder`, `refresh-kept-the-sign-in`, `refresh-home-is-the-users`, `refresh-kept-the-computer-name`, `refresh-is-the-new-system`, `refresh-old-system-kept`, `refresh-record` and `refresh-home-restore-points`, then `refresh-undo` (`bombadil-smoke:851-870`) | the planted marker and project are in the home folder, the sign-in is the home folder's and not the stick's, the files belong to uid 1000, the computer's name is the old one's, the marker planted in the old system is not in the new one, `@.before-refresh-*` holds the old system, `install.json` says `refresh` with something kept aside, and `snapper -c home list` answers. `refresh-undo` runs `bombadil-rollback refresh` and reboots, and the phase file `~/.bombadil-smoke-phase` stops it doing so twice |

The script talks to the host through its own output. The host side is `scripts/test-vm.sh`; `scripts/vm-tools/vmsmoke` answers the same lines in a running VM.

| Line | Meaning |
|---|---|
| `BOMBADIL-SMOKE: START mode=<mode>` | a run begins |
| `BOMBADIL-SMOKE: PASS <name>` | a check passed |
| `BOMBADIL-SMOKE: FAIL <name>: <last 300 characters of its log>` | a check failed; its full log is `/tmp/smoke.<name>.log` |
| `BOMBADIL-SMOKE: SHOT <name>` | the host takes a screenshot to `out/test/<run>-<name>.png`, once; `<run>` is the name of the boot: `live`, `live-install`, `installed`, `old-install`, `refresh` or `refreshed` (the pattern is at `scripts/test-vm.sh:117`) |
| `BOMBADIL-SMOKE: KEYS <boot>-<n> <qcode>...` | the host presses these keys over QMP, once per `<boot>-<n>`; `meta_l+esc` is a chord. `<boot>` is the first 8 characters of the kernel's boot id (`bombadil-smoke:84-87`; the host's pattern is at `scripts/test-vm.sh:126`), so the numbers start again after the undo reboot and the host still sends them |
| `BOMBADIL-SMOKE: DIAG ...`, `NOTE ...`, `SKIP signin: ...`, `AGENTD-LOG: ...`, `MAIL-LOG: ...` | diagnostics. After each of the first four failed checks of a run, `DIAG <name> windows: [...]` (Hyprland's clients with class, workspace and pid) and `DIAG <name> programs: ...` (the pids of `Hyprland`, `quickshell`, `foot`, `footclient`, `zellij` and `agentd`, and the number of `chromium` processes; `diag`, `bombadil-smoke:10-17`). Lines for a Super tap that did nothing or a word that did not reach the pill. The `DIAG browser ...` lines that `browser_diag` prints when `signin-page-again` fails (the browser's command lines, the windows, the targets of its debugging port and the profile's singleton files, `bombadil-smoke:324-332`). `NOTE the machine was still busy when the pictures were taken` and `NOTE the machine was still busy when the keys went in`; `SKIP signin` when the sign-in block is skipped; the last 60 lines of the `agentd` log; and the last 30 lines of the mail service's log |
| `BOMBADIL-SMOKE: REBOOT pass=<n> fail=<m>` | the first pass of `undo`, or of `refreshed`, is about to reboot |
| `BOMBADIL-SMOKE: DONE pass=<n> fail=<m>` | the run ends; `test-vm.sh` exits 0 only when every log has `fail=0`, no `FAIL` line exists and the first log has no `SKIP signin` line (a fresh ISO must run the sign-in checks; `scripts/test-vm.sh:221-224`). `MODE=refresh` is judged by its own rule (`:214-219`): the refreshed log must hold a `REBOOT` line with `fail=0`, the `old-install` and `refresh` logs a `DONE` line with `fail=0`, and none may hold a `FAIL` line |

Without a host that answers, `shot` and `keys` only sleep (`SHOT_WAIT` and `KEYS_WAIT`, 8 seconds by default), and the checks that need key presses fail. `BOMBADIL_SMOKE_NO_POWEROFF` set to any non-empty value stops the final power off and the reboot.

`MODE=install scripts/test-vm.sh` runs the whole path across three boots:

```mermaid
sequenceDiagram
    participant H as test-vm.sh on the host
    participant L as live guest, entry 03
    participant I as installed guest
    H->>L: boot the ISO as a USB disk beside a blank one, Down twice, Enter
    L-->>H: SHOT and KEYS requests
    H->>L: screenshots and key presses over QMP
    L->>L: check install: bombadil-install /dev/vda --yes
    L-->>H: DONE, power off
    H->>I: boot the disk alone
    I->>I: first pass: brain checks, restore point, change, undo, REBOOT
    I->>I: second pass: undo-applied
    I-->>H: DONE with fail=0, power off
```

`MODE=install-encrypted scripts/test-vm.sh` boots entry 04 (`Down` three times) and reads `PASS install-encrypted` from its log, then boots the disk alone with a USB keyboard (OVMF does not see a virtio one) and types the password each time GRUB's `Enter passphrase` prompt shows; it fails when GRUB never asked, or when a second prompt (the initramfs's own) shows (`scripts/test-vm.sh:153-165`). `MODE=refresh OLD_ISO=old.iso scripts/test-vm.sh` needs an older ISO with its install entry. It installs the disk with that ISO (as a CD with 4 GB, because the old installer takes its kernel from the stick's own mount, which copy-to-RAM removes), boots this ISO's entry 05 (`Down` four times) to refresh it, boots the refreshed disk, whose checks end in `refresh-undo` and a reboot, and waits for the old system's `hyprland-running`; it fails when a `layout-` or `refresh-` check of the refreshed system shows after the reboot, which means the undo did not take (`scripts/test-vm.sh:166-191`).

`MODE=installed scripts/test-vm.sh` boots only the disk the last `install` or `install-encrypted` run left, in `out/test/disk.qcow2`, and exits 2 when that file is missing. It still looks up an ISO first: the lookup at `scripts/test-vm.sh:19` runs in every mode, so with no `out/*.iso` and no `ISO` set the script stops there with `ls`'s error and status 2, before it checks the firmware or the disk. It copies the previous `installed.serial.log` to `installed-first.serial.log`, and when that log shows GRUB's `Enter passphrase` prompt it types the password again, as the run that made the disk did; it judges the log of this boot alone (`scripts/test-vm.sh:192-207`). [Testing the whole system in a VM](../contributing/vm-testing.md) covers the host side of these runs. It is for an undo round trip that was cut short, for example an emulator that died as the guest rebooted: the guest remembers its phase in `~/.bombadil-smoke-phase`, so this boot is the second pass, which runs `undo-applied`.

### Running it in QEMU

```sh
scripts/build-in-container.sh   # or scripts/build-iso.sh on an Arch host with archiso
scripts/run-vm.sh               # live boot of the newest out/*.iso
scripts/run-vm.sh --disk        # live boot with a blank 40G disk at out/bombadil.qcow2, seen as /dev/vda
sudo bombadil-install           # inside the VM, in a terminal (Super + Return): asks for the disk, a password, a time zone and a name
sudo bombadil-install /dev/vda  # or name the disk: no password, no encryption; asks for the disk's name to be typed
scripts/run-vm.sh --installed   # boot the installed disk, no ISO
```

`scripts/run-vm.sh` needs KVM (`-enable-kvm`) and one of three OVMF firmware paths (`edk2-ovmf` or `ovmf`). It opens a GTK window with `virtio-vga-gl` (`GL=0` swaps in `virtio-vga` and software rendering), a virtio keyboard and tablet, an Intel HDA sound card, and user-mode networking that forwards `127.0.0.1:2222` on the host to guest port 22. The image enables no `sshd`, so that forward only helps after something starts one in the guest. QEMU is named `Bombadil`; `out/vm/qmp.sock` takes `scripts/qmp.py` commands (see Interfaces), and `out/vm/serial.sock` and `out/vm/serial.log` hold the serial console. `MEM` (6G), `SMP` (4), `RES` (1600x900), `GL` (1) and `SSH_PORT` (2222) size it.

`scripts/test-vm.sh` is the headless counterpart. It boots the newest ISO (or `ISO`) with the firmware as a read-only code image and, where the machine's firmware comes as a code file and a variable file, a copy of the variable file at `out/test/OVMF_VARS.fd`, so that the boot entry GRUB makes is kept from one boot of a disk to the next (`scripts/test-vm.sh:41-51`). It shows a VNC display on `127.0.0.1:99` (`VNC`) and uses KVM when `/dev/kvm` is writable; without it, software emulation with a CPU that lacks AVX (`QEMU_CPU`, default `Nehalem`), because Mesa's JIT crashed on the emulated AVX2. It picks the smoke entry by pressing Down over QMP when the boot menu's countdown shows on the serial console. A `live` run attaches the ISO as a CD and gives the VM 4 GB. The install modes attach it as a USB disk (`qemu-xhci` with `usb-storage`) and give the VM 8 GB, which is how the installer meets copy-to-RAM on a real stick, where the stick is not mounted by the time the install starts (`scripts/test-vm.sh:53-60`); `RAM` sets the memory in every mode. `MODE` is `live` (default), `install`, `install-encrypted`, `refresh` (it needs `OLD_ISO`, an older ISO with its install entry) or `installed` (it boots the disk the previous install run left and still needs an ISO in `out/` or `ISO` set, because the ISO lookup runs in every mode; see the end of [the smoke test](#the-smoke-test)). The install modes and `refresh` stop with status 2 when the ISO has no entry for them (`need_entries`, `scripts/test-vm.sh:139-141`): build it with `BOMBADIL_TEST_ENTRIES=1`. `TIMEOUT` is 2400 seconds per boot. Output goes to `out/test/`. [Testing the whole system in a VM](../contributing/vm-testing.md) owns the host side of the run, and [Development](../contributing/development.md) covers the layers of tests and the tools in `scripts/vm-tools/` that drive a running VM.

`scripts/dev-session.sh` is the third way: on an existing Hyprland desktop with `quickshell` (and `pyside6` only if you want to create apps), it starts `agentd`, `bombadil-mail`, the connection service and the bar from the checkout, with `PATH` pointing at `bin/`, `BOMBADIL_SHARE` at `share/` and `BOMBADIL_PROVIDER` defaulting to `fake`. Unless `BOMBADIL_MAIL_ENGINE` is set to something other than `fake`, mail runs on its fake engine with its database, files, press log and socket (`BOMBADIL_MAIL_DB`, `BOMBADIL_MAIL_FILES`, `BOMBADIL_PRESS_LOG`, `BOMBADIL_MAIL_SOCKET`) in a scratch folder that the script removes on exit, so nothing reaches the mail of a Bombadil that is also installed on the machine (`scripts/dev-session.sh:9-20`). Connections get the same treatment: unless `BOMBADIL_CONNECT_ENGINE` is set to something other than `fake`, the script puts the service's socket and state (`BOMBADIL_CONNECT_SOCKET`, `BOMBADIL_CONNECT_STATE`) in a scratch folder of its own, lets in only the uid that runs the session (`BOMBADIL_CONNECT_UIDS`, which defaults to that uid) and starts `bin/bombadil-connect` on its fake engine before `agentd`, so that `agentd`'s first look at it finds it; with any other value it starts no service and the system unit's is the one in use (`scripts/dev-session.sh:21-32`). It starts no browser service. There is no ISO, no installer and no restore point unless the machine already has a snapper `root` config.

### The Windows launcher

`scripts/bombadil-vm.cmd` and `scripts/wsl-vm.sh` build, install and run the ISO in a QEMU window on a Windows host: QEMU with KVM runs inside a WSL distro and the window is shown through WSLg. `scripts/wsl-vm.sh` is generic: it also runs on any Arch host, as root.

- `scripts/bombadil-vm.cmd` is the entry point. It checks that a dedicated WSL distro answers (the distro's name is set in the file), creates it with `wsl --install archlinux --name <name> --no-launch` when it does not, and runs `bash scripts/wsl-vm.sh <arguments>` in it as root, with the checkout as the working directory. The file's comment names the way to remove everything: unregister that distro.
- `scripts/wsl-vm.sh` must run as root. `setup` installs `archiso qemu-desktop edk2-ovmf git nodejs npm python` if any is missing, loads `kvm_intel` (when `/proc/cpuinfo` has `vmx`) or `kvm_amd` only when `/dev/kvm` does not exist and records the module name in `/etc/modules-load.d/kvm.conf`, and sets git's `safe.directory` (`scripts/wsl-vm.sh:26-36`). `sync_tree` clones the checkout once into a tree on the distro's Linux filesystem (`BOMBADIL_TREE`) and moves that clone, detached, to the commit the checkout is on, because a Windows checkout loses symlinks and executable bits. Uncommitted changes are therefore not built.
- `iso_key` hashes the git trees of `bin`, `src`, `shell`, `share`, `iso`, `install` and `scripts/build-iso.sh` (`scripts/wsl-vm.sh:46`). When the key matches `out/.iso-key` and an ISO exists, the build is skipped, so a commit that only touches documents or VM scripts reuses the last ISO. The build sets `BOMBADIL_TEST_ENTRIES=1` (`:53`), because the install below boots test entry 02, which a release build leaves out.

| Argument | What it does |
|---|---|
| none | Boots the installed disk. When `out/.installed` or the disk is missing, it builds and installs first. It says when the checkout has moved on from what the disk was built from. |
| `live` | Builds if needed and boots the live ISO. The disk is not touched. |
| `refresh` | Keeps the disk and moves it to this checkout in place. Stops the VM, takes a `qemu-img snapshot` named `before-refresh-<time>-<rev>`, boots the disk and runs `scripts/vm-tools/update-in-place --reboot HEAD`. The login, apps and files on the disk stay. This is a shortcut for a development VM and not the installer's `bombadil-install --refresh`, which lays a whole fresh system on the disk and keeps the home (`MODE=refresh scripts/test-vm.sh` tests that one; `scripts/wsl-vm.sh:151-155`). The tool moves the Bombadil tree and the system files the profile owns outright (the Chromium policy, `/etc/environment`, the MIME defaults, `bombadil-browser.desktop`, the icon folders `usr/share/icons/hicolor` and `usr/share/pixmaps`, and the scripts `bombadil-setup`, `bombadil-install`, `bombadil-rollback` and `bombadil-smoke`) and adds a `/usr/local/bin` link for each program in `bin/` that has none; packages, `bombadil-grub-config` and `etc/grub.d`, GRUB defaults, the pacman mirror list, systemd units, the managed Claude Code and Codex files and the person's own files, such as `hyprland.lua`, are not part of it (`SYSTEM` in `scripts/vm-tools/update-in-place:23-26`). |
| `reinstall` | Rebuilds if the checkout changed the ISO's inputs, asks (type `wipe`; `--yes` or `BOMBADIL_YES=1` skips the question), renames the old disk to `bombadil.qcow2.before-reinstall` and installs again. |
| `build` | Builds the ISO only. |
| `stop` | Presses the ACPI power button over QMP and waits up to 60 seconds, then kills QEMU. |

The install runs without a window. It boots the ISO's entry 02, edits its kernel line over QMP to delete ` bombadil.smoke` (`Down`, `e`, `End`, 15 `Backspace`, `Enter`), which leaves a root shell on the serial port, and types a line into it (`scripts/wsl-vm.sh:109-111`): `bombadil-install /dev/vda --yes` with `BOMBADIL_INSTALL_CMDLINE='console=tty0 console=ttyS0,115200'` and `BOMBADIL_INSTALL_LEAVE_MOUNTED=1`, which keeps the new system mounted at `/mnt` so that the same line can append an `hl.monitor` line for `Virtual-1` at `RES` to the installed `hyprland.lua` (a QEMU window reports its starting size, often 640x480, as the preferred mode), then `sync && umount -R /mnt` and `poweroff`. It is the plain form of the installer: the disk is not encrypted and `user` has no password. `MEM` defaults to 5G and `GL` to 0 here. In the window, Ctrl+Alt+F toggles full screen; the Windows key opens the Start menu, so Alt+Space opens the pill. When the log of WSLg's window link shows its helper exiting repeatedly, the script warns and says to run `wsl --shutdown` and start again.

| No login screen | `iso/airootfs/etc/greetd/config.toml` | `initial_session` and `default_session` both run `sh -c 'exec systemd-cat -t hyprland start-hyprland'` as `user`; the file's comment says there is no login screen and no separate user |

Anyone at the keyboard of an installed machine that is running is root: greetd starts the session without asking for the password, and sudo asks for none. A password chosen at install protects the disk at rest and nothing else. With one, the disk is encrypted and GRUB asks for it once when the computer starts; with none (the plain form, and the live system) nothing is encrypted and the account's password is empty. No screen lock exists: `hyprlock`, which `launcher._lock` runs, is not installed (`src/bombadil/launcher.py:1122-1127`), although the guided install says the password "unlocks the screen" (`bombadil-install:921`; Known gaps). That is the stance of the product, not an oversight, with two changes designed: greetd asking for the password and the screen locking on lid close ([What the installer does not do yet](#what-the-installer-does-not-do-yet), [Installed OS](installed-os.md#designed-only)).

### What is in `/etc/skel`

`iso/airootfs/etc/skel/` is the repository's part of what a home starts from: the overlay is laid on the packages' own `/etc/skel`, and the `bash` package adds its own dotfiles there (a statement about that package, which no file here shows). It is copied when `useradd -m` creates the live user and again when the installer makes the installed one (`useradd -m` in `configure`, `bombadil-install:584`, or `cp -a /etc/skel/. /home/user/` when a copy of the running system has the account and no home, `:589`). A refresh keeps the home it finds and adds the skeleton files that home lacks, never replacing one (`cp -an`, `:651`).

| Path in the home | What it is |
|---|---|
| `.config/hypr/hyprland.lua` | The Hyprland session: monitors (`preferred` and a 1920x1080 rule for `Virtual-1`), the `hyprland.start` handler (it imports the session's environment and restarts `bombadil-agentd` and `bombadil-shell`, starts `foot --server`, then restarts `bombadil-mail.service` and `bombadil-browserd.service`), the look (gaps 6 and 12, border 1, rounding 12, blur, `dwindle`, `background_color = 0xff101214` for the desk ground), the animation curve and the slide animations (the `layers` animation is off, `hyprland.lua:59`, so the bar changes size when a picture resizes it instead of sliding), the binds and the window rules. |
| `.config/bombadil/wallpaper` | Comments only. A path of an image on a line of its own replaces the standard picture under the desk ([Boot and the console](#boot-and-the-console-from-power-on-to-the-desk)). |
| `.config/chromium-flags.conf` | `--no-first-run`, `--no-default-browser-check`, `--password-store=basic`, for a Chromium started any other way than by the browser panel. |
| `.claude/skills/bombadil-apps` | A link to `/usr/share/bombadil/share/skills/bombadil-apps`, the app skill for Claude. |
| `.agents/skills/bombadil-apps` | The same link, for Codex. |
| `.claude/skills/bombadil-mail`, `.agents/skills/bombadil-mail` | Links to `/usr/share/bombadil/share/skills/bombadil-mail`, the mail skill, for Claude and for Codex. |
| `.claude/skills/bombadil-connect`, `.agents/skills/bombadil-connect` | Links to `/usr/share/bombadil/share/skills/bombadil-connect`, the connections skill, for Claude and for Codex. |

The binds in `hyprland.lua`:

| Bind | Does |
|---|---|
| `SUPER + B`, `SUPER + T`, `SUPER + F` | toggle the special workspaces `browser`, `terminal`, `files` |
| `SUPER + Q` | close the window |
| `SUPER + Return` | `bombadil terminal`: puts away any drawer but the terminal's own, then starts `foot` without Hyprland's initial-workspace token, so the window opens on the desktop and not inside a drawer that was showing (`src/bombadil/hypr.py:227-251`) |
| tap `SUPER_L` or `SUPER_R` (fires on release) | the global shortcut `bombadil:pill-release`: the pill takes the keyboard |
| `ALT + space` | the global shortcut `bombadil:pill-press`, for a VM window that keeps the Windows key |
| `SUPER + Escape` | `bombadil stop` |
| `SUPER + CTRL + Escape` | `systemctl --user restart bombadil-shell`: restarts the bar's unit, so no second Quickshell races the first |

The two pill shortcuts are global shortcuts that the bar registers (`shell/PillKeys.qml`, loaded once and only under Hyprland), so the key reaches the pill in the bar's own process. `bombadil pill` would be a Python start and a round trip through `agentd`, and on a busy machine the first letters typed after a tap went to the window underneath before the pill had the keyboard. Hyprland does nothing, and says nothing, for a shortcut nobody registered, and the bar listens to one edge of each (the release of a tap, the press of Alt+Space), so a bind in `hyprland.lua` and its shortcut in `PillKeys.qml` change together. `tests/test_iso_profile.py:64-86` holds the names and the edges together, and the smoke's `pill-shortcuts-registered` asks Hyprland for its list of shortcuts before a key depends on them (`bombadil-smoke:180-181`).

The window rules: generated apps (`^(bombadil-app-.*)$`) float, centred, `540 660`; `bombadil-browser`, `bombadil-terminal`, `org.gnome.Nautilus` and `bombadil-details` open `silent` into `special:browser`, `special:terminal`, `special:files` and `special:details`; the `bombadil-sessions` rule floats a coding session's window (`^(bombadil-session-.*)$`) centred at `(monitor_w*0.86) (monitor_h*0.8)` ([coding sessions](#what-the-image-adds-for-coding-sessions)); the `mail-engine` rule sends Thunderbird's windows to `special:mail-engine silent` ([mail](#what-the-image-adds-for-mail)). The skills links resolve only on a system with the tree at `/usr/share/bombadil`.

### What the installer does not do yet

The installer above is what `main` has of [the installed OS](installed-os.md), which owns the state of each piece. [Bombadil, installed](../design/installed-os-brief.md) designs more, and none of it has code anywhere:

| Designed | What `main` does instead |
|---|---|
| The install card, over `--plan` | The plan file with its guards, and a terminal flow that asks for a disk, a password, a time zone and a name. There is no card and no first-start card for the recovery key: a plan run keeps the key in `/var/lib/bombadil/recovery-key` and nothing shows it. |
| Bombadil as packages, then a signed repository, so installed machines can update | A copied tree, links and npm, owned by no package. A machine gets a later Bombadil by a refresh with a later ISO. |
| Next to another system | A fresh install erases the whole disk, Windows included, once its name is typed; a refresh refuses a disk with Windows on it (`bombadil-install:281`). |
| A daily prune of `@.undone-*`, `@.before-refresh-*` and `@.after-refresh-*` after 14 days | Nothing prunes them, although the guided refresh says the old system is kept for 14 days (`bombadil-install:995`). |
| greetd asking for the password, and the screen locking on lid close | greetd opens the session with no password, and nothing can lock the screen. |
| Repair, reinstall and erase from the stick, and a start that puts itself back after two failures | The stick installs and refreshes. `bombadil-rollback --device DEV` undoes from outside by hand, and undo is a command or the pill's word. |

## Principles it keeps

- [The person is a passenger](../principles.md#the-person-is-a-passenger) and [quiet at rest](../principles.md#quiet-at-rest): the image reaches the pill with nothing in the way: `systemd-firstboot` is masked, greetd logs in at once, the installed GRUB menu is hidden (on an encrypted disk it asks for the password once, and the key file in the initramfs means nothing after it asks again), the console prints nothing between the loader and the desk, and first run happens in the pill. The trap is a login screen, a boot menu that waits, a question before the pill, or a unit or program that writes to the console (the greetd line and `quiet` are what keep it empty).
- [Full access, with undo instead of guard rails](../principles.md#full-access-with-undo): `user` has `NOPASSWD: ALL` and, unless the install chose a password, an empty one, and the guard is the layout the installer builds (`@`, `@home`, `@snapshots`, `@log` and `@pkg`, snapper configs named `root` and `home`, `/` named `@` in the fstab, and the kernel inside `@/boot` so a restore point carries its own). The trap is adding a prompt where a restore point belongs, or keeping state outside `@` so that undo cannot carry it: the EFI partition is outside it on purpose, because it holds GRUB and nothing a restore point must bring back.
- [Recovery never goes through the part that broke](../principles.md#recovery-without-the-broken-part): `bombadil-rollback` is a bash script over btrfs and needs no `agentd`, model or desktop (with `--device` it runs from the stick on a disk that will not start, and `refresh` puts back what a refresh moved aside), and the `undo` smoke mode checks the swap across a reboot. The trap is mounting `/` by `subvolid` (undo swaps a snapshot in under the name `@`) or moving the rollback behind the daemon.
- [Every piece degrades](../principles.md#degrade-and-recover): the live image has snapper but no config, so undo says it starts once Bombadil is installed instead of failing; the brain's watcher stays up on the live root and says it is not watching instead of restart-looping; the mail service runs with no account and does not start Thunderbird until there is one; an `agentd` or bar that dies is started again by systemd after a second, and the connection service and the browser service after two seconds, while the pill, the cards and the turns carry on without the connection service (the unit's comment); `bombadil-setup` signs in with no daemon; the installer copies the image, or the running system when no image is mounted, and needs no network (it installs what the stick itself added from the package files already downloaded, with `pacman -U`). The trap is an install step or boot unit that needs the network, `agentd` or a model.
- [Nothing runs on its own that the person cannot see and stop](../principles.md#nothing-runs-unseen): `bombadil-smoke.service` has `ConditionKernelCommandLine`, so it never runs on an ordinary boot, and the test entries say so in their titles and are in a test build only (`scripts/build-iso.sh:19-23`). Background programs that belong to the image are units (`bombadil-brain-watch` and `bombadil-connect`, and the user units `bombadil-agentd`, `bombadil-shell`, `bombadil-brain`, `bombadil-mail` and `bombadil-browserd`), which `systemctl` lists and stops. A coding session runs in a transient `bombadil-dev-<project>-<role>-<run>.scope` unit, where systemd can make one, and `systemctl --user` lists that too. The one exception is `foot --server`: the `hyprland.start` handler starts it with `hl.exec_cmd`, it is not a unit, and nothing starts it again if it dies. Coding sessions tolerate that, because their windows fall back to a plain `foot`. The trap is a unit that runs a test or a destructive step without the person's own kernel argument (entries 03, 04 and 05 already erase or replace a disk without asking and are not a pattern to copy), or a daemon started the way `foot --server` is, directly with `hl.exec_cmd("program")` instead of through a unit: `systemctl` does not list it and nothing starts it again when it dies. Do that only for a helper that something else can do without.
- [Plain files stay the truth](../principles.md#plain-files-stay-the-truth): the overlay is plain files in `iso/airootfs/`, `scripts/build-iso.sh` adds the tree, the links and the CLIs from the repository, and the installer's output is text (`fstab`, `crypttab`, GRUB defaults, a preset, `install.json`). The trap is a build step that writes something not derivable from the repository, so that what is in the repository is not what is in the image.

## Extending it

**Add a package to the ISO**

1. Add its name on its own line to `iso/packages.x86_64`, under the `#` comment group of `iso/packages.x86_64` it belongs to. The build installs from `core` and `extra` only (`iso/pacman.conf`); a package from another repository needs a section for that repository added there first.
2. If a service must run, put an enable link in `iso/airootfs/etc/systemd/system/<target>.wants/`, as `NetworkManager.service` is linked in `multi-user.target.wants/`. A unit for the user's own session goes in `etc/systemd/user/` with a link in `etc/systemd/user/default.target.wants/`, as `bombadil-brain.service` and `bombadil-mail.service` do. That unit starts at login, before Hyprland has a screen: a program that needs the display must be handed the session's variables and restarted once Hyprland is up, as the `hyprland.start` handler does for `bombadil-agentd` and `bombadil-shell` after `import-environment` (`hyprland.lua:9-10`), for the mail unit (`hyprland.lua:15-18`) and for the browser unit (`hyprland.lua:19-22`). `bombadil-agentd.service` and `bombadil-shell.service` show the other pattern: no `[Install]` section and no link, and only the handler starts them. The installer copies the image, `/etc` included, so the installed system gets the units and links with no change to `bombadil-install` (which enables `greetd`, `NetworkManager`, `systemd-timesyncd`, `fstrim.timer` and `snapper-cleanup.timer` itself, `bombadil-install:595`). A unit that must exist only on the live system also goes into the removal loop at `bombadil-install:437-440`.
3. If a file you add must run or be private, add a `file_permissions` line in `iso/profiledef.sh`. Files a package owns need nothing.
4. To stop it being dropped, add an assertion like `test_there_is_sound` to `tests/test_iso_profile.py`, which reads the list through `_packages()`. If a program must be on `PATH` after boot, add a check of its own to the always-run block of `bombadil-smoke`, for example `check NAME bash -c 'command -v PROGRAM'`. Adding the name to `tools-installed` (`bombadil-smoke:30`) proves nothing, because `command -v A B C` exits 0 when any one name is found; `dev-tools` (`bombadil-smoke:363`) is built the same way. A program that `bombadil-install` or the initramfs needs belongs in the set `test_the_stick_carries_everything_the_installer_calls` holds (`tests/test_iso_profile.py:107`); a tool the installer calls is also one `probe` looks for before it touches the disk (`bombadil-install:139-173`).
5. Rebuild. A machine that is already installed does not get the package from the list until it is refreshed with the later ISO (`bombadil-install --refresh` lays the image's system on the disk and keeps the home); `scripts/vm-tools/update-in-place` carries no packages (the agent can still install one with `pacman`, which its system prompt tells it to). `scripts/wsl-vm.sh` notices the change because `iso_key` hashes `iso/`.

**Add a program to the image**

1. Put the program in `bin/`. `scripts/build-iso.sh:14` copies `bin/` into `/usr/share/bombadil/bin`, and `file_permissions` sets that directory to 0755 (`iso/profiledef.sh:27`).
2. Add its name to the `for b in ...` list at `scripts/build-iso.sh:25`. Without it there is no link in `/usr/local/bin` and the program is not on `PATH` on a fresh image. `scripts/vm-tools/update-in-place` links every program in `bin/` that has no link (line 73), so an installed VM needs no edit.
3. For a script that must run as root and live in `iso/airootfs/usr/local/bin` (as the five scripts do), add a `file_permissions` line (`iso/profiledef.sh:20-25` show the pattern) and add its path to `SYSTEM` in `scripts/vm-tools/update-in-place:23-26`, so that a `refresh` carries it ([restore points](restore-points.md) says the same for a root script; `bombadil-grub-config` is one of the five and is not in `SYSTEM`). A script for `etc/grub.d/` needs the same line, because `grub-mkconfig` skips a file there that is not executable; `test_every_script_the_image_adds_to_the_path_or_to_grub_is_executable` holds both folders to it.
4. Add a check to `bombadil-smoke` that looks for the name on its own, in the loop style of `brain-tools-installed` (`bombadil-smoke:32`), `mail-tools-installed` (line 33) and `connect-tools-installed` (line 35); `tools-installed` proves nothing for one more name. Add a separate check instead of a name in the brain loop: `tests/test_brain_service.py` pins the text `bombadil-brain bombadil-brain-watch; do command -v`.

**Add a provider CLI to the image**

The provider's own side (its class in `src/bombadil/providers.py`, its sign-in, its launcher words) is in [agentd](agentd.md#add-a-provider), which owns the whole recipe; see also [os-mcp](os-mcp.md#change-how-a-cli-is-told-about-the-server-or-add-a-provider) and [browser and sign-in](browser-and-signin.md#extending-it). The edits that belong to this piece:

1. `scripts/build-iso.sh:30-31`: add the npm package to the `npm install -g` line, so the CLI is in the image and first run only has to sign in. The line carries `--allow-scripts=@anthropic-ai/claude-code`, set for that one package; a CLI with an install script of its own needs its own `--allow-scripts=<package>` entry there, and the smoke check of step 5 is what shows whether it works (the flag's behaviour is npm's and was not run here).
2. `iso/profiledef.sh:28-29`: when the CLI comes from an npm scope the image does not have yet, add `/usr/lib/node_modules/@<scope>/` with `0:0:755`, because `mkarchiso` copies airootfs without modes.
3. `iso/airootfs/usr/local/bin/bombadil-setup`: the `select provider in claude codex` list (line 10), the install `case` (lines 11-14) and the login `case` (lines 26-29).
4. `install/carry.list`: add the CLI's credential path, relative to the home, on a line of its own. Without it an installed system starts signed out of that CLI. The installer needs no change for that; add the CLI's state folder to `HOME_SUBVOLS` (`bombadil-install:44-45`) as well when a restore point of the home must not roll its conversation back, as it does for `.claude` and `.codex` (nothing takes a restore point of the home yet, so this readies the folder for the day something does).
5. `bombadil-smoke:104-105`: add a check like `claude-cli` (`as_user NAME --version`).

**Add a smoke check**

1. Open `iso/airootfs/usr/local/bin/bombadil-smoke` and choose the block. Above the first `if [[ "$mode" != "undo" ]]` block (line 444) it runs in every mode. Inside the mail block (lines 444 to 478) it runs in every mode but `undo`: the place for a check that stops the mail unit and runs the service on its fake engine. The connections block (lines 481 to 554) has its checks that run in every mode first (lines 530 to 539) and, inside its own guard (lines 540 to 554), the ones that run in every mode but `undo`: the place for a check that puts the connection service on its fake engine through a drop-in and then restores the unit. The sign-in block (lines 566 to 647) runs in `live` and `install` only, and only when no provider is chosen (lines 560 to 566): the place for a check that restarts `agentd` or changes the provider; the name and voice checks sit at its start (lines 572 to 595), before the real logins. The idle-cost check (lines 649 to 715) follows. Then come the blocks for one mode each: `install`, `install-encrypted` and `refresh` (lines 725 to 766), the `undo` block (lines 796 to 849) and the `refreshed` block (lines 851 to 870). `layout_checks` (lines 769 to 794) is what `undo` and `refreshed` both run, so a check of what an install made, on every installed disk, belongs there; the first pass of `undo` is where a check that needs the installed btrfs layout belongs, as the brain checks do.
2. Write `check NAME COMMAND...`. `NAME` is the word in `PASS NAME` and `FAIL NAME` and the log key `/tmp/smoke.NAME.log`; keep it lower case with hyphens and unique. The command passes by exiting 0. Wrap anything slow in `wait_for SECONDS COMMAND...`, which retries once a second. Run anything that must see the session through `as_user COMMAND...`.
3. Reuse the helpers in the script: `hypr_json KIND`, `has_client 'PYTHON-EXPRESSION'`, `special_shown NAME`, `active_is CLASS`, `has_layer NAME`, `mcp_call TOOL 'JSON'`, `agentd_send 'JSON'`, `history_has TEXT`, `launcher_ran WORD TEXT COUNT`, `revives UNIT` (kills a user unit's main process and waits for systemd to start another). `has_client` evaluates the Python expression once per Hyprland client, which the expression sees as `c`, and passes when it is true for any of them: `has_client 'c["class"]=="bombadil-browser"'`. `launcher_ran` passes when `launcher_done WORD TEXT` is greater than COUNT, so take `before=$(launcher_done WORD TEXT)` before the action and pass `"$before"` as COUNT. `mcp_call` passes when the tool answers without `"isError": true`, so it proves a call returned, not what the call did: follow it with a check that reads the result, as `app-shown` follows `create-app`.
4. For a screenshot, call `shot NAME`: lower-case letters, digits and hyphens only, because the host matches `SHOT [a-z0-9-]*` (`scripts/test-vm.sh:117`) and cuts the name at the first other character. For key presses, call `keys QCODE...`: lower-case qcodes, digits, `_` and `+`, because the host matches `KEYS [0-9a-f]*-[0-9]* [a-z0-9_+ ]*` (`scripts/test-vm.sh:126`); the function adds the boot id and the running number itself.
5. If the check needs a package or file, put it in the image first (the recipes above). If the fact is static, add a test to `tests/test_iso_profile.py` as well, which fails sooner.
6. Run `bash -n iso/airootfs/usr/local/bin/bombadil-smoke`. The script is baked into the image and `scripts/test-vm.sh` boots the newest `out/*.iso` (or `ISO`), so rebuild the ISO first (`scripts/build-in-container.sh`) and then run `scripts/test-vm.sh`; run on the old ISO, it shows none of the added check. On an installed VM, commit the change, run `scripts/vm-tools/update-in-place REF`, which carries `bombadil-smoke` into the guest, and then `scripts/vm-tools/vmsmoke`. `vmsmoke` refuses on a VM that already has a provider chosen (`~/.config/bombadil/config.toml`) unless `FORCE=1`; its own comment gives the sign-in checks as the reason (they restart `agentd` with stand-in providers, and `codex login` revokes a stored Codex login). The smoke skips those checks itself where a provider is chosen (`SKIP signin`, `bombadil-smoke:560-566`), so with `FORCE=1` on such a VM they are skipped, not run, and the other checks still run. The name and voice checks also fail on a VM that already has `~/.config/bombadil/persona.toml`, because `no-persona-before-voice` wants it absent ([the traps](../contributing/vm-testing.md#traps)). Run it as `scripts/vm-tools/with-scratch vmsmoke` on a scratch copy (with `FORCE=1` when the copy has a provider) or with `FORCE=1` on a disposable VM ([Development](../contributing/development.md) describes the VM tools). Every `check` counts in `DONE pass=<n> fail=<m>`, and the run fails on any `FAIL`.

**Change what the image tells Claude Code or Codex**

1. A setting for every machine goes in `iso/airootfs/etc/claude-code/managed-settings.d/50-bombadil.json` (Claude Code's managed hooks), in `iso/airootfs/etc/codex/requirements.toml` (Codex's managed hooks) or in `iso/airootfs/etc/codex/config.toml` (Codex's defaults; the person's own `~/.codex/config.toml` sits above them, as the file's comment says). It does not go in the skel: a skel copy is made once and never updated, and Codex writes project trust into the user's own file. `tests/test_dev.py` asserts that the skel has no `.codex`.
2. To add a hook event, put it in both hook files the same way, each running `bombadil-signal claude` or `bombadil-signal codex`. What the event means to the dots is decided in `bin/bombadil-signal` and `src/bombadil/dev.py` ([Coding sessions](coding-sessions.md) owns that). Add the event to the list in `test_managed_hooks_cover_the_events_the_dots_need`.
3. The installer copies the image, `/etc` included, so an installed system gets the files with no change to `bombadil-install`; `scripts/vm-tools/update-in-place` does not carry them ([Known gaps](#known-gaps)).
4. Run `python3 -m pytest -q tests/test_dev.py -k managed_hooks`. It and the smoke's `dev-hooks-parse` read the files and run neither tool: whether Claude Code or Codex accepts a setting is theirs to say.

**Add a first-run step**

There is no registry of first-run steps. The step belongs in one of these places, by what it does:

1. The person's first run, which is choosing the AI and signing in: `agentd`'s setup states, in `src/bombadil/agentd.py` and `src/bombadil/signin.py`. Follow the steps in [browser and sign-in](browser-and-signin.md#extending-it). `bombadil-setup` is the terminal fallback; keep it in step by editing its `select provider in claude codex` list and its `npm install` lines.
2. A root action once per live boot: add a oneshot unit to `iso/airootfs/etc/systemd/system/` with `WantedBy=multi-user.target` and an enable link in `multi-user.target.wants/`, the way `bombadil-live.service` and `pacman-init.service` are written. Order it `Before=greetd.service` if the session needs its result. Because the installer copies the image's `/etc`, add the unit to the loop `for u in bombadil-live pacman-init` and to the `rm -f` line (`bombadil-install:437-440`) if it must not exist on the installed system.
3. A root action once at install time: add the command to the chroot block of `configure` (`bombadil-install:572-597`), which runs with `bash -e`, or after it for files on the target (`$target`, `/mnt` unless `BOMBADIL_TARGET` says otherwise). A refresh runs the same block over the home it keeps, so the command must be safe to run twice.
4. An action at every login: add `hl.exec_cmd(...)` to the `hyprland.start` handler of `iso/airootfs/etc/skel/.config/hypr/hyprland.lua`. It reaches only homes made after the change (see the next recipe). A program that must stay up belongs in a user unit instead, restarted from the handler with `systemctl --user restart` after the environment is imported, as `bombadil-agentd` is ([Add a package to the ISO](#extending-it), step 2).
5. Cover it with a `check` in `bombadil-smoke` and, for a file, a path-based test in `tests/test_iso_profile.py`.

**Add a file to the home a user starts with**

1. Put the file under `iso/airootfs/etc/skel/` at its path relative to the home: `etc/skel/.config/example/app.conf` becomes `~/.config/example/app.conf`. A symlink stays a symlink (the skills links are examples). Put nothing personal or secret there: it ships in the public image.
2. `mkarchiso` copies airootfs without modes. If the file needs another mode, add its image path (`/etc/skel/...`) to `file_permissions` in `iso/profiledef.sh`.
3. It reaches the live session's home (`useradd -m` in `bombadil-live.service`) and the installed home (`useradd -m` in `configure`, `bombadil-install:584`, or `cp -a /etc/skel/. /home/user/`, `:589`). It reaches a home that already exists only as a file that home lacks: a refresh adds missing skeleton files and never replaces one (`cp -an`, `:651`), so a changed line in an existing skeleton file never reaches a machine installed earlier.
4. To carry something the person made on the live system into the installed one, add its path, relative to the home, on a line of its own in `install/carry.list`; `desk.toml` and `tips.json` are there as examples, and the installer needs no change. Use that for the person's own data, not for defaults. Add the path to `test_the_installed_system_keeps_the_desks_places_and_what_tips_has_taught` in `tests/test_installer.py:419`, which holds the shipped list to what it should carry. A path that a restore point of the home must not roll back (a conversation, a cache) also goes in `HOME_SUBVOLS` (`bombadil-install:44-45`), which matters once something takes such a restore point.
5. Test it by reading the file by path, as `test_the_pill_opens_from_super_and_from_alt_space` does for `hyprland.lua` and `test_the_file_new_systems_ship_holds_only_comments_so_the_standard_picture_shows_and_can_be_watched` in `tests/test_wallpaper.py` does for the `wallpaper` file, or with a booted check like `app-skill-installed` (`bombadil-smoke:123`).

**Add or change a boot entry**

1. Add `iso/efiboot/loader/entries/NN-name.conf` with `title`, `sort-key`, `linux`, `initrd` and an `options` line that begins `archisobasedir=%INSTALL_DIR% archisosearchuuid=%ARCHISO_UUID% cow_spacesize=2G`, as the five entries do; `mkarchiso` fills the placeholders. `loader.conf` names the default entry (`default 01-bombadil.conf`).

A test entry takes a number from 02 to 09, because a release build deletes `0[2-9]-*.conf` (`scripts/build-iso.sh:19-23`): an entry numbered 10 or above would ship.

**Change the quiet console or its colours**
